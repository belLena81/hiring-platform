# Local engineering quality

This project uses local verification and independent agent review. There is no CI/CD pipeline. Neither a commit nor an agent's summary substitutes for running the applicable checks.

## Pure functional core

- Domain functions operate on immutable values and return values or typed errors. Validation and lifecycle transitions must not read clocks, generate IDs, log, access configuration, or perform I/O. Pass time/identity and other required inputs explicitly.
- Represent legitimate absence with `Option`, expected rejection with `Either` or an explicit error ADT, and side effects with Cats Effect. Do not use `null`, sentinel strings, thrown business exceptions, partial pattern matches, or unchecked `.get` to model ordinary outcomes. Preserve existing API absence semantics rather than silently changing them.
- For analytics, actual business failures use the `AnalyticsError` throwable channel; orchestration outcomes such as deferred or released work use typed values. Field-level configuration and value parsing accumulate with `ValidatedNec` and convert to `Either`/IO at the owning boundary.
- Model closed states and expected business outcomes with explicit enums/ADTs. Use `Validated`/`ValidatedNec` when independent input errors should accumulate, then convert to `Either` when sequencing is needed. Do not throw or raise an effect error for an expected domain/repository result and immediately recover it with `attempt`; keep unexpected exceptions in the effect channel and translate them once at the responsible framework or infrastructure boundary.
- Services sequence effects and enforce authorization/atomic use cases. Infrastructure adapters perform database/network work and translate boundary failures. A function returning `IO` is not a pure business function merely because effects are wrapped.
- Use `Resource` for ownership and cancellation-safe cleanup, injected/effectful clock and ID generation at service boundaries, and `Ref`/other appropriate effect primitives for shared state. Avoid mutable global state, detached fibers, `Await`, and unsafe runners inside the application. When framework interop requires execution, isolate it at one documented runtime boundary.
- Use the least powerful abstraction that supports the actual operation. Prefer concrete domain functions; use `F[_]` constraints where they express a useful boundary. Do not build a generic framework, free algebra, or transformer stack solely to appear functional.
- Decision (user-approved 2026-10-14, reversing the earlier concrete-`IO` choice): the main Hiring application migrates its service and repository ports to `F[_]` with the weakest Cats Effect capability each operation needs, as specified in [effect-polymorphic services](specs/effect-polymorphic-services.md). `IO` is chosen only at `Main`, runtime wiring and Sangria interop. The migration is complete: ports and services use `RepositoryF[F, A] = EitherT[F, RepositoryError, A]` and `UseCaseF[F, A] = EitherT[F, UseCaseError, A]`, and the temporary `IO` aliases are removed. Free algebras, mtl stacks and a second runtime remain out of scope.
- Keep expected repository and use-case errors in `RepositoryF`/`UseCaseF` across private helpers and transaction callbacks. Lift raw driver effects once; unwrap only where an external adapter or effect-control boundary must observe outcomes. Mongo exception guards and transaction/session retry control own their required `IO` crossings; background workers may interpret typed outcomes at their processing boundary. Use sequential `traverse_` for ordered writes that must stop on the first expected failure.
- Analytics services and ports use `F[_]` with the Cats Effect capabilities needed by their operations; `IOApp` entrypoints select `IO`. Preserve these existing resource and test seams without adding another effect abstraction. Allocate mutable driver state and observe runtime context inside each effect evaluation. Cancellation must await running driver cleanup before releasing the resources that exclude other writers.
- Optimize through algorithms, batching, indexes, bounded concurrency, and allocation measurement. Encapsulated mutation inside a necessary third-party adapter must not leak mutable state into the domain. Any deliberate departure from these rules needs a concrete rationale and review, not a claim of speed without evidence.

## Typed configuration and dependency use

- Put packaged runtime defaults in HOCON and load through the normal Typesafe Config/PureConfig boundary. Use typed raw and validated configuration values; validate once at startup and return typed failures rather than letting malformed settings reach business code. Isolate blocking file/config parsing in the owning effect boundary where required.
- Use standard `config.file`/`config.resource` selectors and HOCON substitutions, including environment substitutions when needed. Production Scala code must not read environment variables directly or invent another source-merging/precedence layer without an explicit requirement. Test-only environment switches remain test-only.
- Prefer existing, configured dependency capabilities and their idiomatic APIs. Add a dependency only to address a concrete gap; consider Scala/JDK compatibility, maintenance and provenance, transitive surface, and operational cost. Keep integrations behind the appropriate adapter and avoid duplicating library behavior without measured or security-based justification.
- Kafka client pairing: the application build uses fs2-kafka 3.9.1 over kafka-clients 4.3.1 against the `apache/kafka:3.9.2` Compose broker (`build.sbt`, `compose.yaml`). Kafka clients and brokers are bidirectionally compatible across these versions; the pairing is exercised only by the Kafka integration suites, so bump either side in a scoped task that reruns them.

## Authorization and query efficiency

- Use deny-by-default RBAC. Derive actor identity and roles from trusted authentication context; enforce roles and resource ownership in services, not only resolvers. Carry authorization predicates into writes/queries when required to prevent races between an authorization read and a data operation. Keep nested GraphQL loading and request caches authorization-safe.
- Preserve Candidate, Recruiter, and singleton Admin as the current role model. Community/tenant scoping is future work: before activating it, define trusted membership and ensure every affected service, repository query, and unique constraint carries the scope. Never treat a caller-provided community or tenant ID as proof of membership.
- Shape database queries around selective predicates, authorization filters, projection, deterministic order, and bounded pagination. Derive indexes from real access patterns and assess write/storage cost as well as read benefit. In application code, prevent N+1 access, repeated fetch/decode/hydration, unbounded materialization, and avoidable CPU/allocation work.
- For claimed query/performance improvements, capture representative explain/query-plan evidence and compare a reproducible workload before and after, including rows/documents examined versus returned, latency, and relevant resource/write costs. Do not add indexes, caches, or denormalization without a demonstrated use-case benefit.

## Develop and debug through observable behavior

For a behavioral bug, first reproduce the failure with a focused regression test or a documented observation. Trace the failing data through API → service → repository/external boundary, form a specific hypothesis, change one cause, and rerun the relevant check. If an attempt fails, use the new evidence to revise the hypothesis; avoid speculative batches of fixes.

For new domain behavior, use a focused red/green/refactor cycle when practical: see the test fail for the intended missing behavior, implement the general rule, then simplify with tests passing. A compilation/setup failure is not proof that a regression test detects the bug. Do not retrofit ceremony onto prose edits. Tests can be corrected when evidence shows they are wrong, with the changed expectation recorded and independently reviewed; never weaken a test merely to get green.

Exercise real pure functions and the actual effect runtime. Fake external ports for service tests; use a real disposable database for queries, constraints, transactions, and migration correctness. Control time and randomness; synchronize concurrency tests with explicit signals rather than sleeps. Verify results and durable effects, not only that a mock method was called. Test useful laws/invariants, such as rejected transitions leaving state unchanged and replay preserving deduplicated outcomes, where applicable.

## Local settings and data

Keep machine-specific files under the ignored root `.local/` directory:

| Path | Purpose |
|---|---|
| `.local/config/` | Application overrides and local service settings |
| `.local/data/` | Database bind mounts, generated datasets, caches, and analytical checkpoints |
| `.local/logs/` | Runtime logs and local diagnostic output |
| `.local/backups/` | Database dumps and migration recovery copies |

The packaged application logger currently writes to ignored `_logs/` instead of `.local/logs/`; see [logging](logging.md). This implementation mismatch remains explicit until a scoped runtime change aligns the appender. New local diagnostic artifacts follow `.local/logs/`.

The local environment may use ignored `.env`/`.env.*` files where tooling supports them (agent read tools are denied only the root files `.env`, `.env.local`, `.env.development`, `.env.production` and `.env.test`, and edits of any other `.env*` name only get the guard's approval prompt; any other `.env.*` name needs its own exact-path deny rule in `.claude/settings.json`, see [agent development](agent-development.md); prefer `.local/config/` for machine secrets); sanitized `.env.example` and `.env.<name>.example` files remain shareable. Keep local Codex preferences at the ignored `.codex/config.toml`; shared agent rules and skills remain versioned. IDE `.idea/` directories are ignored at every depth.

Commit safe defaults/examples, migration scripts, schema definitions, and deliberately small synthetic test fixtures in their normal source directories. Do not put shared configuration inside `.local/`. Never store real credentials or personal data in example files, and never force-add ignored local data. These are storage conventions, not implemented configuration loading: set up explicit loading/mounts in the relevant application or infrastructure slice. Ignore rules do not protect files already tracked by Git.

## Local checks and readiness

Run from the project root:

```bash
scripts/check-local.sh
```

The command uses Python 3.9+ to validate project-local skills, checks Java 17+ (using `JAVA_HOME` when set), then runs the unit and integration suites of both builds through `scripts/run-local-tests.sh test` and `scripts/run-local-tests.sh analytics` under JaCoCo (6 steps). It therefore requires Docker for the integration services. Each suite run fails when merged unit + integration line coverage is below 85%. **Decision (2026-11-07):** it no longer checks formatting, and it skips a suite whose inputs are unchanged since that suite last passed. Reason: the pre-commit hook formats every commit and agents may not bypass it, so a format check only repeated that work; and a docs-only, spec-only or format-only change reran two hours of tests that could not have changed. The inputs of the root suite are `src/`, `test-support/`, `build.sbt`, `project/`, `docker/`, `compose.yaml`, `compose.test.yaml`, `Dockerfile`, `.sbtopts`, `.jvmopts` and the test wrapper scripts; the analytics suite covers `analytics/` instead of `src/`, `build.sbt` and `project/`; Markdown files are never inputs. The check compares a content hash with `.local/logs/check-local-passed-root` and `-analytics`, written only after a PASS, so committing between runs does not trigger a rerun and a changed input does. `CHECK_LOCAL_FORCE=1` runs both regardless. The risk it controls is a wasted two-hour run; the risk it accepts is that a change outside those paths (for example a dependency resolved from the network) is not retested. It is an explicit local command, not a hook, CI job, deploy command, schema migration, or complete readiness certification. It runs without requiring a Git repository or staged files or any global skill installation.

| Change | Additional evidence before completion |
|---|---|
| Domain/service behavior | Focused positive and negative tests; cancellation/resource tests where relevant |
| DB or resolver behavior | Real-DB and GraphQL integration checks; add the harness in that slice if absent |
| Stored data or wire contract | [Migration and compatibility checks](schema-evolution.md) |
| Performance | Same reproducible before/after workload, query plans/counts, latency/resource/cost comparison |
| Docs/skills | Local references, skill validation, and independent scenario review |

Scala compiler warnings are checked by the build. Scalafmt is configured with standard Scalafmt rules for the Scala 3.9 application and separate Scala 3.7.4 analytics build. At the repository root, run `sbt scalafmtAll scalafmtSbt` to format the application and its build definitions, then `cd analytics && sbt scalafmtAll scalafmtSbt` to format analytics. Check them with `sbt scalafmtCheckAll scalafmtSbtCheck` in each build. These tasks do not run inside the Claude Code Bash sandbox, because scalafmt downloads itself and the sandbox has no route for that; there, the pre-commit formatter runs them outside it.

**Formatting on commit (decided 2026-11-04).** The versioned git hook `.githooks/pre-commit` runs `scripts/format-staged.sh`, which formats the staged `*.scala`, `*.sbt` and `project/*.scala` files of both builds with the scalafmt version each build pins (`sbt scalafmtOnly` and `scalafmtSbt`, so the hook formats exactly as the pinned version does) and re-stages the files it changed; a commit with no such file staged costs under a second because sbt is not started. A staged file that also has unstaged changes is refused rather than formatted, because formatting the working tree would silently stage the unstaged part; stage the whole file or stash the rest. `scalafmtSbt` formats every build file of a build, so an unstaged build file may change in the working tree; the hook reports it and does not stage it. Three git modes are limited by design: during `git commit <path>` git runs the hook on a temporary index while the real index is locked, so a file that needed formatting is formatted in the working tree and the commit is refused; running the same `git commit <path>` again then passes and records only that path (a `git add` from the hook would land only in the temporary index and leave the unformatted copy staged for the next commit, and a plain `git commit` would sweep in other staged work); `git commit --amend` formats only the files staged for the amendment, not files already in the commit being amended (re-stage them or run `sbt scalafmtAll` first); a merge without conflicts and rebase picks do not run `pre-commit`, while concluding a conflicted merge with `git commit` does. A path may contain only letters, digits and `. _ / + @ -` because the paths form one sbt command string, where `;` separates commands; any other character is refused before sbt starts. An edit made to a staged file while sbt runs is staged together with the formatting. The hook starts sbt and therefore loads the working-tree build definition (`build.sbt`, `project/`) with the committer's environment, the same trust as running sbt by hand, which is one more reason to read a pulled build diff before committing on top of it. The hook is enabled per clone by the same `git config core.hooksPath .githooks` as the documentation gate; `git commit --no-verify` bypasses it, so the Claude Code commit hook (`check-docs-current.py --hook`) denies an agent commit that uses `--no-verify`, a short flag group containing `n`, or a `core.hooksPath` override (decided 2026-11-07); this hook is now the gate of record for formatting, because `scripts/check-local.sh` no longer checks it. A person committing in a terminal can still bypass the hook. Why it matters: on 2026-11-04 HEAD `3cffc2f` was committed with one unformatted file, so the next full local check would have failed at the formatting step and the MVP condition 6 run would have been lost to a whitespace diff; formatting at commit time removes that class of failure instead of catching it hours later.

The unit suite (`sbt test`) is Docker-independent. The application has the explicit `sbt 'IntegrationTest / test'` task for live HTTP and disposable MongoDB checks; `scripts/check-local.sh` requires Docker because it includes these suites and the merged coverage gate. Coverage can also be run directly with `sbt jacoco 'IntegrationTest / jacoco'`, which fails below 85% merged line coverage. GraphQL SDL and operation fixtures are checked in the unit suite. Transactions and migrations require disposable MongoDB tests; connectivity tests cannot certify those guarantees. Missing integration/migration/compatibility tests cannot be deferred to a future CI pipeline.

**Analytics test Spark sessions (decided 2026-11-03).** Every analytics unit and integration spec that needs Spark builds its session through `AnalyticsTestSpark.builder(...)` or `AnalyticsTestSpark.session(...)` (`analytics/src/test/scala/com/example/hiring/analytics/AnalyticsTestSpark.scala`); a spec adds or overrides entries on that builder only for a setting it actually tests, and never hand-builds a session from `SparkSession.builder()`. A spec or fixture that obtains its session through production wiring (`SparkRuntime.sparkMongo`) applies the shared settings that can change on a live session through `AnalyticsTestSpark`, never through a local copy of the list. The only exception is a spec whose subject is session construction or lifecycle itself (for example a resource, shutdown or driver-execution spec): it must say so in a comment, and should start from `AnalyticsTestSpark.settings` where that does not defeat the test. Why: on tiny test tables Spark's and Delta's defaults (200 shuffle partitions, 50 Delta snapshot partitions) turn every Delta commit, merge and compaction into hundreds of near-empty tasks. One hand-built session made `KafkaProducerFencerIntegrationSpec` take over 3 minutes for a single record and time out, and the full analytics run took 3h43m against about 2h before. The shared builder keeps the production-semantic settings (UTC, Delta extension and catalog, the vacuum retention check enforced), so the change removes overhead without changing what a test proves. Test JVMs also set the two partition defaults (`spark.sql.shuffle.partitions=2`, `spark.databricks.delta.snapshotPartitions=2`) as system properties in `analytics/build.sbt` (and explicitly for the forked streaming child JVM), so sessions that production wiring creates in-process (`AppModule` batch and streaming runs) get them; production configuration is unchanged. Code Reviewer treats a new hand-built session as a defect; an unexplained jump in the analytics run time is reported as a regression, not absorbed.

## Operator scripts

Every script in `scripts/` that an operator runs (`generate-local-traffic.sh`, `seed-local-jobs.sh`, `run-local-tests.sh`, `check-local.sh`, `check-container-runtime.sh`, `scan-container-images.sh`, `verify-account-deletion-recovery.sh`, `run-acceptance.sh`, `check-skills.py`, `check-docs-current.py`, `check-spec-verdicts.py`, `check-done.sh`, `format-staged.sh`, `check-agent-hooks-live.sh`) follows one contract, so nobody has to guess whether a run is stuck; the live hook check is the exception to the progress rule below, because it prints only when each of its five sessions starts and ends, not every 10 s while a session runs. Container entrypoints under `docker/` and the hooks `guard-harness.py`, `guard-agent-scope.py` and `record-review-run.py` are outside it, as are the `--hook` modes of `check-docs-current.py`, which answers with a hook decision instead of a RESULT line, and `check-skills.py`, which prints nothing on success and exits 2 with the problems on stderr on failure.

1. **Start line:** what the script does, its parameters with defaults, and the expected duration or bound.
2. **Progress:** any wait or loop longer than about 10 s prints a status line at least every 10 s (traffic: elapsed/total and request counts by result; test wrapper: phase, elapsed time, last log line).
3. **Bounds:** every network call and wait has an explicit timeout; retries are bounded; the total run respects its stated duration or a documented limit (`HIRING_TEST_TIMEOUT_SECONDS`, per sbt invocation, default 4 h because a whole `check-local.sh` run was observed at 2h41m-2h47m (full runs on one workstation, 2026-11-07); `HIRING_TEST_LOCK_WAIT_SECONDS`; `COMPOSE_TIMEOUT_SECONDS`, per docker compose call; `SCAN_TIMEOUT_SECONDS`; `CHECK_LOCAL_FORMAT_TIMEOUT_SECONDS`). Out-of-range values exit 2.
4. **Interrupt:** Ctrl+C, SIGTERM or SIGHUP (closed terminal) prints an "interrupted" line with what was completed, stops only processes and temporary files the script itself started, and exits 130.
5. **End:** one line `RESULT: PASS|FAIL|BLOCKED` with counts, duration and the log path where one exists. Exit codes: 0 pass, 1 fail, 2 usage error or precondition not met (BLOCKED), 130 interrupted.
6. **Help and arguments:** `--help` prints usage, parameters, exit codes and examples; invalid arguments exit 2 with a message.
7. **Failures** name what failed and the next action; they never end in a bare stack trace or a silent exit.

Two documented exceptions let credentials into the local measurement scripts; both are opt-in, synthetic-only and loopback-only. `generate-local-traffic.sh --mix search` reads a bearer token of a seeded synthetic candidate from `TRAFFIC_BEARER_TOKEN` or `TRAFFIC_BEARER_TOKENS`, never from an argument, never prints it, and gives it to curl through a 0600 header file in a 0700 temporary directory (`.local/data/traffic.*`) that is removed on exit and on interrupt (after a SIGKILL it may be removed by hand). `seed-local-jobs.sh` writes the random passwords and tokens of its synthetic accounts only to `.local/data/perf-seed.env` with mode 0600, prints the path and never the contents, writes tokens only after a format check (token characters and length, strict ISO-8601 expiry) and fails closed otherwise. Both refuse any base URL whose host is not exactly `127.0.0.1`, `localhost` or `[::1]` (there is no remote option), and the seed script follows no redirect and uses no proxy. The env file is meant to be sourced in a subshell, `( . .local/data/perf-seed.env && scripts/generate-local-traffic.sh ... )`, so the tokens do not stay in the operator's shell. Why: every Mongo-backed query needs authentication and a telemetry-overhead measurement must exercise MongoDB; the risks controlled are a token on a command line or in a log, a token sent to another host, and an unvalidated server value written into a file that a shell will source. The default mix of `generate-local-traffic.sh` stays unauthenticated and unchanged. `scripts/tests/local-traffic-options.sh` is the network-free self-test of their options, validation and percentile helpers.

Output carries no secrets: base URLs with credentials are rejected, and log excerpts come from build and test output only. `scripts/operator-lib.sh` (sourced, not run) holds the shared bounded runner, heartbeat and test-count helpers used by the test wrapper, `check-local.sh` and the image scan. The test wrapper and the formatter write sbt output to a log and print a heartbeat instead of streaming it; follow a log with `tail -f`. The phase shown for `test` and `analytics` runs is inferred from the first sbt summary line in the log. The test wrapper's `kafka` mode (2026-11-05) runs the five Kafka transport integration suites of the root build (`KafkaScramAuthenticationIntegrationSpec`, `ProducerRestartFencingIntegrationSpec`, `OperationalEventComposeIntegrationSpec`, `KafkaTopicRetentionReaderIntegrationSpec`, `KafkaQuietTopicRetentionIntegrationSpec`) directly, like the `interview` mode, with no unit phase. Reason: the `test` mode always runs `sbt test` first, and on a JDK whose lambda metafactory rejects the `SafeDiagnostics` event sink (`LambdaConversionException`, observed on Java 17.0.20.1 at HEAD 1ec7a9d, before any Kafka change) the forked test JVM throws and then hangs until the run limit, so broker-backed evidence for the Kafka flow was otherwise unobtainable; that unit-phase defect was a code linkage defect in `SafeDiagnostics.withEventSink` and was fixed in commit 7133239 (2026-11-04), so the `test` mode completes again; the `kafka` mode stays because it needs no unit phase.

## Review before and after coding

Before substantial implementation, relevant specialists check the ready spec for missing flows, unnecessary complexity, pure/effect boundaries, access patterns, migration/compatibility impact, and testability. Reuse the existing Architect, Data Engineer, Big Data Engineer, Security Engineer, Code Reviewer, and QA roles rather than spawning duplicate reviewer personas.

After coding, review correctness, completeness, security, simplicity, and measured performance. Verify feedback against current source; fix supported blockers or record a source-based explanation for disagreement and obtain the relevant reviewer's updated verdict. Optional ideas become explicit follow-up scope, not silent expansion. The coordinator cannot override a failed gate. End with independent QA of the final state.

## Reused template ideas

Adapted from the supplied `.claude` workflow, `review-spec`, testing guide, performance/completeness reviewers, and review-feedback/systematic-debugging patterns. The generic template's exception-first style is replaced with typed FP errors; ownership checks follow this project's Candidate/Recruiter/Admin model rather than importing an unrelated tenancy model. No Claude-specific slash commands, automatic commits/pushes, worktree hooks, CI watchers, or placeholder passing gates are installed.
