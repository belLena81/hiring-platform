## Source facts

- `analytics/` is a separate Scala 3.7.4 build using Spark 4.0.1, Delta 4.0.0, and Java 17. It already has bounded Kafka batch ingestion, Bronze/Silver/Gold datasets, quarantine, report generation/suppression, Mongo generation/revision publication, erasure controls, and a shared lakehouse mutex.
- `OperationalEventTransforms` parses the existing seven-field envelope, deduplicates Bronze by Kafka coordinate and Silver by event ID, and derives event time from `occurredAt`.
- Phase 6 physical-retention and writer-exclusion gates remain open; runtime activation cannot be provisioned until every new storage surface is covered by erasure and audit paths and all Phase 6 evidence passes.
- The initial healthy-load assumption is at most 500 committed records/minute across three partitions. Use local `local[2]`, fixed-seed synthetic fixtures, and report bursts/backlogs separately. No infrastructure budget or cloud deployment is in scope.

## Contracts

- Run an opt-in resource-managed streaming process with 60-second micro-batches, Kafka `read_committed`, `failOnDataLoss=true`, default `maxOffsetsPerTrigger=1000` (bounded to 100,000), and explicit initial offsets for every Kafka partition. At checkpoint creation, compare the configured partition set with broker metadata and fail on missing or unexpected partitions. Never fall back to `latest`.
- Feed each `foreachBatch` frame into the shared ingestion and publication stages. Preserve coordinate/event-ID idempotency, quarantine, existing report formulas, K=10 suppression, generation/revision guards, and accepted Kafka offset gaps.
- Use stateless Spark topology and application-owned durable watermark/progress. Keep subject-attributed analytical facts under existing deletion/retention control. Native stateful Spark aggregation is out of scope.
- UTC daily windows close when `dayEnd <= previousWatermark`. Open days remain provisional. Advance only after successful guarded publication, monotonically to the greatest admitted, valid, unsuppressed event time minus 24 hours. Cap permitted near-future event times at the batch observation time. Quarantine events more than five minutes beyond observation. These intervals and the 30-day late-fact retention are fixed policy values. Empty, duplicate-only, suppressed-only, quality-blocked, erasure-pending, and idle periods do not advance progress.
- Recheck deletion markers on retries. Persist stable observation time and input identity before Delta writes; derive candidate watermark only from facts admitted after those refreshed checks. Mongo progress and Spark checkpoint are separate durable boundaries and require explicit reconciliation.
- Keep late arrivals for closed days in a normalized 30-day late-fact dataset for explicit replay; store no raw envelope and disable Delta column statistics. Replay selects explicit coordinates, at most 1,000 records per run, preserves original expiry, and cannot advance watermark or bypass deletion/HMAC/generation guards.
- Bind checkpoints to stream/source/lakehouse/contract/settings identity. Missing or incompatible established checkpoints fail closed. Batch ingestion cannot bypass a lakehouse registered to streaming. Ownership is fail-closed, without expiry or automatic takeover.
- Isolate Spark callback execution through Cats Effect `Dispatcher`; query shutdown/cancellation must work while callbacks run, and waiting must not occupy the single Spark driver executor. Use `Resource` for all runtime ownership.
- Keep GraphQL shape and operational event envelope unchanged. Use HOCON/PureConfig and accumulated typed validation. No cloud provisioning, envelope versioning, legacy readers, automatic lakehouse reset, frontend, new report dimensions, dependency upgrades, or broad redesign.

## Design refinements

These refinements are planned implementation requirements. Preserve the existing ports and adapters, pure policies, typed validation, resource ownership, and idempotent natural-key writes. Use capability-specific types and the existing stack; a generic workflow engine or repository framework is out of scope.

| Refinement | Required design and benefit | Acceptance mapping |
|---|---|---|
| Streaming coordinator and recovery state machine | Keep orchestration in a Spark-free application service using progress, publication, deletion-marker, and ownership ports. Model preparation, ingestion, guarded publication, and checkpoint acknowledgement as distinct recovery boundaries. Separate stable input identity and observation time from refreshed deletion checks and publication decisions so retries and faults can be tested through fake ports. | HCS-02, HCS-07, HCS-08, HCS-10 |
| Typed frame boundaries and progress codec | Distinguish raw Kafka frames from parsed operational events within Spark adapters; validate each shape at its owning boundary. Centralize progress schema, ordered row fields, nested partition summaries, outcome decoding, and microsecond timestamp normalization in one adapter-local codec. This prevents raw/parsed schema confusion and schema-less row field lookup. | HCS-01, HCS-02, HCS-07 |
| Testable query lifecycle | Introduce an adapter-private query factory/handle for start, wait, and stop. Waiting must allow cancellation to reach shutdown; cleanup must release callback, checkpoint, and driver resources after cancellation or failed startup. Use deterministic effect signals for lifecycle tests and retain real Spark recovery proofs. | HCS-08, HCS-12 |
| Shared dataset inventory | Centralize dataset paths and applicable privacy, retention, reclamation, and audit policies. Inventory progress, late facts, checkpoints, and temporary/spill storage, including retained files and logs. Distinguish control metadata from subject-attributed facts rather than applying subject deletion indiscriminately. Maintenance and audit paths must consume the inventory so new storage cannot be omitted silently. | HCS-11, HCS-13 |

### Decisions required before dependent implementation

- Define durable lineage registration, initial bootstrap versus established-checkpoint recovery, and reconciliation across Delta streaming progress, Mongo report publication, and Spark offset/commit records. A lost established checkpoint must not become a new stream automatically.
- Define whether `IngestionCommitted` is a recoverable stage or a terminal outcome. Reconcile immutable preparation evidence with retry-time admission and candidate-watermark recomputation after refreshed deletion checks; publication and watermark commits must remain generation guarded.
- Resolve authorization expiry: the contract requires rejection of expired authorization, while the current record has no validity timestamps. Specify validity and startup checks, or explicitly agree a permanent identity-bound grant before changing that contract.
- Define progress pruning and retained lineage/recovery evidence so pruning cannot erase the distinction between bootstrap and resume. Include each storage surface's applicable policy in the inventory.
- Resolve the 60-second trigger versus UC11's Bronze p95 under 30 seconds target before claiming UC11 acceptance. Keep the report p95 <= 120 seconds target and measure healthy load, bursts/backlogs, lag, storage growth, and Spark resource use separately.
