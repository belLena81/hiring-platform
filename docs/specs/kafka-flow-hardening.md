- Facts: one Kafka transaction per outbox record; one synchronous commit per consumed record; decoders (Circe and Spark) reject any envelope/payload whose key set differs from the exact known set; no record headers; transactional id = prefix + fresh UUID per producer lifetime, registered per subject in `producer_registrations` with `_id = subject:transactionalId` and states Active/Fenced (Fenced rows expire after 8 days); fencing is admin `fenceProducers` by transactional id; SASL/PLAIN on all listeners; topic provisioning only in `docker/kafka/provision-access.sh` (1 partition, RF=1); consumer `partition-concurrency = 4`; no consumer lag or producer metrics; no `max.poll.*` tuning; kafka-clients 4.3.1 against broker image 3.9.2.
- Decisions (user, 2026-11-04):
  - D1 Publication sends one Kafka transaction per publication wave (the claims returned by one claim call, at most `PublicationWaveSize`). Reason: a transaction costs two coordinator round trips; per-record transactions give nothing beyond idempotence because no consumer offsets are included. Controls broker load and publisher latency.
  - D2 Consumers commit offsets per batch (`commit-batch-size`, `commit-batch-interval-ms`), never per record. Correctness stays with the durable receipt/quarantine before the offset is emitted. Controls commit RPC volume and rebalance cost.
  - D3 Wire contract becomes evolvable with JSON kept: records carry headers (`content-type`, `hiring-schema-version`, `hiring-event-type`, `hiring-event-id`, `traceparent` when a span exists; interview records carry content type, version and `hiring-step`); decoders accept unknown additive fields and still reject missing or wrongly typed known fields; an unsupported version header quarantines as `UnsupportedVersion`; header/body disagreement quarantines as `MalformedEnvelope`. The body stays authoritative; the fingerprint stays over the value bytes so erasure identity and duplicate detection are unchanged. Reason: tolerant reader is the precondition for additive evolution; headers carry metadata without parsing the body.
  - D4 Producer identity splits into a stable transactional id (`<role prefix><worker id>`) and a per-lifetime generation id (UUID). A restart with the same worker id fences its predecessor through Kafka's epoch bump. Registry rows are keyed `subject:transactionalId:generationId` with `registeredAt` stamped by the database clock (`$$NOW`) and the retirement cut-off read from the same clock (review fix 2026-11-05; index `(transactionalId, state, registeredAt, _id)`); erasure fences by transactional id on the broker and marks Fenced only the generation ids it read, so a replacement generation that registered after the fence stays Active. One worker id per running instance (`KAFKA_WORKER_ID`, `INTERVIEW_WORKER_ID`); two instances sharing an id fence each other, which is documented as misconfiguration. Reason: zombie fencing on restart without operator action; the generation id keeps per-lifetime attribution for erasure.
  - D5 Topic contract is documented per topic (partitions, RF, min ISR, retention, segment, max bytes, owner); local stays 1 partition/RF=1. Consumer partition concurrency is bounded by partitions.
  - D6 Client listeners authenticate with SCRAM-SHA-512; the controller listener keeps PLAIN with the single broker principal (KRaft bootstrap simplicity; production formats storage with `--add-scram`). Clients default to SCRAM; PLAIN is allowed only under the existing loopback/plaintext rule and only for the test broker until migrated.
  - D7 Kafka client observability: consumer lag gauge, producer send duration and failure counter, rebalance counter, under OpenTelemetry with no hiring data in attributes; alert rules for sustained lag and publisher failure ratio.
  - D8 Consumers set `max.poll.records` and `max.poll.interval.ms`; producer sets `compression.type=lz4`, `linger.ms=5`; receipt consumer stays a placeholder with its revisit trigger documented; clients 4.3.1 vs broker 3.9.2 recorded as compatible.
- Architect review (2026-11-04, folded in): D1 wave failure semantics (lease lost during send: abort, leave the lost claim, release the others without charging an attempt, tolerate Conflict; producer fenced mid-wave: release every claim uncharged, end the generation; markPublished per claim independently; attempts are charged only on single-claim sends, a multi-claim non-broker failure releases uncharged and the claims retry as single-claim waves; `transaction.timeout.ms` set explicitly below the lease). D2: rebalance-caused commit failures (`CommitFailedException`, `RebalanceInProgressException`) are non-fatal (logged, counted, dropped); the permit is held only around processing, never around the commit; the redelivery bound is `maxPrefetchBatches × max.poll.records`. D3: producer side stays strict (exact key sets on encode/outbox insert), reader tolerant; headers are optional metadata permanently (absent version = 1), duplicates, non-UTF-8 or oversize header values are `MalformedEnvelope`, headers are never persisted to Bronze or quarantine, fingerprint excludes headers; `schema-evolution.md` requires a privacy classification before any additive field is emitted. D4: retirement reads with a cut-off before fencing and marks only pre-cut Active rows by `_id`; `markFenced` always by read `_id` with an Active guard; analytics erasure requires the registry migration complete; a generation registers only after `initTransactions` succeeded and a new generation id is drawn on every init; sustained ProducerFenced failures are the misconfiguration signal for shared worker ids; production worker ids come from per-instance identity (pod ordinal), never a replica-shared variable. D7: lag comes from the client's `records-lag` metric snapshot, not from broker calls under the consumer lock; `error.type` is a closed set (outermost Kafka exception class or `other`), never record keys, ids or the cause chain; rebalance counter has group and kind attributes; revoked partitions drop their series. D5: changing a partition count remaps keys and erasure barriers cover only captured partitions, so it is an operator procedure (drain erasure, stop producers). Naming: `OperationalEventHeaders` (not `KafkaRecordHeaders`); glossary distinguishes "Producer generation" from the analytics "Report generation".
- Assumptions: local volume is low, so wave size 4 and commit batch 100 are starting values, not measured optima. SCRAM on KRaft 3.9 client listeners works with users created via `kafka-configs.sh` after broker start (validated by integration run).
- Open questions: none blocking.
- Follow-up fixes from the documentation source check (2026-11-05): (a) producer `delivery.timeout.ms` and `transaction.timeout.ms` are derived as `max(10000, lease*1000 - 5000)` from the publisher lease (floor 15 s, `KafkaLeaseSeconds`) or the interview claim window, `request.timeout.ms = min(10000, delivery/2)`, so send plus commit stays inside the lease (KFH-08.2 tests); (b) the interview consumer verifies content type, version and `hiring-step` headers, refuses duplicate/oversize/non-UTF-8 headers and bodies with repeated keys (KFH-03.2/03.3/03.7 interview tests); (c) Spark validity applies the same malformed-header rules as the Circe reader (KFH-03.7 Spark tests, 68 analytics tests pass).

## Behavior and contracts

- Publication wave (D1): claim up to N events (one per partition key at most, enforced by the claim), renew every lease for the duration of one `produceWithoutOffsets(chunk)`; success marks each claim Published independently; a send failure is classified once (`isBrokerUnavailable`, `isProducerFenced`): a broker-unavailable failure or a single-claim wave keeps the attempt charge (`releaseForRetry`, or `markFailed` at max attempts), a fenced producer or a multi-claim non-broker failure releases every claim uncharged (`releaseUncharged`) and the events retry one per wave; a lease lost before the send aborts the wave with nothing sent and releases the other claims uncharged.
- Batched commit (D2): per partition, processed offsets flow through `commitBatchWithin(size, interval)`; a record that is not durable raises before its offset is emitted and stops the partition stream, so no later offset of that partition can commit.
- Headers and tolerant reader (D3): see Decisions. Required envelope keys and required payload keys per event type remain exactly today's sets; unknown keys are ignored in both Circe and Spark validity. Version `1` is the only accepted value.
- Producer identity (D4): `ProducerWorkerId` matches `[a-z0-9][a-z0-9-]{0,63}`. Registry row: `subjectId, transactionalId, generationId, kind, state, registeredAt, fencedAt?, expiresAt?`, validator updated, indexes `(subjectId, kind, state, _id)`, `producer_registration_generation_state` `(transactionalId, state, registeredAt, _id)` (retirement filter and page order), TTL on `expiresAt`; `registeredAt`, `fencedAt` and `expiresAt` are stamped by the database clock. Migration (new ordinal after the latest applied): rewrites existing rows so the old UUID suffix becomes `generationId` and the stored transactional id is kept, pre-MVP direct cutover, stop earlier writers first, forward-only recovery. Registration upsert keys on the new `_id` without the Active filter. `canonicalPrefix`/`validateProducerIds`/`LogFields.validPublic` accept prefix + worker id; a `GenerationId` log field is added.
- SCRAM (D6): provisioning creates the seven client users idempotently from the secret files; clients use `ScramLoginModule`; the `jaasLiteral` escaping stays.
- Observability (D7): `hiring.kafka.consumer.lag {record}` attributes `hiring.consumer.group`, `messaging.destination.name`, `messaging.kafka.partition`; `hiring.kafka.producer.send.duration s`; `hiring.kafka.producer.send.failures {failure}` attribute `error.type` = sanitized class name; `hiring.kafka.consumer.rebalances {rebalance}`.

Invariants: at-least-once publication with idempotent consumers; one in-flight event per subject; a Fenced generation never publishes again.
