## Desired behavior

### Actors and authorization

Candidates search only visible open jobs and obtain recommendations for their trusted authenticated identity. Recruiters request matches for owned open jobs; preserve the current explicitly authorized Admin behavior. Validate role/ownership before query embedding, search or facet calls. Nested/direct-ID access and cache keys obey the same policy. Search results remain advisory; ranking never applies, accepts or rejects an application.

Private candidate residence, availability and consent remain owner-only values. Matching retains the HSE semantics: opted-in candidates satisfy supplied private filters, opted-out/missing-consent candidates bypass only those private filters, and all candidates satisfy active-account, role, required-skills and model predicates. Do not use private filter values as new ranking features, facet dimensions or explanations merely because they are available in persistence.

All new retrieval paths must reuse the Phase 8 authoritative eligibility recheck and bounded short-result behavior. A deleted/closed/ineligible hit is discarded before output; failure to recheck yields sanitized unavailability. A concurrent update after the final read does not create a response-lifetime snapshot guarantee. The API must document this boundary.

### Radius discovery

The caller supplies structured center coordinates and radius; the service does not infer their location, geocode text, or persist a candidate tracking history. Validate finite latitude/longitude and positive bounded radius with typed values before database/provider work. Define units, maximum radius, coordinate order and boundary inclusion in the accepted contract before implementation; reject impossible coordinates rather than clamping or guessing units.

Radius combines with existing job filters and visibility using conjunction. Jobs without accepted structured coordinates cannot satisfy a radius filter; they remain eligible for searches that omit it. Preserve existing city-only queries. A radius query must never silently fall back to city text or ignore distance when the geo index is missing. Empty geographic matches return an empty page.

Distance is calculated by the selected Mongo/Atlas geographic capability, with tested agreement at the agreed boundary/tolerance. Exercise identical coordinates, just-inside/on/outside radius, negative longitude, poles/antimeridian and missing coordinates. Do not implement unbounded all-job distance calculations in application memory.

Radius results require deterministic cursor pagination with a unique ID tie-breaker, including equal-distance/rank cases. The selected sort, encoded cursor coordinates, query fingerprint and concurrent-index limitation must be explicit in the contract decision. Reject a cursor bound to different filters or ranking policy. Stable data must page without gaps or duplicates; concurrent edits/index refresh may reorder results unless a separately accepted snapshot mechanism is introduced. No generic snapshot store is implied.

Distance exposure, ordering precedence between relevance and distance, remote-job semantics and multiple job locations are product choices below. Implementation must not invent them from the existing free-text city field. New coordinates are supplied through authorized recruiter/Admin job mutation inputs after validation; candidate queries cannot rewrite a job's location.

### Lexical search and facets

Support an evaluated lexical alternative alongside current vector/hybrid behavior, using explicit index fields/analyzers and bounded query inputs. Fixed-path query builders accept typed values; caller text cannot supply search operators or arbitrary field paths. Keep query language/tokenization choices visible in the evaluation fixture set, including punctuation, casing, empty input and multilingual cases if the corpus actually covers them.

Facet counts must correspond to the selected query's eligible visibility/authorization set and agreed facet-filter semantics. No count may reveal closed jobs, deleted entities, another recruiter's restricted data or candidate private attributes. Counts over only the returned top-K cannot be labeled corpus totals. A stale index cannot be trusted for authorization-sensitive totals; select a provably authorized aggregation strategy or return facets unavailable rather than exposing unreconciled counts. Do not hydrate an unbounded candidate set to repair counts.

Bound facet dimensions, bucket count and request cost; sort bucket ties deterministically. Missing values are omitted or placed in an explicit bucket only after the facet contract chooses that policy. Facets and hits use the same query/filter identity. If a consistent exact count cannot be provided, an explicitly accepted approximate/unavailable contract must explain it; never silently call an estimate exact.

Missing/incompatible indexes, unsupported Atlas capabilities and timeout return typed sanitized unavailability. No silent fallback changes lexical analyzers, fusion algorithm or count meaning. Local Community Mongo checks validate core workflows but cannot certify actual Atlas lexical/vector/facet execution.

### Recommendations, matching and personalization

Establish a fixed Phase 9 relevance baseline before evaluating a new personalized ranking. Start from the simplest candidate: existing application RRF/vector behavior and deterministic skill evidence. Proposed features must be authorized, necessary and available at ranking time. Do not add sensitive profile inference, protected attributes, private residence/availability signals, or behavioral tracking without a separately specified purpose, consent/retention policy and review.

Separate candidate generation from pure ranking. The ranking function accepts a bounded authorized hit list and typed allowed features, returns stable scores/order and deterministic evidence, and performs no I/O. Retain original retrieval score where the existing contract does so. Missing permitted features produce an explicit baseline behavior, not invented values. Tie order must be stable and described in evaluation records.

Evaluate overall and use-case/filter subgroups on held-out fabricated human judgments. Include cold profiles, missing skills, sparse matches and counterfactual fixtures where only a disallowed/private attribute changes; such changes cannot affect ranking. Do not turn the score into a probability of hiring success or expose model-generated personal rationale.

Adopt only if pre-agreed relevance, latency, privacy and cost gates pass. Otherwise record an explicit defer decision and retain existing default ranking. A defer outcome can close the experimental-personalization decision criterion; it does not close unimplemented radius, lexical or facet criteria. The current strategy selector remains the configuration seam; add a concrete algorithm only after its evaluation justifies it.

### Freshness, provider failures and recovery

Use current model and source-hash checks for recommendation/match query embeddings and authoritative result validation. Preserve version-guarded writes and the Phase 9 shared preparation contract. No new embedding version field is implied; if model/schema identity changes, specify it independently from aggregate revision and update the one active contract.

Provider timeouts, malformed vectors, cancellation and stale-write conflicts keep typed outcomes and existing ownership. A user search failure does not block operational hiring transactions. Durable embedding repair resumes after restart, and a revoked/deleted entity cannot be resurrected by delayed provider results. Keep one bounded retry owner per operation; no retry of validation or authorization failures and no hidden provider fallback.

## APIs, persistence and code boundaries

The approved local additions are optional `GeoPointInput` on job location, `nearbyJobs(center, radiusKm, filter, first, after)` returning job, kilometre distance and cursor plus `hasNextPage`, and `jobDiscoveryFacets(filter, center?, radiusKm?)`. Facet center and radius must appear together. Existing semantic search fields retain their contracts. Invalid coordinates/radius/filter/page size and mismatched cursors return sanitized typed errors. Discovery is authorized for active Candidates and singleton Admin; Recruiters are denied.

Before MVP, update the single active GraphQL/cursor/event shape directly with its consumers/fixtures; do not introduce legacy readers, versioned endpoints or dual writes. Geographic operational Mongo storage and indexes require a new restartable migration/verification plan, bounded scanning, concurrent-write behavior and recovery checks. Never infer coordinates from city strings or backfill private information. Missing old coordinates must have an explicit allowed representation. Old binaries that replace job records may be incompatible; define stop/cutover conditions before new writes. Existing migrations remain immutable.

- Domain: immutable geographic criteria and ranking inputs, smart constructors, pure validation/decisions, exhaustive ADTs and typed IDs. Pass time/identity explicitly; no Mongo/GraphQL/Circe/provider dependencies.
- Application: retain `UseCaseIO`/`RepositoryIO` over `IO`; services sequence authorization, query execution, authoritative checks and result assembly. Preserve typed errors through private helpers.
- Adapters: Mongo/Atlas owns geospatial/query stages, analyzers, projections, counts and cursor execution; GraphQL owns coercion and public error mapping; provider adapters own network/vector validation.
- Validation: `ValidatedNec` accumulates independent input/configuration errors, then `Either` sequences decisions. Use `Option` for absence; no nulls, business exceptions or partial `.get`.
- Runtime: existing `Resource` owners release clients/cursors/workers under cancellation; bound branch budgets, facet buckets, batches and concurrency using existing FS2/Cats Effect tools.
- Maintainability: small typed filter builders suffice; Composite needs accepted nested Boolean criteria. A new Strategy needs a concrete evaluated algorithm. Avoid generic discovery frameworks, caches and new infrastructure without measured need.

### Problem and rule

`jobDiscoveryFacets` today counts the structured filter set only. A candidate who typed a text query cannot get facets for that query. Requirement: facets for a text query use the same query and filter identity as the lexical results, and counts are computed from the authoritatively eligible set (Open job, authorized actor), never from the index. Never present a bounded count as an exact total, never trust a lagging index for authorization-sensitive totals, never hydrate an unbounded set.

User decisions (2026-10-13): (1) facets ignore the embedding-model predicate, so Open jobs without a current embedding are counted; (2) a broad query is not "unavailable": counts cover the top-N lexical matches (N = the cap) and the payload labels that coverage explicitly; `SEARCH_UNAVAILABLE` is unchanged; (3) index lag for newly opened jobs is accepted and documented, and the Atlas Local test records it.

### Source facts (inspected 2026-10-13)

- `JobFacetQuery(filter, radius)`, `JobService.jobDiscoveryFacets` (validate, `discoveryScope` allows Candidate/Admin only, then repository) and `MongoJobRepository.jobDiscoveryFacets` (optional `$geoNear` first stage or `$match` of `discoveryFilter`, then `$project` and one `$facet`; at most 21 buckets read per dimension, 20 returned, `truncated`; count descending then value ascending) run inside the users-collection `$lookup` wrapper `authorizedDiscoveryPipeline`, which re-reads the actor as Active with the right role.
- `discoveryFilter` is the authoritative predicate: `status = Open`, optional `location.city`, `skills $all`, `createdAt >= createdAfter`. Embedding data is not part of it.
- The job lexical branch is `$search` on `jobLexicalIndex` (`text` on `title`, `description`, `requirements`, `skills`, with a `filter` clause from `SearchEligibilityCriteria.jobs(model, filter)` rendered by `MongoSearchEligibilityRendering.indexed`), limited to `branchResultLimit`. That criteria includes the embedding-model predicate, which is correct for hybrid hits but not part of authoritative eligibility.
- The job lexical index (`MongoAtlasSearchSetup.jobLexicalDefinition`, `dynamic: false`) maps `title/description/requirements` as string, `skills` as string and token, `status` and `location.city` as token, `createdAt` as date, `embeddingMeta.model` as token. It has no `location.country` and no boolean `location.remote` mapping.
- Query text is capped at `SearchableText.QueryMaxChars` (2048) with `SearchError.InputTooLarge`. `jobDiscoveryFacets` complexity is `100 + child` and the root is in `expensiveRoots`.

### Strategies compared

| | (a) `$search` bounded ID set, then exact structured aggregation | (b) `$searchMeta` facet collector | (c) `$search` then hydrate hits and count in memory |
|---|---|---|---|
| Counts from | Authoritative `jobs` collection restricted to matched IDs, with `discoveryFilter` re-applied | The search index | Application memory |
| Over-inclusion (closed/deleted/lagging) | Impossible: eligibility re-evaluated from operational truth | Possible: counts reflect index state, so authorization-sensitive totals trust a lagging index; reconciliation needs per-hit fetches or an unavailable result | Impossible after hydration |
| Omission (newly opened job not yet indexed) | Possible, same as lexical hits; reduces a count, never leaks | Same | Same |
| Index change | None | Yes: `location.country` mapping, `remote` as token, facet-capable mappings; new index names, readiness gates, cloud/preview risk | None |
| Cost | One `$search` of at most 1001 IDs plus one `_id`-bounded aggregation over at most 1000 documents | One `$searchMeta` call | Unbounded or capped hydration of full documents |
| Works with radius | Yes: `_id $in` inside the `$geoNear` `query` | No (`$geoNear` must be first) | Partially |
| Exactness claim | Exact over the matched, currently eligible set when the match set is complete | Exact only over the index's view | Exact only if the whole set is hydrated, which is unbounded |

Recommendation: **(a)**. It is the only option that keeps the existing authoritative aggregation, needs no index change, composes with radius, and makes over-inclusion impossible by construction. Its cost is bounded by a fixed ID cap, and the price of that bound is that a broad query is counted over only its top-N lexical matches, which the payload labels `TOP_MATCHES` (user decision) so it is never read as a total. (b) is rejected for now because the index can lag and its counts would need reconciliation anyway; (c) is rejected by the no-unbounded-hydration rule. Revisit (b) with reconciliation if measured `TOP_MATCHES` rates make the labelled scope unhelpful.

### Data Engineer review outcome (2026-10-13)

Verdict: **PASS**. No index, mapping, setup or migration change is required. Product decisions (embedding predicate ignored, `coverage`/`coverageLimit`, accepted index lag) were taken as given. Source checked: `MongoAtlasSearchSetup.jobLexicalDefinition` (and `validLexical`, a subset-inclusion check), `MongoJobRepository.jobDiscoveryFacets`, `authorizedDiscoveryPipeline`, `discoveryFilter`, `MongoHiringIndexSetup` jobs indexes. Figures below are design reasoning, not measurements; the implementation must replace them with the evidence listed in D5.

**D1. Cap N = 1000 confirmed (default).** Step 1 is one `$search` with `$limit 1001` directly after it (so the limit reaches mongot), then `$project {_id: 1, score: {$meta: "searchScore"}}`. The index has no `storedSource`, so mongod resolves each hit by an `_id` lookup (about 1001 point reads of full job documents). That is bounded and acceptable; adding `storedSource` would be an index change and is rejected until HDQ-12.C shows `$search` latency at the cap is a problem. Step 2 sends at most 1000 string IDs (about 50 KB, far below the 16 MB command limit; a Set removes duplicates). The `_id $in` lets the planner use the `_id_` index with at most 1000 point bounds, so documents examined should be at most 1000 on the non-radius path, and the `$project` before `$facet` keeps the buffered documents to four small fields (far under the 100 MB stage limit; `$unwind` output is bounded by skills per job, which the implementation records from the validator's maximum). The configured cap must be validated to 1..5000 so a misconfiguration cannot produce an unbounded `$in`. Stale-index note: a job closed after indexing still occupies a slot in the 1001 window and is removed only in step 2, so a `TOP_MATCHES` result may count fewer than N jobs; this is accepted and documented, never an over-count.

**D2. Ties: accept mongot window membership, make the in-window order deterministic; no indexed sort.** Score-then-`_id` `$search` sort would need `_id` mapped as `token` in `jobLexicalDefinition`, which means a new index name, a rebuild, an updated required definition and a readiness gate under the repeatable setup verification (fail closed on mismatch, no drops), plus sort-by-doc-values cost on every query, and it would still not make Lucene scores stable across segment merges. The benefit is only a stable pick among exactly tied boundary jobs in a result already labelled `TOP_MATCHES`. Decision: project the score, sort the window by score descending then ID ascending in the application, and drop the last element. This is deterministic when the tie spans ranks N and N+1 and both are in the window; if a tie extends beyond the window, membership is mongot's and is not claimed deterministic. HDQ-12.3 tests the first case with a fake matcher; Atlas Local does not assert tied-boundary membership.

**D3. Authorization: service-level check before the matcher is sufficient; the `$search` does not run inside the wrapper.** `$search` must be the first stage of its pipeline and cannot share the first-stage slot with `$geoNear`, and the N+1 coverage signal needs the IDs outside the aggregation, so the single-pipeline form is rejected. Safety argument: (a) the matcher output is a set of IDs of jobs that were Open at index time and is never returned to the caller, so a stale or revoked actor learns nothing from step 1; the service denies Recruiter, non-Active and unauthenticated actors before calling it (HDQ-12.6, matcher call count zero); (b) step 2 still runs through `authorizedDiscoveryPipeline`, which re-reads the actor as Active with the right role in the same operation that produces the counts, and returns `AuthorityRevoked` otherwise; (c) counts come only from step 2, whose predicate is `discoveryFilter` (`status = Open`, plus city, skills, createdAfter) intersected with `_id $in`. Jobs have only Draft/Open/Closed in source and no separate soft-delete or visibility flag, so `status = Open` is the whole eligibility predicate; a hard-deleted job is simply not found. A set of IDs can therefore only restrict the result: an ineligible ID matches nothing, so counts cannot include ineligible jobs. The `$in` clause must be added to the same `$and` and never replace `discoveryFilter`.

**D4. Radius: put the ID restriction inside `$geoNear.query`; keep `$geoNear` first.** Stage order is `$geoNear` (query = `discoveryFilter` AND `location.remote = false` AND `_id $in`), `$project`, `$facet`, as today. Caveat: `$geoNear` always drives from the `jobs_location_point` 2dsphere index; the `_id` clause is a residual filter, so documents examined scale with the Open jobs with coordinates inside the radius, not with N. This is no worse than today's exact structured radius facets, which examine the same geo candidates, and it keeps the same distance semantics as the existing radius path. A `$match` with `$geoWithin`/`$centerSphere` plus `_id $in` would examine at most N but has not been proven boundary-equivalent to `$geoNear`, so it is not adopted; it becomes a candidate only if D5 shows examined far above N at the largest permitted radius, and then only with a boundary-equivalence test. ### Source facts (inspected 2026-11-10)

- **How the existing order and ties work:**
  - `HybridRankFusion.retrieval` is the application RRF, with `RankConstant` 60. It orders by fused score, highest first. On equal scores it compares branch ranks in branch order: the first branch where the two hits differ decides, and a hit absent from that branch loses (`Int.MaxValue`). The last tie-breaker is the identifier string in ascending order (UUID text). `fuseJobs` (vector, then lexical) and `fuseCandidates` (job vector, then query vector, then lexical) use it.
  - The vector-only paths are `recommendedJobs`, and `candidateMatches` without query text. They return the order in which `$vectorSearch` emits hits. `jobVectorPipeline` and `candidateVectorPipeline` run `$vectorSearch`, `$set score` and `$project`, with no `$sort` and no application tie-breaker. Native fusion sorts by score (highest first), then by `_id` ascending.
  - `SemanticSearchService` keeps the retrieval order through the authoritative recheck. `liveHits` removes duplicates and drops hits that are gone or no longer eligible. The service then applies `take(first)` and sets `matchedSkills = SkillMatching.matched(candidateSkills, jobSkills)`, which uses the job's spelling and `SearchTerm.canonical`.
- **Public contract.** The `ScoredHit` interface on `RankedJob` and `RankedCandidate` already exposes three fields: `score` (the retrieval, fusion or rerank score), `retrievalScore` (the fusion score, kept when rerank reorders) and `matchedSkills`. Under Q7 option B (2026-11-10), adoption changes none of these fields: `score` and `retrievalScore` keep their current meanings, `matchedSkills` keeps its meaning, and the ranker's fused value is mapped to no field. The decision record below gives the reasons.
- **Bounds.** `PageSize.Max` is 100. The repository branch limit is `branch-result-limit`, or `num-candidates` (100) when that is unset.
- **Evaluation code.** `SearchEvaluationAssessment`, `SearchEvaluationHarness`, `SearchEvaluationMetrics`, `SearchEvaluationCapture` and the fixtures are test sources under `src/test/.../service/search/`, not `src/main`. `SearchEvaluationStrategy` is a parameterized enum. Its four retrieval cases are `Lexical`, `Vector`, `ApplicationRrf` and `AtlasAnn`. Slice 2 adds `SkillEvidenceRanked(underlying)`, which names the retrieval strategy it ranks over. It is not a retrieval branch: the integration retrieval raises `Unavailable` for it. `SearchEvaluationStrategy.values` no longer exists, and nothing used it. The assessment returns `Recommend`, `Defer` or `Reject`:

With an allowance of 0 the relative rule is the strict `>`. An absolute-budget breach (`AbsoluteLatencyBudgetExceeded`) is a `Defer` reason, not a `Reject` reason (see [Latency](#outcomes)). ### Problem and non-goals

Both sides rank by retrieval similarity alone. A hit that covers more of the job's listed skills can rank below one that covers fewer. HDQ-07 defines a ranker that may promote visible skill coverage within the authorized retrieved list. HDQ-08 decides from evidence whether that ranker replaces the default.

Non-goals:

- Behavioral tracking: search sessions, clicks, views, applications, dwell time, or recruiter decisions.
- Private residence, availability or consent, protected attributes, and any proxy for them (including name) as features.
- A probability of hiring success, or any calibrated likelihood.
- Model-generated rationale, an LLM or a learned model.
- Native `$rerank` (HSE-05.C).
- A selector or configuration entry, or a Strategy, before adoption.
- Any change to retrieval, eligibility, authorization or the GraphQL schema.
- `semanticJobSearch`, whose intent is the caller's query, not the profile. Outside the ranker (Q8, 2026-11-10).
- The degraded lexical fallback, which is not evaluated and keeps its order. Outside the ranker (Q8, 2026-11-10).
- Automatic hiring decisions.

### Allowed features

A feature must be authorized, necessary and available at ranking time.

| Feature | Recommendations (candidate to jobs) | Matching (recruiter to candidates of an owned open job) | Why allowed |
|---|---|---|---|
| Retrieval rank | 1-based position of the job in the `recommendedJobs` list after the authoritative recheck | 1-based position of the candidate in the `candidateMatches` list after the authoritative recheck | Already computed. The ranker uses rank rather than raw score because vector, lexical and RRF scores are not comparable across modes or models. |
| Skill evidence | Distinct canonical job skills covered by the caller's own profile skills, out of the job's distinct canonical skills | Distinct canonical skills of the owned job covered by the candidate's profile skills, which the minimized DTO already returns, out of the job's distinct canonical skills | The caller can already see both inputs, and the normalization is the same as `matchedSkills`. With distinct canonical counts it equals matched / (matched + missing) in the planned `missingSkills` field of [GDF-02](guided-discovery-and-followup.md). |

The retrieval score is not a ranker input. The ranker reads only the retrieval rank and the evidence.

| Excluded | Reason |
|---|---|
| Residence, availability, consent | These are private, owner-only values (see [Actors and authorization](#actors-and-authorization)). Consent decides eligibility only. |
| Name, email, ID text | A name can be a proxy for a protected attribute, and IDs carry no relevance. The ID text is used only for validation. |
| Protected attributes or inferences about them | Not stored. Inferring them is a non-goal. |
| Experience summary text | Scoring free text needs a language model. |
| Sessions, applications, clicks, views, recruiter decisions | This would be behavioral tracking, or learning from human decisions. It needs its own purpose, consent and retention specification. |
| Job recency, city, country, remote | Not needed for this problem. Recency needs an injected clock, and a location preference would need private residence. A later experiment may take these up. |
| Raw retrieval score, embedding vectors | Retrieval rank already expresses them, and raw scores are not comparable. |
| Number of candidate skills | It would reward skill stuffing. Evidence counts the job's skills only. |

### Ranker contract

The ranker lives in `com.example.graphQL.cats.domain.search`, beside `SearchFusionStrategy`, in `SkillEvidenceRanking.scala` (slice 1). Its unit tests are in `src/test/scala/com/example/graphQL/cats/domain/search/SkillEvidenceRankingSpec.scala`.

- **Dependencies:** it depends only on `domain.model` (`SearchTerm`) and cats data types. It uses no Mongo, Circe, GraphQL, provider, clock, configuration, logging or `IO`.
- **Callers:** none in production until adoption. No service, resolver, repository or runtime file references it. Its callers are test sources only: its unit tests, and the slice 2 evaluation composition `SkillEvidenceRankedComposition.scala` under `src/test/.../service/search/`.

Signatures to implement (names are final unless the Code Reviewer finds a glossary conflict):

```scala
final case class SkillEvidence private (covered: Int, required: Int)
object SkillEvidence {
  /** None when the job lists no skill or no job skill is covered: no evidence, never an invented zero. */
  def of(candidateSkills: Set[String], jobSkills: Set[String]): Option[SkillEvidence]
}
final case class RankingHit[Id](id: Id, retrievalRank: Int, evidence: Option[SkillEvidence])
// Output element. fusedValue is internal: no API field maps it, on adoption or otherwise (Q7, option B).
final case class RankedHit[Id](id: Id, retrievalRank: Int, evidence: Option[SkillEvidence], fusedValue: Double)
enum RankingBasis { case RetrievalOrder, SkillEvidence }
final case class RankingOutcome[Id](basis: RankingBasis, hits: List[RankedHit[Id]])
enum RankingInputError {
  case InvalidLimit(limit: Int); case TooManyHits(limit: Int)
  case NonPositiveRetrievalRank(rank: Int); case DuplicateRetrievalRank(rank: Int)
  case BlankKey; case DuplicateHit(key: String)
}
object SkillEvidenceRanking {
  val RankConstant: Int = 60 // the HybridRankFusion constant, reused, not tuned
  def rank[Id](hits: List[RankingHit[Id]], maxHits: Int)(key: Id => String)
      : Either[NonEmptyChain[RankingInputError], RankingOutcome[Id]]
}
```

1. **Validation.** Errors accumulate (`ValidatedNec`), then convert to `Either`. The rules:
   - `maxHits` must be at least 1.
   - `hits.size` must be at most `maxHits`. An oversized input fails with `TooManyHits`; it is never truncated silently.
   - Each `retrievalRank` must be at least 1 and unique.
   - Each `key(id)` must be non-blank and unique.
2. **Skill evidence.**
   - `required` is the number of distinct non-blank canonical job skills.
   - `covered` is the size of the intersection with the candidate's canonical skills.
   - The result is `None` when `required` or `covered` is 0. Candidate skills outside the job's set add nothing.
3. **Evidence rank.** Hits with evidence get a competition rank: 1 plus the number of hits whose coverage is strictly greater. Coverage is compared exactly: `covered_a * required_b` against `covered_b * required_a`.
4. **Internal fused value.** The value is `1/(60 + retrievalRank)`, plus `1/(60 + evidenceRank)` when the hit has evidence. It is a two-term Double sum, so the order of addition cannot change it. Each output hit carries it as `fusedValue`, for the evaluation and tests. The value is internal: no GraphQL field or response maps it (Q7, option B, 2026-11-10). No log or metric maps it either; any such use needs a separate decision and review.
5. **Order.** Hits are sorted by `fusedValue`, highest first, then by `retrievalRank` ascending. Retrieval ranks are unique, so this is a total order, and the result does not depend on the order of the input list.
6. **Baseline.** When no hit has evidence, `basis = RetrievalOrder` and the order is ascending `retrievalRank`, which is today's order exactly. This covers a cold profile with no skills, a job with no skills, no overlap at all, and an empty list. Hits without evidence keep their relative retrieval order in every case.
7. **Output.** The output is a permutation of the input: no hit is added or dropped. It carries the basis, each hit's evidence and the internal `fusedValue`. The `fusedValue` is not a probability, a hiring-success measure or a display score.
8. **Adoption placement (future, not part of HDQ-07).** On adoption, the ranker would run in `recommendedJobs` and in the normal path of `candidateMatches`, after `liveHits` and before `take(first)`. `retrievalRank` would be the 1-based position in the `liveHits` list. Until then, the evaluation gets the same effect by requesting the service with `first` equal to the bound, ranking the result, and then taking K. That equals ranking the captured top-K list only while every eligible set is at most K. The truncation guard in `SkillEvidenceRankedEvaluation.rankedRun` refuses a possibly truncated ranked run with `PossiblyTruncatedCapture(queryId)`; the rule is under [Pairing](#personalization-adoption-path-hdq-08).
   - **Fallback (Q8, 2026-11-10).** The ranker never blocks a response. If it is disabled, returns an error (for example `TooManyHits` at the bound) or fails internally, the response keeps the retrieval order, which is the previous result. This applies to `recommendedJobs` and recruiter matching only. `semanticJobSearch` and the degraded lexical fallback stay outside the ranker and keep their order.
   - **Visibility (owner answer 'yes' to the Q8 follow-up, 2026-11-10).** A fallback is visible operationally: it is logged and counted as a metric by error kind and by counts only. The log and metric never carry the `Left` contents, a key text, a `RankedHit` or a `RankingOutcome` (the Security note in the [slice 1 checkpoint](#slice-1-checkpoint-2026-11-10)). **Latency (Q3, owner selection 2026-11-10: "Latency tolerance: 2-5 seconds for free tiers").** Two rules apply.

- **(a) Absolute budget, provider-generated capture.** An absolute p95 budget between 2 and 5 seconds applies to captures whose embeddings are provider-generated (`embeddingProvenance == ProviderGenerated` on either report). The value is open: the owner fixes one number before the run, and the recorder suggests one number rather than a range so that the gate is testable. In source (2026-11-10): the assessment requires `absoluteP95Budget` for such a capture (a missing budget returns `InvalidField("assessmentPolicy.absoluteP95Budget")`, a typed failure, not a pass). Any paired baseline or candidate success-latency p95 above the budget raises `AbsoluteLatencyBudgetExceeded`, and that breach resolves to `Defer`. The check covers both the baseline and the candidate p95; a candidate-only check is a one-line change if the owner asks for it. The budget never feeds the relative rule, so free-tier network latency alone cannot `Reject` the ranker.
- **(b) Relative rule, ranker's own added time.** The ranker's added time is measured per query, not estimated: the ranker call is timed with an injectable `RankerTimer` (`RankerTimer.live`, which reads `System.nanoTime`, is the default; tests pass `RankerTimer.fixed`; the ranker has no production caller), and that measured time is added to the baseline latency of the same query. The added time is judged against the same-capture baseline: a candidate p95 above the baseline p95 plus `latencyNoiseAllowanceMillis` raises `LatencyRegression`, which rejects. The allowance is a required policy field with no default, and its value is open for the owner. An allowance of 0 reproduces the strict `>`. Recorder's reason: the ranker is an in-memory function over the bounded hit list (at most 100 hits, see Bounds), so its added time is expected to be milliseconds or less (an estimate, not measured). The allowance exists to absorb measurement noise. A negative, NaN or infinite allowance is an `InvalidField("assessmentPolicy")` error.

The ranker report shares its retrieval with the baseline. The ranked run's latency is the baseline latency plus the measured ranker time (the `RankerTimer` seam): for each query, the ranked latency is that query's baseline latency plus the ranker time measured for it, and the ranked p95 is taken over those values. Independent captures would not help: on one query per group, noise would decide the outcome.

Recorder's consequence: with an allowance of 0 the strict rule rejects any measured added time. With an allowance, the ranker passes this rule only when its measured added time stays within it. The owner's value decides how much added time is tolerated. Thresholds other than latency are unchanged.

#### Statistical limits

What the assessment can conclude:

- Whether a privacy or eligibility violation was observed on these fixtures.
- Whether any supported query failed.
- Whether provider requests changed.
- The ranker's ordering effect on 3 labelled held-out queries.
- Whether a free-tier real-embedding run is operationally feasible.

What it cannot conclude:

- **Statistical significance.** Each selected held-out group holds one query, so a group "mean" is a single value.
- **Recall@7.** No eligible set is larger than 5, so when retrieval returns every eligible entity, Recall@7 is the same for any ordering. Only NDCG@7 can move.
- **Independence from the rubric.** The rubric labels by intended role and required skills, and skill evidence measures required-skill coverage. Part of any NDCG gain is therefore expected by construction.
- **Generalization, subgroup or fairness effects, user benefit, and cloud latency.**

Limit on this corpus (recorder's statement, 2026-11-10): a `Recommend` rests on 3 labelled held-out queries and cannot by itself establish a general ranking improvement. The owner's Q1 answer allows adoption on the local run with the other gates in place, so the adoption record must state this limit.

**Enlarged corpus (Q5 answered 2026-11-10: run on the current 12-query corpus first; no enlargement before the first run).** The following is deferred and not authorized. It would add:

- more held-out queries per use case and filter group;
- eligible sets larger than K;
- recommendation queries for several candidate profiles;
- adversarial cases where skill overlap and intended role disagree, and skill-stuffed profiles.

It needs a new packet and a new human review against the new digest, plus more provider requests. The HSE ceilings (10,000 entities, 100 queries) still apply. No size is proposed as sufficient.

  - (1) Keep the ranker value unexposed, and let list order carry the ranking. Selected by Q7 (option B, 2026-11-10).
  - (2) Add a new field. Rejected by Q2.
  - (3) Carry the ranker value in `score`, following the rerank precedent. Not chosen: it exposes a ranker-derived number through a public field, the tension with Q2 that was raised on 2026-11-10.

| Risk, through list order only (Q7 option B) | Why it matters |
|---|---|
| Read as a probability of hiring success, or as an automated decision | Search is advisory. A top position invites reading the order as a decision, which conflicts with the non-goals. No number is shown, so the risk comes through order only. |
| A recruiter-side ranking of candidates | It may bring the employment-screening rules of the owner's jurisdictions into play, whether shown as a number or as order. The owner or legal counsel must check this; this record asserts no law. |
| Probing hidden attributes | A caller can vary queries and observe order changes to infer values that the ranker or retrieval uses. Order-only output leaks less than a number, but not nothing. |
| Non-comparability of `score` | `score` stays the retrieval, fusion or rerank score, which differs across queries, retrieval modes, models and embedding versions. Clients must not compare it across lists. |
| `score` read as a monotone rank | For ranked results `score` need not decrease down the list, so a client that sorts or thresholds by `score` undoes the ranking. The API reference must say so at adoption. |
| Gaming by skill stuffing | Order changes show a caller which listed skills move a hit up. Coverage limits the job side, but not the candidate side. |
| Contract lock-in and cursor or tie semantics | Under the single-active-shape policy, list order for ranked results becomes a contract that clients page, cache or display by. A later change to the ranker or its tie rule changes that contract. |
| Explanation requirement | A shown order must be explained. The only explanation allowed here is deterministic evidence (`matchedSkills`, and the planned `missingSkills`), not a model rationale. |

**Consequences of Q7, option B (recorder's analysis; owner selection 2026-11-10):**

- `score` keeps its meaning on adoption: the retrieval, fusion or rerank score. The order of `recommendedJobs` and recruiter matching results changes on adoption, which is a behavior change for the list. The [API reference](../api.md) must document, at adoption, that list order is authoritative for ranked results and that `score` need not decrease down the list, and the change goes through [schema evolution](../schema-evolution.md) review.
- No ranker-derived number is exposed, so the ranker value is not comparable across responses. `score` remains a retrieval, fusion or rerank score and is not comparable across queries or modes (an existing condition). A client that sorts a ranked list by `score` replaces the ranked order with the retrieval order.
- A fallback response (Q8) and a ranked response carry `score` with the same meaning; only the order differs. A client cannot observe the fallback: no field or flag reports it (fallback visibility, see [adoption placement](#ranker-contract)).

**Mitigations (recorded with Q2 and Q7; the owner or a legal check may revise them):**

- Ordering is documented as authoritative, in the API reference and the SDL description, with `score` described as a retrieval score that need not decrease down the list. Neither is described as a probability, a hiring-success measure or an automated decision.
- No new field. The public shape stays as it is.
- The ranker's order is a deterministic function of the caller-visible skill coverage and the retrieval rank. The HDQ-07.8 counterfactual requires that residence, availability, consent and name do not change it.
- The value is not model-derived and generates no rationale. Explanation remains `matchedSkills` and the planned `missingSkills`.

**Residual risks the mitigations do not remove:** clients may still read the list order as a probability or a decision; skill stuffing on the candidate side still raises rank (coverage limits only the job side); and a caller can infer relative coverage by varying listed skills and watching the order. Each of these needs the adoption review to accept it or to change the design.

**Revisit trigger:** the owner or a legal check requires a different exposure, or a concrete client need arrives with an explanation design.
