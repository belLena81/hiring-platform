## Source context and decisions

- Verified implementation (read 2026-11-06): `docker/observability/alerts.yaml` defines `HiringApiHighErrorRate`, `HiringBacklogOldestPendingTooOld` (age above 300 s for 2 m, ticket), `HiringBacklogUnobserved` (sample age above 60 s or absent, for 2 m, ticket), `HiringApiSlowRequests`, `HiringKafkaConsumerLagHigh`, `HiringKafkaPublisherSendFailureRatioHigh`, `HiringKafkaProducerFenced`, `HiringKafkaRebalanceRateHigh`. `docker/observability/prometheus.yaml` has `rule_files` and no `alerting` section. `compose.observability.yaml` has no Alertmanager. Evaluation interval is 5 s. The containerised API runs with `KAFKA_ENABLED=false` (`compose.yaml`).
- Verified facts about earlier evidence: `docs/specs/hiring-observability-resilience.md` records that `promtool check rules` was not run (no local binary; the project hook blocks `docker exec` and `docker run`), and the Mongo-stop test that made `HiringBacklogUnobserved` fire. The prior reading found no record of `HiringBacklogOldestPendingTooOld` firing from a stalled worker.
- Constraints that shape the design: the Bash sandbox and `.claude/settings.json` deny `docker run` and `docker exec`, and allow only user-run scripts outside the sandbox (the `run-acceptance.sh` pattern). Edits to `compose*.yaml`, `scripts/` and `docker/` are workflow-file edits that need human approval.
- Decisions:
  - D1. `promtool` comes from the already pinned `prom/prometheus` image, run as a compose service in a profile, with the entrypoint `promtool`, a read-only mount of the rules and tests, no network and the same hardening as the other services. No new image for the tests.
  - D2. Alertmanager is a new local-only service from the official `prom/alertmanager` image, pinned by digest like every other image, bound to 127.0.0.1, with `cap_drop: [ALL]`, `no-new-privileges`, `read_only` and a memory limit. It is a new dependency, so Security review is required.
  - D3. Two named local receivers: `local-page` for `severity="page"` and `local-ticket` for `severity="ticket"`. They are labels for a local sink, not an escalation design. `send_resolved: true` on both. Real routing stays a deployment choice (see the observability specification).
  - D4. The sink is chosen by the implementer from: (a) a log-only webhook receiver built from an image the stack already pins, (b) Alertmanager's own delivery counters and its `/api/v2/alerts` API if no pinned image can receive a webhook. The choice and its reason are recorded. No external endpoint, no credential.
  - D5. The drills are user-run scripts outside the sandbox, like `scripts/run-acceptance.sh`. The rule tests run through a separate script and are not added to `scripts/check-local.sh` in this slice: they need Docker, and a skipped Docker step must not read as a pass. This is a recorded limitation.
  - D6. No rule changes unless a test proves a defect. A defect found goes back through this spec as a recorded finding.
  - D7 (2026-11-06, from finding F1). The payload guarantee is "no hiring content, identifiers or credentials", enforced by an explicit allowlist of ten label names: `alertname`, `severity`, `hiring_capability`, `job`, `instance`, `exported_job`, `service_name`, `telemetry_sdk_language`, `telemetry_sdk_name`, `telemetry_sdk_version`. The last seven are added by our own Prometheus scrape and the OpenTelemetry resource, not by hiring data. Values are checked where the set is closed: `hiring_capability` in {`operational_event_outbox`, `embedding_work`, `drill`}, `service_name` = `hiring-api`, `severity` in {`page`, `ticket`}. Any other label name is a FAIL. Annotations are `summary` only. Labels are not dropped with relabeling in this slice. Reason: a real alert carries the scrape and resource labels, so a three-name set would fail on correct behavior; an allowlist still catches a new label that could carry content. Coverage: the check runs on the synthetic alerts of the delivery drill and on each real alert the backlog drill inspects after it fires. None of the four Kafka rules is covered yet. Of them, only `HiringKafkaProducerFenced` has been observed firing under Kafka traffic (the KFH-04.9 operator drill, 2026-11-08, git-ignored evidence); the consumer-lag, send-failure-ratio and rebalance-rate rules have not been observed firing. The age drill takes about 9 minutes because the age rule needs more than 300 s plus its 2 m `for`; the threshold is not shortened for the drill, because a shortened rule would not prove the real one.

## Behavior and contracts

- Rules and tests: every rule in `alerts.yaml` has at least one `promtool test rules` case that fires and one that stays silent, with explicit `eval_time` values. `promtool check rules` passes. Tests live next to the rules in `docker/observability/`.
- Delivery: Prometheus gets an `alerting` section that points at the local Alertmanager. Alertmanager groups by `alertname` and `hiring_capability`, routes by `severity`, and delivers to the two local receivers with resolved notifications.
- No-data policy is part of the contract and is tested: an absent backlog series must fire `HiringBacklogUnobserved` and must not fire or clear `HiringBacklogOldestPendingTooOld`.
- Safety: payload labels are limited to the allowlist of decision D7 (the observability specification's cardinality and privacy rules still apply). No hiring content, identifiers or credentials. Alertmanager's API and the sink are reachable from the workstation's loopback or the compose network; the sink has no authentication (Security N1, recorded in the local observability limitations).
- Drills never change application data beyond the rows of the one job they create, and delete only that job's pending rows, selected by identity and time and deleted by `_id`. The guarantee and its single assumption are stated under OAV-03. A drill ends with the backlog empty and any stopped service restarted; the seeded job and accounts stay, so the stack is not returned exactly to its starting state, and the seed refreshes `.local/data/perf-seed.env`.

## Domain language and examples

- Context, aggregate and invariant touched: operational observability; no hiring aggregate. The invariant is "unknown is not healthy": missing data is never rendered as zero or as a recovery.
- Glossary terms used: backlog age, unobserved, alert rule, alert receiver, drill release scope, alert label allowlist. The glossary entries are in [domain language](../domain-language.md).

## Performance and cost

- Cost: $0, local containers only. One extra container (Alertmanager, about 64 MB limit) and an optional sink. No paid provider.
- Workload: no throughput claim. The drills are functional. They run on one workstation, at the local evaluation interval of 5 s, and prove behavior at that setting only, not delivery latency in a deployed system.
- Simpler alternative considered: verify only with `promtool test rules` and skip Alertmanager. It would leave the page and ticket labels meaning nothing and would not show a delivery failure, so it is not enough for the stated outcome.
