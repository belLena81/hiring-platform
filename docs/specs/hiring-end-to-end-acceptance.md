# Hiring end-to-end acceptance run

## Identity and scope

- Task: one scripted, repeatable run that exercises UC01 to UC13 on a real local stack and records an observed result per use case. It is condition 2 of the MVP (local) definition in [development milestones](../development-milestones.md#current-refactoring-and-path-to-mvp-checked-2026-10-29).
- Status: **draft; slices 2 and 4 implemented 2026-11-02 (Tier B suite, embedding stub, `scripts/run-acceptance.sh`) but no complete passing run yet (Tier B not run: agents cannot; Tier A has two intermittent failures, F14 and F15); slice 1 (Tier A) implemented and run 2026-10-29; findings F1 to F4 fixed and verified by the same suites, one intermittent CONFLICT open (F2 remainder), F5 to F8 untouched.** Slice 3 (analytics step) implemented and run 2026-10-29/30 on the in-flux analytics tree: HEA-11.2, 12.1, 12.2, 13.1, 13.2 PASS after the owner decisions on F9 to F11 (hired-cohort dataset), evidence provisional. Atlas-dependent Tier B criteria have not run. Independent reviews of the fixes: Code Reviewer, Security Engineer and final QA PASS with follow-ups (see Checkpoint).
- Coordinator: Product Manager. Scala Developer writes the suite and the pipeline script. Data Engineer reviews the seed data and the Atlas Local index setup. Big Data Engineer owns the analytics step. Independent Code Reviewer, Security Engineer (the role matrix HEA-14 and the secrets handling) and QA review the final state.
- User outcome: a single named run answers "does the product do what the 13 use cases promise, end to end?" with a log a reviewer can read, instead of many focused suites that each prove one slice.
- Actors: Candidate, Recruiter, singleton Admin, and the system (events, analytics).
- Non-goals: performance or SLO claims, load, deployed or cloud evidence, real Voyage or calendar providers, Atlas cloud, human relevance judgement, the guided discovery features of Phase 11A, Kafka-over-TLS from a container, frontend. The run proves behavior on a bounded synthetic dataset on one machine.
- Dependencies: the closed analytics refactoring (shapes must be final before the run is recorded as evidence); Atlas Local for UC02, UC06 and UC10.

## Source context and decisions

Source facts read on 2026-10-29 at branch `refactor`, HEAD `321c2eb`:

| Boundary | Fact |
|---|---|
| Existing coverage | Many focused suites (`src/it`, `analytics/src/it`) and `MainProcessSpec`, which starts the real `Main` for startup and failure cases only. No test or script drives all 13 use cases through the real HTTP API and then the analytics output. `scripts/generate-local-traffic.sh` sends only read-only health and invalid queries. |
| Test stack | `compose.test.yaml` (owned by `scripts/run-local-tests.sh`) provides Mongo 8 (community) and the SASL Kafka broker. It has no Atlas Search or Vector Search. |
| Atlas Local | `compose.atlas-local.yaml` is opt-in. The harness guard denies agents `docker compose` for every file except `compose.test.yaml`, and protects the compose files from edits. So an agent cannot start Atlas Local, the full `compose.yaml`, or the analytics profile. The user runs those. |
| Embeddings | The only provider is Voyage (`voyage-4-lite`, 1024 dimensions). Its endpoint is configurable (`application.conf` `voyage.endpoint`). Test fakes exist only inside unit suites. |
| Analytics | The batch reads one explicit Kafka partition and offset range per run, writes Delta locally and publishes the report. The report period is at most 30 days. Distributions are suppressed below K=10 distinct candidate subjects. The containerised API runs with Kafka publication disabled (D6 of the [container runtime](hiring-container-runtime.md)), so UC11 to UC13 run with the API on the host (`sbt run`), not in the API container. |
| Roles | Candidate, Recruiter, singleton Admin seeded from explicit configuration (README "Trusted Admin initialization"). Every mutation needs an `idempotencyKey`. |

Decisions (proposed; revisable by the user):

- D1 Two tiers.
  - **Tier A, agent-runnable:** an integration suite against the real `Main` over HTTP on the test stack. It covers every use case that does not need Atlas search (UC01, UC03, UC04, UC05, UC07 to UC09, UC11 publication) and the role matrix.
  - **Tier B, user-run:** a script that starts Atlas Local, Kafka and the API on the host, runs the same story plus UC02, UC06, UC10, then the analytics batch and the Admin report (UC11 consumption, UC12, UC13). Agents write it; the user runs it and pastes the log path into this document.
- D2 Embeddings in the run come from a small local HTTP stub that implements the Voyage endpoint contract and returns deterministic 1024-dimension vectors from hashed words, so similar texts are close. No paid call, no API key, no flakiness. One separate opt-in smoke with a real Voyage key is optional and is not part of the acceptance claim.
- D3 One story, one dataset, fixed seed. A scripted narrative with fixed names and IDs (below). Re-running on a clean stack must give the same counts.
- D4 The run asserts business outcomes, not implementation details: GraphQL results, history, event counts and report numbers.
- D5 The dataset has 12 candidates so the K=10 suppression is both lifted for the main report and checked as suppressed for a smaller slice.
- D7 Analytics step design (slice 3, 2026-10-29). Agents may run only `scripts/run-local-tests.sh`, and the analytics build (Scala 3.7.4, Spark) and the root build (Scala 3.9) share no classpath, so no single suite can both run the real API and the real batch. A root-build suite cannot call the batch (no nested sbt, no Spark on the root classpath); an analytics-build suite cannot start the API. Chosen: three agent-run wrapper commands that meet in files under the ignored `.local/data/hiring-story-analytics/`, with no protected-file edit and no user step:
  1. `scripts/run-local-tests.sh test '*HiringStoryAcceptanceIntegrationSpec'` runs the story on the real `Main`; its last test (HEA-11.3) exports the committed topic records (key and exact value, topic order) to `story-events.jsonl`.
  2. `scripts/run-local-tests.sh analytics '*HiringStoryAnalyticsReportIntegrationSpec'` (analytics build, package `com.example.hiring.analytics.hiringstory`) republishes those records unchanged, one transaction each, to a fresh isolated topic, runs the production one-shot batch (`AppModule.batch`, the same program as `HiringAnalyticsBatchMain`) twice over the same offset range, reads Silver stage times, asserts HEA-11.2/12/13, and exports the two report documents the batch published (`report-documents.jsonl`).
  3. `scripts/run-local-tests.sh test '*HiringStoryAnalyticsAdminReportIntegrationSpec'` (root build) starts the real `Main` on an owned database, stores those documents unchanged and reads them through the real Admin `analyticsReport` (HEA-12.2 and the API-level HEA-12.1/13.1). Nothing recomputes the report.
  The chain runs for two datasets: the 12-candidate story (`story-events.jsonl`, `report-documents.jsonl`) and the hired cohort (`cohort-events.jsonl`, `cohort-report-documents.jsonl`; commands `... test '*HiringCohortStoryIntegrationSpec'`, `... analytics '*HiringCohortAnalyticsReportIntegrationSpec'`, `... test '*HiringCohortAnalyticsAdminReportIntegrationSpec'`). Cohort run 2026-10-30: 60 candidates and 213 mutations in 7 s on the API (0 CONFLICT retries in the passing run; an earlier run hit one CONFLICT on `moveApplicationToInterview`, F2 remainder, so the cohort retries CONFLICT with the same idempotency key as `docs/api.md` advises), 161 events published; the analytics suites take about 310 s per dataset unloaded and about 620 s under heavy machine load (two Spark batch runs each; load dependent).
  Chain mode (QA follow-up 2026-10-30, fixes a full-run regression): the export deletes downstream reports, so an unordered full `scripts/run-local-tests.sh test` that ran an export before the Admin suites, with no analytics step between, failed them. The chain now runs only when it is started explicitly by the marker file `.local/data/hiring-story-analytics/chain-started` (create it with mode 0600 in a 0700 directory before step 1; remove it afterwards). Without the marker the export, the analytics suites and the Admin suites are skipped (`assume`, the convention of the Atlas-gated suites), nothing in the hand-off directory is touched, and the skip is reported as unverified, never as a pass. With the marker, a missing, stale or mismatched hand-off FAILS. A marker file was chosen over an environment variable or system property because the wrapper passes neither through to the test JVMs and the agent harness forbids setting `HIRING_*` variables; a marker is order independent, visible and works for both builds. Risk: a forgotten marker keeps later full runs in chain mode, where a full run (export, then Admin suites without analytics) fails by design: remove the marker after the chain.
  Hand-off binding (review follow-up 2026-10-30): the story export deletes its dataset's events and downstream report files before it writes, writes the events file with owner-only permissions (directory 0700, files 0600), and the analytics step writes the SHA-256 of the events file it consumed as the first line of its report file. The Admin suites recompute that digest from the events file on disk at read time and FAIL (not skip) when, in a started chain, the events file, the report file or the matching digest is missing. The digest is taken from the exact bytes the analytics step reads when it starts, not at export time. A skipped, stale or out-of-order step is therefore never a pass; only the missing Atlas-dependent criteria are BLOCKED. The hand-off files hold published events with pseudonymous subject UUIDs, are disposable and are rewritten by the next export.
  Limits of this design: the batch reads a republished copy of the story's records (same payloads and keys, new offsets), not the original topic, because the root suite's topic namespace is deleted when it ends; the three commands must run in that order; the files are the only coupling. A user-run step is not needed. Tier B (Atlas Local) stays user-run.
- Open questions: Q1 Atlas Local as the only Mongo in Tier B, assuming it provides the replica set that transactions need (verify in the first slice). Q2 whether Tier A should also run against Atlas Local when the user starts it. Q3 report timing: batch is one-shot, so the run reads the report after the batch exits (no freshness claim).

## Behavior and contracts

### The story (seed and order)

All names are fictional. Operations are the checked GraphQL contract (`src/test/resources/graphql/hiring.graphql`) and use the existing operation fixtures where they exist.

1. Start: Admin is seeded from configuration. Admin signs in.
2. Accounts: Recruiters Rita (R1) and Ravi (R2); candidates C01 to C12, among them Ana (C01), Bo (C02) and Cy (C03).
3. Jobs (UC07): R1 creates and publishes J1 "Scala Backend, Berlin, skills Scala and Kafka", J2 "Kotlin Services, Berlin", J3 "Java Developer, Munich"; R2 creates and publishes J4 "Data Engineer, Berlin". R1 updates J3, then closes J3. R1 creates J5 and leaves it unpublished.
4. Embeddings: the embedding worker processes jobs and candidate profiles. Admin `embeddingCoverage` shows no missing or stale entries before search is exercised.
5. Discovery: UC01, UC02, UC03, UC06.
6. Applications: C01 to C12 apply to J1 (UC04); C01 also to J2. Duplicate and closed-job attempts are made. Candidates read their own applications (UC05).
7. Recruiter review: R1 lists J1 applications (UC08) and moves them through the lifecycle (UC09): C01 Created, Accepted, Interview, Hired; C02 Created, Rejected with feedback; C03 Created, Accepted, Interview, Rejected; C04 Created, Declined by the candidate with a reason; C05 Created, Accepted; C06 to C12 stay Created.
8. Candidate matching (UC10): R1 asks for matches for J1.
9. Events and analytics: all above published (UC11); the batch consumes the range; Admin reads the report (UC12, UC13).

|---|---|---|

### Tier B search story and expected outcomes (slice 2; written 2026-11-02 before any Tier B run)

Tier B drives the real `Main` over HTTP like Tier A, but on Atlas Local (the only deployment with `$search`, `$vectorSearch` and `$rankFusion`) and with `vector-search.enabled = true`. It uses a smaller story than the 12-candidate one, because the search ranking, not the volume, is the subject. Data are the fictional texts in `test-support/.../HiringSearchStoryData.scala` (single source for the suite and the unit test that fixes the oracle below).

Embedding provider (found in `VoyageEmbeddingService`, `vector-search.voyage.*`, `MongoHiringRuntime`): the application posts `POST <endpoint>` with a bearer token, JSON `input`, `model`, `input_type`, `output_dimension`, and reads `data[0].embedding` and `model`. A provider outage (refused connection, timeout, 429, 5xx) becomes `EmbeddingError.ProviderUnavailable`, which the search service turns into the keyword fallback (`degradedReason PROVIDER_UNAVAILABLE`). The configuration reader accepts only `https://` endpoints, so the stub speaks TLS with a throw-away self-signed certificate (generated with the JDK `keytool` into an owner-only directory) and the child JVM trusts it through `-Djavax.net.ssl.trustStore`. The stub (`DeterministicEmbeddingStub`, test-support, JDK `HttpsServer`, no new dependency) returns a unit vector of 1024 hashed lowercase words (term frequency, FNV-1a), so texts sharing words are close. The application is pointed at it by configuration only: `vector-search.voyage.endpoint` and a placeholder `vector-search.voyage.api-key`. No production code was changed for the stub. The stub counts served calls and can be stopped (connection refused) to simulate an outage.

Data. Recruiter Rita (R1) owns J1 to J3 and J5, Ravi (R2) owns J4. J1 "Scala Backend" (Berlin; Scala, Kafka), J2 "Kotlin Services" (Berlin; Kotlin, Spring), J3 "Java Developer" (Munich; Java; created, published, then closed), J4 "Data Engineer" (Berlin; Spark, SQL), J5 "Backend Prototype" (Draft, never published). J3 and J5 deliberately contain the query words "JVM" and "backend", so a visibility leak would put them at the top. Candidates: Ana (Scala, Kafka, "Five years of backend work", Berlin, opted in), Bo (Kotlin, Munich, opted in), Cy (Java, Karlsruhe, opted in), Dee (Scala, "Four years of Scala services", Hamburg, NOT opted in).

Oracle (derived from the texts, checked by `DeterministicEmbeddingStubSpec`, not from a Tier B run): for the query "functional JVM backend" the cosine order puts J1 above J2 and J4, and the hidden J3 and J5 above J2 and J4; Ana's profile is closest to J1 among all five jobs; for J1 the candidate order starts Ana then Dee.

Unknowns, stated so a failure is read correctly: (a) whether the first read after indexing shows every document (the suite bounds this wait, 120 s); (b) whether Atlas Local returns every opted-in and opted-out candidate for `first: 10` on four documents (vector search is approximate; four documents is far below the candidate limit); (c) whether `updateMyProfile` keeps the old embedding or clears it (both give a typed refusal); (d) whether the lexical side and the `$rankFusion`/application RRF fusion also rank J1 first: the oracle fixes the vector order only, and J1 alone contains "backend" and "JVM" among the open jobs, so J1 first is expected from both branches, but the fused order of J2 and J4 behind it is not asserted. - F14 diagnosis and fix (2026-11-02, Data Engineer). Evidence: with a test-harness sampler of `event_outbox` (`OutboxDiagnostics`, enabled by the ignored marker file `.local/data/outbox-diagnostics` or `HIRING_OUTBOX_DIAGNOSTICS`; silent otherwise), a failing HEA-11.1 run showed 3 rows `Retryable`, `attempts` 0, no `lastError`, no lease, `InFlight=0`, `Failed=0`: `JOB_CREATED`, `JOB_UPDATED`, `JOB_CLOSED` of one job by one recruiter, unchanged from t+10 s to the timeout while 41 other events were `Published`. So Kafka, wtimeout, lease renewal and subject-lease conflicts are not the cause: the rows were never claimed. Root cause (commit `462aac9`, found by reading the claim): the persisted claim cursor passed any examined row, but the page after the cursor was empty only when nothing was blocked. `JOB_CREATED` was skipped in a batch because it shares the recruiter's subject with an event taken earlier in the same batch (a subject has one in-flight event); the cursor moved past it; its followers `JOB_UPDATED` and `JOB_CLOSED` are blocked by it (DDR-06.1), so every later page after the cursor held those blocked rows, was non-empty, and the scan never wrapped to the start. Deadlock until the cursor row set changes (never, once no new events arrive). Before `462aac9` the page after the cursor was empty, the claim wrapped and found the skipped row. It is intermittent because it needs a same-subject event ahead of the first event of an aggregate within one claim batch. Fix (minimal, no change to DDR-06.1 order or DDR-01 leases): when the scan after the cursor reaches the end of the due rows and claims nothing, the claim reads once from the start (`MongoOperationalEventRepositories.scala`, `claimPage`). A first attempt that pinned the cursor before every unclaimed row broke the reviewed hot-subject fairness test (`MongoProducerRegistrationsIntegrationSpec` "fair claim scan checkpoints past more than one page of busy subjects across claims") and was dropped. Regression test `OutboxBatchClaimIntegrationSpec` "DDR-06.1 an event skipped for a shared subject is reached again although every follower of its aggregate is blocked" fails on the code of `462aac9` (second claim empty) and passes with the fix.
