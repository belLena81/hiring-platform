# Hiring Analytics Lakehouse

## Identity and scope

- Status: in progress
- User outcome: Admin can query bounded, aggregate hiring analytics produced from local Kafka events without coupling request handling to Spark.
- Authorized scope: a local Scala 3.7.4 Spark/Delta analytics module using Spark/Delta's Scala 2.13 artifacts, Compose integration, Bronze/Silver/Gold datasets, an Admin GraphQL read model, account-deletion erasure requests, tests, and canonical documentation.
- Non-goals: cloud deployment, Structured Streaming, a dashboard, current-state enrichment, changes to the operational event envelope, or a 365-day historical analytics store.
- Delivery decisions: complete all open HAL-01–HAL-13 criteria in dependency-ordered local slices. `deleteMyAccount` commits the durable tombstone/request/generation hide and immediately returns a random bearer receipt with `PENDING`; `accountDeletionStatus(receiptId)` reports only pending/completed/not-found, so the caller can observe completion after Kafka and Delta retention horizons without holding an HTTP request open. Receipt lookup is independent of the deleted account's authentication session. The wait never runs inside the mutation receipt transaction. The worker is owned by the opt-in analytics Compose profile; deletion preflights worker health before mutation. A completed mutation receipt replay returns the same durable status receipt.
- Privacy decision: an unattributable malformed source record is quarantined using Kafka coordinates, a payload hash, and a sanitized failure category; its raw value is never persisted in Delta. Existing attributable raw records remain subject to scoped purge, with whole affected raw/quarantine scope deletion when attribution cannot be verified.
- Local security decision: use authenticated KRaft Kafka ACLs with a versioned current publisher principal (`hiring_publisher_v2`) allowed to write the operational topic and scoped transactional IDs, a distinct analytics reader, and a distinct transactional-ID fencer. The current Compose PLAIN SASL maps omit the retired pre-transactional `publisher` principal; ACL initialization also force-removes stale topic, cluster-idempotence, and transaction-ID rights for it. Applying this configuration to a running broker requires stopping old publisher processes and restarting/recreating the broker, after preserving and verifying its KRaft data. A new broker started with the current config should reject the former publisher credentials during authentication. Credentials belong in the ignored root `.env` (`KAFKA_BROKER_PASSWORD`, `KAFKA_PUBLISHER_V2_PASSWORD`, `KAFKA_READER_PASSWORD`, `KAFKA_FENCER_PASSWORD`); generate URL-safe hex values (for example, `openssl rand -hex 32`) and never put local values in tracked files. Root app settings use `KAFKA_ENABLED=true`, `KAFKA_PUBLISHER_USERNAME=hiring_publisher_v2`, `KAFKA_PUBLISHER_V2_PASSWORD`, `KAFKA_READER_USERNAME=analytics_reader`, and `KAFKA_READER_PASSWORD`; the erasure-worker Compose service receives reader and fencer credentials from the same ignored env file. The local Compose broker now declares persistent KRaft storage. On 2026-09-25 the regular broker was stopped, its complete `/tmp/kafka-logs` tree was backed up and copied byte-for-byte to `.local/data/kafka`, and it restarted with the original cluster ID and topic offsets.
- Security objective: remove delayed outbox replay as a source of deleted-subject analytics data. The permanent scrubbed `Deleted` account record is the replay-deny source; HMAC deletion markers cover bounded Kafka and analytical retention and expire 31 days after erasure completion. Security review remains pending until this behavior is implemented and independently verified.
- Stale-writer decision (2026-09-24): every publisher process uses a unique Kafka transactional ID; Mongo subject fences retain the IDs associated with claims, and the receipt-owned deletion transaction copies those IDs into the durable erasure request. The erasure worker must confirm Kafka producer fencing for every recorded ID before it captures the read-retention barrier or purges outbox rows. IDs are retained until fencing succeeds so claim registration and deletion cannot race past one another. A fence failure leaves the receipt Pending. This only protects transactional publishers; deployment cutover must stop and revoke old nontransactional publisher binaries/credentials. Spark's Kafka source uses `read_committed` so aborted records cannot enter Delta.
- Release status: local development evidence is in scope. Do not describe K=10 suppression as a formal anonymity guarantee.

## Source facts and decisions

- `hiring.operational-events` is the current unversioned seven-field source envelope. Spark consumes that exact shape with declarative parsing and does not reimplement the Scala Circe decoder.
- Required `eventId` and `aggregateId` values must be nonblank after trimming. Null-valued Kafka tombstones are malformed and use topic/partition/offset coordinates as a stable quarantine identity across replayed ranges.
- GraphQL mutations run through `MutationReceiptRepository`, which supplies a receipt-owned `MutationWriteContext`; the current account deletion joins it to tombstone the account, close open recruiter jobs, and append `JOB_CLOSED` outbox events atomically.
- `deleteMyAccount` requires a non-noop context for the analytics-aware path. A new erasure-request port joins the same session before account deletion; direct repository deletion remains a non-analytics repository operation.
- Deleted account tombstones retain the account UUID and `Deleted` status after personal profile/authentication fields are scrubbed. Outbox publication must check all persisted subject references against this durable deny source on every attempt.
- Outbox records currently persist actor ID and opaque payload but no indexed subject-reference list. Add actor and every candidate ID as internal `subjectIds`; this does not change the seven-field Kafka envelope. A versioned migration must backfill and validate every retained row before publisher startup. Any undecodable or incomplete row blocks startup; it must be manually resolved or terminally quarantined without publication, never guessed.
- Outbox sends and account deletion share a per-subject publication fence. A publisher obtains a durable, expiring lease for every subject in a record, rechecks tombstones while holding that lease, and retains it until Kafka send completion/ack or definitive failure. Deletion first installs its tombstone and erasure request transactionally, then waits for all earlier subject leases to finish/expire and drains the broker's committed offsets before erasure can complete. Publishers cannot acquire a new lease after the tombstone exists. Kafka ACLs restrict writes to this publisher identity. An erasure remains active until the drain point is beyond all pre-delete sends; a crash recovers via lease expiry and repeated drain.
- Analytics report state and generation are stored independently of the expiring report payload. Account deletion atomically increments the durable generation and hides the current snapshot. Each batch captures the generation before processing; publication atomically compares the expected generation and requires a strictly newer run revision before replacing the snapshot. A missing snapshot never resets the generation. A failed comparison leaves the newer hidden/visible state untouched.
- Bronze and quarantine raw data files retain records for seven days. Delta transaction logs can retain legacy raw-value column statistics for up to 30 days; new Bronze/quarantine tables disable column statistics, and erasure completion waits through log retention, checkpoints the cleaned snapshot, and verifies pre-purge log paths are absent. Silver, Gold, and published Mongo snapshots retain 30 days. Gold is rebuilt only from retained Silver data.
- Silver pseudonymizes only allowed identifier fields with a dedicated HMAC secret. Gold exposes only groups with at least ten contributing subjects/events.
- The runnable batch reads at most 100,000 `Pending` or `Processing` requests from `analytics_erasure_requests`, validates UUID subject IDs, and HMAC-tokenizes them before run mutation. A larger backlog fails before Delta mutation. With active markers, it expires Bronze, quarantine, and Silver, purges matching identified rows (and unattributed raw/quarantine rows), rebuilds Gold, and requests retention-safe vacuum. Raw table writes disable indexed column statistics. The opt-in worker waits for the Kafka horizon, Delta's seven-day data-file safety horizon, and the 30-day legacy Delta log retention horizon; it checkpoints cleaned raw tables and verifies captured data and transaction-log paths are absent. Compose Mongo URIs name the `rs0` replica set because the worker's guarded report publication requires Mongo transactions. The batch materializes and validates the deletion-marker snapshot before creating/updating HMAC control metadata or reserving report generation/revision; it then atomically publishes the Mongo snapshot before writing a `PUBLISHED` manifest. A run with active markers instead writes `ERASURE_PENDING` and does not publish. The separate opt-in erasure worker owns publisher drain, outbox purge, retention barriers, Delta reclamation, Gold refresh, and guarded report reveal/completion.

## Metric and publication decisions

- Event-time days use UTC calendar boundaries. Funnel and skill activity use `occurredAt`. GraphQL period bounds select UTC calendar-day buckets inclusively and are limited to 30 calendar days. `asOf` is the completion time of the latest successfully published run; the batch is manually invoked and has no freshness SLO.
- A time-to-hire observation uses the first `APPLICATION_CREATED` time and first subsequent `Hired` status time for an application. Missing creation/hire events, a hire before creation, or conflicting lifecycle facts are excluded and counted only when the remaining published count passes suppression.
- Suppression is evaluated independently for every output cell, using distinct pseudonymized subjects as the contributor count. Funnel values count distinct applications, skill activity counts posting events, and time-to-hire summarizes eligible applications; no subject may contribute more than once to a metric cell's suppression count. Every exposed count, including eligible/excluded counts, must satisfy suppression or be omitted.
- Any malformed or conflicting event in the requested offset range is quarantined and marks the run `QUALITY_BLOCKED`. Valid facts may be retained in Silver for later deterministic rebuilds, but neither Gold nor the Mongo snapshot may advance from a quality-blocked run. Existing published snapshots remain available until a later eligible run succeeds.
- The runner continues to consume the existing seven-field operational event envelope. Unknown event types or aggregate types are quarantined as malformed for this slice; envelope evolution remains a separate compatibility change.
- The batch erasure workflow is resumable and idempotent. Pending and Processing requests remain active markers; after guarded snapshot publication, Complete markers remain active until their 31-day `expiresAt` and Mongo TTL cleanup. The batch source filters expired Complete markers using the injected Cats Effect clock. A later account deletion changes the durable snapshot generation and prevents an older batch from publishing.
- Kafka is immutable within its retention window. Delta Bronze/quarantine rows must carry subject references independently of successful parsing. When an input cannot be attributed, erasure purges the entire affected raw/quarantine range (or the complete raw/quarantine dataset if precise range attribution is unavailable), then verifies no readable Delta snapshot/file can reconstruct it. Erasure cannot complete while affected retained Kafka records can still be replayed; the bounded source retention and publisher drain are part of that proof.

## Run and recovery contract

- A run is identified by an immutable run ID and exact topic/partition/offset ranges. Reusing a run ID with different ranges is rejected. Exact range retries are idempotent; overlapping and concurrent runs against the same lakehouse are serialized or rejected. Manifest states distinguish `STARTED`, `QUALITY_BLOCKED`, `FAILED`, and `PUBLISHED`.
- A run is not marked `PUBLISHED` until all Bronze, Silver, quarantine, Gold, and Mongo snapshot writes have succeeded and reconciliation has passed. The final Mongo snapshot replacement and Delta manifest update cannot share a transaction: if Mongo publication succeeds but the final manifest update fails, the new complete snapshot can be visible while the manifest remains incomplete. Retrying the exact same run republishes idempotently and completes the manifest without duplicate facts; a run is never reported successful until that marker is durable. Earlier failures, including Mongo publication failure, leave the prior snapshot readable. Mongo publication is an atomic replacement of one complete snapshot, and older runs cannot overwrite a newer published `asOf`.
- Reconciliation records requested, read, deduplicated, valid, quarantined, conflicting, suppressed, and published counts per range. Empty reads are distinguished from expired or unavailable offsets; incomplete requested ranges fail rather than silently producing an empty report.
- Kafka retains source records for seven days. If requested offsets have expired and no retained local Bronze copy can satisfy the run, the operator receives a clear unrecoverable-range result and the report is not advanced. Recovery is a new explicit range/run, not implicit offset discovery.
- Retention means expired rows are unavailable to all reads and report rebuilds, and expired data files are eventually physically reclaimed under a documented Delta-safe maintenance procedure. Mongo snapshot expiry remains enforced independently.
- HMAC marker records identify the key version used. The reader accepts active and retiring keys for matching existing rows, while new rows emit only the active primary-key token. Deletion-marker matching derives aliases for every configured key so historical rows remain erasable. HMAC material must contain at least 32 random bytes; generate it with `openssl rand -base64 32`. A non-TTL Delta control registry stores a domain-separated HMAC verifier for every key ID, rejects changed material under an existing ID, and retains retired IDs so an ID cannot be rebound to different key material. The verifier is integrity metadata, not secret material; it must never be logged. A legacy lakehouse without the registry fails closed rather than silently anchoring the current secret; it requires a controlled rebuild/re-key or independently trusted one-time provenance migration. Key retirement remains blocked until every Delta row, report, and marker derived from that key has expired or been safely re-keyed, and external writers are fenced; the current stored-token scan is not sufficient proof of historical Delta-log or cross-process cleanup. Secrets remain outside source control, logs, run manifests, and Compose defaults.

### HMAC key rotation and retirement procedure

1. For a new lakehouse, create a random 32-byte secret and assign a never-before-used key ID. Start the batch and worker with the same primary key configuration; startup creates the initial continuity registry. Never replace the secret while retaining its key ID.
2. To prepare a rotation, create a random secret and never-used ID for the new key. Keep the old key as primary and add the new key as a retiring/match key to every batch and worker. This anchors the new ID without changing newly emitted tokens, and the primary-key compatibility check continues to pass. Keep all processes on this configuration while preparing the cutover.
3. There is no zero-gap automatic re-key path: `subjectToken` is one-way pseudonymized and only raw Bronze/quarantine data remains for seven days, while Silver retains 30 days. To avoid splitting aggregation identities, pause batch ingestion and wait until every old-primary Silver row has expired (up to 30 days after the last such row). Keep the erasure worker running with the old primary during this period so pending deletion work can continue. This pause can lose events older than Kafka's seven-day retention; a no-loss live rotation requires a separately designed and reviewed re-key/rebuild mechanism, which is not implemented.
4. Before switching, verify the batch/worker primary-key compatibility check succeeds with the old key still primary and inspect that no unexpired old-primary Silver row remains. Complete the writer cutover together: stop old binaries and other analytics writers, revoke obsolete credentials, then configure the new key as primary and the old key as retiring/match key on every batch and worker. New rows carry only the new primary token, while erasure markers match both versions. Kafka transactional fencing does not fence nontransactional or external writers.
5. Keep the old key configured until old-key rows have expired or been purged from Bronze, quarantine, and Silver, and retention cleanup is verified. Wait through the relevant windows: seven days for raw data files, 30 days for legacy Delta log/statistics and Silver/report snapshots, and the Kafka retention barrier. Complete normal erasure checkpoint/physical reclamation verification. Check active erasure requests and replay state before removing the old match key.
6. Run an operator-reviewed retirement check across current Delta snapshots, retained historical Delta log/data paths, Mongo report output, active marker/replay state, and every writer deployment. Capture evidence of absent old-key references and completed cleanup. If any surface is inaccessible or its retention horizon has not elapsed, keep the old secret configured and block retirement.
7. Remove the old secret from primary/retiring configuration only after the evidence above is complete. The continuity registry entry remains permanently; reintroducing that key ID is allowed only with the exact original secret. Never delete or rewrite the registry to make a failed continuity check pass. There is no automated emergency rotation for a compromised key; suspend analytics publication and use an independently reviewed purge/rebuild response rather than bypassing the primary compatibility check.

For an existing lakehouse without the continuity registry, ordinary startup must fail closed. Do not seed it from the currently configured secret. Use a controlled rebuild/re-key while the old secret is independently verified, or an independently trusted provenance record and a reviewed one-time migration. If no trusted provenance exists, do not claim that same-ID secret continuity or safe retirement has been established.
- The opt-in local workload is a deterministic 100,000-record synthetic range over one topic partition and a 30-day event-time window, with a fixed seed and a documented mix of lifecycle, job-created, malformed, duplicate, and conflicting records. Record the exact generated counts and the host/JDK/Spark/Delta settings with each run. This is a reproducibility baseline, not a latency or throughput SLO; no cost claim is made for the local-only run.
