## S1 read path: decisions and results (2026-10-19)

Status of the findings: MR-01, MR-02, MR-03, MR-11 and FD-04 are done. GQ-02 (selection-driven field projection from `astFields`) was not part of this change and is done in S5.

Decisions:

- **Embedding stays on the domain `Job` and `User`.** Moving it to a read model touches `EmbeddingPipeline`, `SemanticSearchService`, `SearchEligibility`, both codecs, the validators and about thirty tests, which exceeds one read-path slice. Instead the reads are split by what they return: `users.find` and `jobs.find` (profile or display) never read the vector and report `embedding = None`; `findVersioned` is the single whole-document read and is used only by the embedding pipeline, compare-and-set writes and search ranking. The port documents this. Revisited in S5, which keeps it with a concrete reason (S5 section).
- **Actor projection is `ActorRecord(id, role, accountStatus, adminSingleton)`**, without `name` and `email`: no authorization path reads them, and omitting them keeps personal data out of the per-request read. `AuthenticatedActor.viewer` is now an `ActorRecord`. `ActorAuthorization.resolve` and `readScope` return it, and `HiringReadScope.validated`, `canManage`, `canView` take it (`JobOwner` for the job side). Callers that need the profile use `resolveProfile` (`me`) and search uses `resolveWithEmbedding`/`readScopeWithEmbedding`.
- **`readScope` reuses the request's resolved actor** (`resolve` then `scopeOf`). Search revalidation after a provider or vector call deliberately does not: `currentReadScope` always re-reads (test `MVR-05` keeps that property), because a request-cached actor must not outlive a deleted account.
- **The NotFound versus Forbidden distinction is kept**, so the pre-checks were reduced rather than removed: `jobApplications` still reads `jobs.findOwner` (a projected read of one job, no user read) before the aggregation; `applicationHistory` still reads the application and, for a Recruiter, the job ownership. They are one projected read each instead of full documents, and the actor is read once. The aggregations keep enforcing access independently.
- **`candidateMatches` still reads the full job twice, on purpose.** The second read happens after provider and vector retrieval and revalidates that the owned job is still open and its embedding is current; reading once would drop that concurrency guard. Both reads now go through `findVersioned` explicitly, since `jobs.find` no longer carries the vector.
- **`ApplicationSubmission.create` takes `(candidateId, candidateRole, ...)` instead of a `User`** (one domain edit outside the originally allowed paths), because submission now resolves only an `ActorRecord`.
- Minimal projections decode strictly (exactly the projected fields). Profile, display and list reads reuse the existing full-document decoder, whose unknown-field check is unchanged and still fails closed; no `noUnexpectedFields` set was widened.
- `updateProfile` (both the candidate and the direct path) is one `findOneAndUpdate(ReturnDocument.AFTER)` with the profile projection; a lost guard is `Conflict` as before. `updateEmbedding(id, ...)` reads only `version`.

Accepted risks (Security Engineer residuals):

- **Write authorization trusts the request-cached actor.** Mutations resolve an `AuthenticatedActor` read at the start of the request, so an account deleted mid-request is not seen by the service check. This is bounded by the repository: application writes re-validate the active actor and job ownership inside the write transaction (`MongoApplicationWriteFence`), profile and embedding writes carry an active-account guard in the update filter, and read pipelines re-check the actor (AC-03.3). Search revalidation after long steps always re-reads (AC-03.4).
- **`Forbidden` versus `NotFound` can reveal that an application or job exists.** Pre-existing behavior kept on purpose for the existing error contract; IDs are UUIDs and responses are sanitized. Revisit if enumeration becomes a stated threat.

Not verified, or open:

- No per-request Mongo operation count was captured end to end through GraphQL; AC-02 counts are at the service boundary with counting fakes, and AC-01/AC-03 at the Mongo command boundary. The "bytes per auth read" saving is by projection shape; no byte counts were measured, and the vector width assumption (about 1536 doubles) is unmeasured.
- `me` now costs two small reads (the request's actor projection and the profile read) instead of one whole-user read.
- `MongoRecruiterJobClosure` page reads still use whole job documents; not in scope.

## S2 error model: decisions and results (2026-10-20)

Status of the findings: FD-01, FD-02, FD-06, FD-07 (partly, see below) and FD-08 are done. Worktree `.local/worktrees/consolidation`, uncommitted.

Decisions:

- **FD-01.** `InterviewActionError` and `InterviewActionF` are deleted; interview actions return `UseCaseF` and report an interview rule as `UseCaseError.InterviewRule`. `HiringGraphQLResolverSupport.mutationResult` is the only place that decides data versus top-level error, from the catalog metadata (`exceptional`, `isAuthenticationFailure`); interview actions pass `authorizationRefusalAsData = true` so a role or ownership refusal stays a typed payload and one refused alias does not discard the others. The one-off `Repository(Unavailable)` remap for an exceptional workflow rule (`ProposalTtlOutOfRange`) is dropped: the catalog already classifies it as exceptional `UNAVAILABLE`, so the code seen by a client is unchanged (test `AC-06.7`). The only visible difference is the sanitized top-level message, now `Service unavailable` (the rule's own catalog message) instead of `Repository unavailable`.
- **FD-02.** `UseCaseF.translate` is the single total `RepositoryError => UseCaseError`: `AuthorityRevoked` is `Domain(Forbidden)`, the repository's lone-vector-branch failure `VectorSearchUnavailable` is `Search(VectorSearchUnavailable)`, everything else is `Repository(error)`. `UserAccountService` no longer builds `Repository(error)` by hand. The two catalog branches for `Repository(AuthorityRevoked)` are gone: `isAuthorizationRefusal` tests `Forbidden` only, and `classifyRepository` delegates the two translated cases to `translate`, because the exhaustive match over `RepositoryError` still needs them (the compiler requires the cases; the policy lives once). `RepositoryError.VectorSearchUnavailable` stays as the repository port's signal (the Mongo fusion needs a repository-level failure for a lone vector branch); the use-case layer now has one reading, `SearchError.VectorSearchUnavailable`, and `service/search/SearchFailure` offers the named views `degradation` (provider outage or lone vector failure) and `asSearchFailure` (what a caller sees for a non-degradable failure).
- **FD-02 `searchFailure`.** The requested distinction "Overloaded versus InvalidStoredData degrade differently" is not observable without changing public codes: `MVR-05/MVR-10` (existing contract) require corrupt stored data in an eligibility read to be sanitized as an unavailable search. So `asSearchFailure` keeps that contract (every store fault except `Conflict` becomes `VectorSearchUnavailable`, `Forbidden` is kept) and the distinction that does exist is tested instead: only a lone vector failure degrades to lexical retrieval; `Overloaded`, `Unavailable` and corrupt data fail with no lexical query (`AC-06.2`). `degradable` now reads the unmapped failure through `degradation` before `asSearchFailure`. Reopen if the product wants a corrupt-data failure to surface as a different code.
- **FD-02 `Idempotent`.** The round trip stays, with its reason: `receipts.execute` runs the write inside a repository transaction whose failure channel is `RepositoryError`, so a repository failure must be raised (to roll back) and a business rejection returned as `Rejected` (to record the receipt). Removing it needs a generic failure channel on `MutationReceiptRepository`, a separate port change. The mapping back goes through `UseCaseF.repository`, i.e. `translate`, so the policy is still single. `Idempotent` re-raises only errors that stayed `Repository(_)`: a `Search(VectorSearchUnavailable)` produced inside a write would become a rejected receipt instead of aborting the transaction. No write produces it today; `IdempotentSpec` pins the rule.
- **FD-06.** `MongoStoredDocumentDecoding.toStored` (for `ValidatedNel[StoredDocumentError, A]` and `Either[StoredDocumentError, A]`) is the one collapse into `InvalidStoredData`; `MongoDocumentFields.toRepository` and `MongoStoredDocumentDecoding.repository` now delegate to it. `RepositoryError.InvalidStoredData` carries no payload on purpose: accumulation is codec-internal and the detail is deliberately not surfaced (the read fails closed; no field name or stored text is logged or returned, and no field values are logged). Accumulation is therefore kept where the errors exist: `MongoSearchSessionWorkCodecs.readWork/readClaim` return `ValidatedNel` instead of `.leftMap(_.head)` and report the problems of session and event together. `leftMap(_ => RepositoryError.X)` sites went from 32 to 27; they are not eliminated.
