## Behavior and contracts

### Slice 1 — Dead-end recovery, reasons, similar jobs

**GDF-01 Zero-result recovery.** When a candidate job search with filters returns no eligible job, the service re-runs it with one filter relaxed at a time and returns the first non-empty page with `relaxedFilters` (which filter, from what, to what). Default order: drop `createdAfter`, then turn `skills` from all-of to any-of. City is not relaxed by text. Distance relaxation is deferred (`nearbyJobs` only; no radius rule yet; see Checkpoint). At most two relaxation attempts per request; each attempt is charged exactly what the `jobs` field was charged for the request. No relaxation when the original page is non-empty. Unfiltered empty results stay empty. The `createdAfter` bound is inclusive (`createdAt >= createdAfter`, `MongoJobRepository.scala:412`); dropping it removes the lower bound for every job.

**GDF-02 Visible reasons.** Hits gain `missingSkills` next to `matchedSkills`: for a candidate viewing jobs, the job's required skills not in the caller's own profile; for a recruiter viewing candidates of an owned job, the job's required skills not in the candidate's skills. Both derive from data the caller can already see, so no new private candidate data is exposed. The function stays pure and shares the existing normalization (case, spaces).

**GDF-03 Similar jobs.** `similarJobs(jobId, first)` returns open, visible jobs nearest to the given job's stored embedding, excluding the job itself, with the standard eligibility recheck. It makes no embedding provider call. A missing or stale job embedding returns `SearchUnavailable`. It is an expensive root with the same price formula and budget. The job must itself be visible to the caller; otherwise the result is as for an unknown job, so existence is not disclosed.

Recorded deviations for GDF-03 (coordinator decisions, 2026-11-12; the owner may veto each): (1) candidate-only: a Recruiter or Admin gets `CANDIDATE_REQUIRED`, as `semanticJobSearch` and `recommendedJobs` do; the GDF-03 text above does not restrict the caller. (2) No search-session recording and no `searchId` argument or field: `SearchKind` is a closed enum in the operational event wire codec, the Mongo codec and the analytics build (`OperationalEventTransforms.scala:300`), and a new kind is an event-contract change. (3) `first: Int!` is required; the GDF-03 signature in the text above does not state nullability (the other search roots also take `first: Int!`). The source job is removed in the service after the vector query, not by a `_id` filter in `$vectorSearch`, which would need a new index. The vector query limit is `branchLimit`, not `first`: at least 100 (`PageSize.Max`, `VectorSearchConfigValidation.scala:41`), applied in `MongoSemanticSearchRepository.scala:190`. `first` is applied in the service after the source job is dropped and the remaining hits are rechecked. The source job takes one of the `branchLimit` slots, so with `branchLimit` = 100 and `first` = 100 a page holds at most 99 results, within the "at most `first`" contract.

### Slice 2 — Follow-up message drafts

**GDF-04 Message drafts.** A query returns a draft for a given application and action:

- Recruiter or Admin owner: Accept, Interview, Reject.
- Candidate (own application): Decline reason, interview reschedule request.

Each draft has `body` (plain text), `basis` (the facts it used: job title, matched/missing skills, interview slot) and `editable: true`. Drafts are English and neutral in tone; there is no language parameter for the MVP (Q2). It is built from templates plus the GDF-02 facts. Rules: it never includes a score, rank or similarity; it never includes private residence, availability or consent; a rejection draft lists skills only as a suggestion for the recruiter to confirm. A draft changes nothing and sends nothing. The recruiter submits the final text through the existing action mutation, which keeps its required `feedback`/`reason` validation. Draft access requires the same ownership as that mutation, enforced in the service.

### Slice 3 — Query understanding and alerts

**GDF-05 Query understanding.** `semanticJobSearch` returns `suggestedFilters` derived from the query text. Skills come from the canonical skills of the eligible open jobs (the same population as `jobDiscoveryFacets`); a city is recognized only when it exists in that set. Matching is deterministic and case-insensitive. Suggestions are never applied automatically (D2). Empty or unrecognized text yields none.

**GDF-06 Saved searches and job alerts.** A candidate saves a keyword query and filter. At most 5 saved searches per candidate (owner default, 2026-11-11; typed configuration). The cap is enforced in the store, not by a preflight read: one slot per candidate and index (slot rows `<candidateId>:<slot>` or a guard document; the exact form is chosen by the Data Engineer), with a race test asserting that two concurrent saves by a candidate with 4 stored searches leave at most 5. The query text is stored only in `saved_searches`.

Matching is keyword-only: no embedding, no vector search and no provider call at save time or per run (owner decision 2026-11-11). A bounded scheduled worker reads jobs created after the saved search's position, and keeps only jobs whose text matches the saved keywords and that pass the same eligibility rules as search. The cadence and the per-run limit are typed configuration; their default values are documented in slice 3.

Port and delivery (N1): a new port `JobAlertNotificationProvider` with `notify(alert: JobAlertNotification(savedSearchId, jobId, recipientId, key), now)` and `lookup(key)` returning a `JobAlertReceipt`. The key is `jobAlert:<savedSearchId>:<jobId>`, built from IDs only, never from query text. The provider gives exactly one receipt per key and uses the same error type as the interview port. The ledger provider is the only implementation (fake/local); no email provider is added. Receipts are stored in a new collection `job_alert_receipts` keyed by the key. Delivery runs in one transaction that re-reads the saved search (it exists and is owned by the recipient) and rechecks that the job is still open and visible to the candidate before it inserts the receipt. The worker advances a per-saved-search position `(createdAt, jobId)` only after the receipts for that batch are written. A crash between those steps re-considers jobs, and the key prevents a second receipt.

Contract tests: the interview contract suite is generalized into one shared receipt contract run by two subjects, the interview provider and the alert provider. The existing DDC-04.x test names are kept, and a GDF-06 alert subject is added. Test-only change, reviewed by Code Reviewer and QA.

Schema: one versioned migration `037_saved_searches_and_job_alert_receipts` creates `saved_searches` and `job_alert_receipts`, with closed validators, the indexes (`candidateId` on `saved_searches`; `recipientId, savedSearchId` on receipts; TTL on `retentionExpiresAt` on receipts), and recorded validator and index history. It is re-runnable with recovery and verification. Migration 036 is never edited. Flyway is not used for Mongo. The receipt retention period is not set by this spec (see Checkpoint); the TTL index is created only after the owner or the slice documents that period in the retention docs. A TTL shorter than the window in which a job can be re-considered would allow a second receipt for the same key, so the slice must justify the value against the position rule.

Privacy and erasure: query text appears only in `saved_searches`. It is never in receipts, keys, logs, errors, events or analytics (a test asserts this). Account deletion removes the candidate's saved searches first, then their receipts by `recipientId`. It is re-runnable. Later SES alert adapter is out of scope.

### Cross-cutting

**GDF-07 Baseline measures.** Before slice 1 ships, record on a bounded synthetic corpus: zero-result rate, rank of the first click, share of searches followed by a click, and recruiter time from application to first status change. No target is set until a baseline exists. Local measures are labelled as such and prove no production result.

**GDF-08 Authorization, cost and failure.** Every new root checks role and ownership before any paid or vector call (provider call count is asserted 0 on a forbidden request). The cost budget applies to GDF-01 and GDF-03. The `SearchUnavailable` union applies to GDF-03 (implemented, see its row). `jobs` (GDF-01) has no union: a failed base search stays a GraphQL error, while a failed optional relaxation keeps the empty base page and is logged (`JOB_SEARCH_RELAXATION_FAILED`). This is a documented deviation (see the GDF-08 row and the deviation list under Checkpoint). Failure of an optional step (relaxation, suggestions) never blanks the base result.

## Performance and cost

- Slices 1 and 2 add no provider call. GDF-01 adds at most two extra searches on an empty first page; GDF-03 reads a stored vector.
- GDF-06 adds no provider call and no vector search per run. Each scheduled run issues one bounded keyword query per saved search and at most the per-run limit of receipts. Work is bounded by the per-candidate cap (5), the cadence and the per-run limit (typed configuration). Keyword-only matching was chosen over vector alerts (owner, 2026-11-11): it needs no embedding provider and no vector read, at the cost of finding only keyword matches. Storage grows with receipts, which the TTL index on `retentionExpiresAt` bounds once its period is set. No price or storage size is assumed here; they are not measured.
- No latency or recall claim is made. Workload, dataset size, concurrency and percentiles are recorded only by a measured run.
