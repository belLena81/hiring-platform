# Hiring Search Enhancements

## Status and outcome

- Status: ready for specialist review
- Actor: candidates searching open jobs; recruiters matching candidates against jobs they own
- Outcome: expose deterministic match evidence, support recruiter-entered natural language plus structured candidate filters, and provide selectable MongoDB hybrid-ranking and embedding-evaluation paths without changing the default search behavior.
- Authorized scope: additive candidate search-profile fields and GraphQL inputs/outputs, Mongo persistence and setup, semantic search adapters/services, local search evaluation, docs, and focused tests.
- Non-goals: LLM-generated explanations or decisions, resume parsing/storage, account/job lifecycle changes, new paid services or provisioning, automatic rollout to live Atlas, replacing the durable manual embedding worker, or adding candidate availability/location to job-search ranking.

## Verified source facts

- `SemanticSearchService` embeds candidate job-search text and uses `MongoSemanticSearchRepository` for vector and hybrid retrieval. Candidate recommendations and recruiter candidate matches are currently vector-only.
- Job hybrid retrieval runs Atlas `$vectorSearch` and `$search` as parallel queries and fuses results in application code with reciprocal-rank fusion. The existing fusion is the default and remains available.
- Embeddings are manually generated by Voyage through a durable work queue; embedding writes use source-hash and aggregate-version checks. Candidate searchable text contains summary and skills, not structured location/availability.
- Candidate profiles currently contain skills, experience summary, and a resume reference. Recruiter candidate matches are authorized against an owned open job and return only name, skills, and experience summary.
- Atlas Search index setup owns vector and job lexical indexes. MongoDB `$rankFusion` requires version 8.0+, `$scoreFusion` requires 8.3+, and native `$rerank` requires Atlas 8.3+ and is preview-only; compatibility must be explicit and opt-in.

## Contracts and decisions

- Add optional candidate current residence (country and city) and availability status (`AVAILABLE_NOW` or `UNAVAILABLE`). Add a candidate-controlled `recruiterSearchOptIn`, default false for new and legacy profiles. These fields are not included in embedding text and are not returned in recruiter candidate-match results. Persist a deterministic lowercase/trimmed `skillsCanonical` search sidecar while preserving original skill spelling in profile output.
- Add optional natural-language recruiter query and structured candidate-match filters for required skills (all required), residence country/city, and availability status. A present residence requires country and may include city. Existing `candidateMatches(jobId, first, searchId)` calls retain their meaning. An absent natural-language query uses the owned job embedding; a supplied query adds a separate query embedding and lexical candidate branch, fused with the owned job's candidate-vector branch. Private filters apply only to opted-in candidates; opted-out or missing-consent candidates retain their inclusion and score contribution from the existing unfiltered job-vector branch, independent of private-field values. Missing private values do not match for opted-in candidates. No raw residence/status filters are saved in search-session telemetry.
- Add deterministic `matchedSkills` evidence to ranked job and candidate results. Skills use case-insensitive trimmed matching; no model-generated rationale or inference is returned.
- Existing app-side RRF remains the default. MongoDB rank fusion and score fusion are selectable experimental strategies; native fusion and reranking are disabled by default. Native reranking is separately opt-in and operates only on a bounded candidate set.
- Preserve current manual embedding writes as authoritative. Automated Embedding is an isolated Atlas preview comparison, not a production storage/query mode or a dual-write path. The experiment must use disposable synthetic data and disclose provider/API/index storage costs; no Atlas deployment is provisioned by this task.
- Candidate profile schema evolution is additive. Missing optional fields decode as absent and default opt-in to false; do not backfill or infer location, availability, or consent. Add a versioned, restart-safe verification migration that scans bounded `_id` batches, permits absent fields, rejects malformed present residence/status/consent values, derives only the non-sensitive canonical skill sidecar from existing skills, and records completion only after verification. All older application binaries must be stopped before migration/new writes because profile replacement by an old binary can drop new fields. New writes validate the same invariants. Add new non-destructive Atlas Search indexes under new names; do not drop existing indexes.
- Candidate residence/availability/opt-in can be read in the authenticated candidate's own profile only. Recruiter result DTOs and search-session telemetry exclude raw values. Explicit residence/availability filters change only opted-in candidates' results; opted-out candidates retain baseline inclusion independent of private-field values.
- Candidate lexical retrieval searches only the fixed fields `profile.skills` and `profile.experienceSummary` through the configured `candidateLexical` index (default `candidates_text_search`). Candidate matches require `role = Candidate` and `accountStatus = Active`. Apply active-account, required-skill, and opted-in private-filter predicates inside each vector and lexical retrieval branch before its `numCandidates` limit.
- Use a new `candidateMatchVector` index (default `candidates_embedding_vector_match_v1`) separate from the existing recommendation index. Declare every filter path: `role`, `accountStatus`, `embeddingMeta.model`, `profile.skillsCanonical`, `profile.recruiterSearchOptIn`, `profile.currentResidence.countryCanonical`, `profile.currentResidence.cityCanonical`, and `profile.availabilityStatus`. Put structured candidate filters inside `$vectorSearch.filter` before top-K; use an OR branch so opted-out/missing-consent profiles bypass only residence/availability predicates while opted-in profiles must satisfy all supplied private predicates. Trim/case-fold residence into canonical sidecar values and retain original spelling only in the candidate's own profile. Wait for the configured Atlas readiness timeout and require each new index to be queryable before using it.
- Candidate search repositories return a minimal DTO (`id`, `name`, skills, experience summary, embedding metadata, score), never full candidate account/persistence documents.
- `matchedSkills` is the case-insensitive trimmed intersection of the authenticated candidate's skills with each job's skills, or the owned job's skills with each matched candidate's skills; preserve spelling from the job and sort case-insensitively with a stable tie-breaker.
- Natural-language recruiter queries are trimmed and capped at `SearchableText.QueryMaxChars` (2048) before provider/search work. Required skills are capped at 100 values of at most 256 characters each; residence country/city are nonblank and at most 256 characters each. All filter values use fixed-path typed BSON.
- Each vector/lexical branch is limited to configured `numCandidates`. App RRF uses rank constant 60, equal branch weights, and deterministic ties by component rank then candidate ID. Without recruiter query, candidate matching uses only the job-vector branch. Native `$rankFusion` uses equal weights; `$scoreFusion` uses sigmoid normalization and equal weights. Final Mongo-fused results sort by score then ID.
- Server configuration selects `applicationRrf` (default), `mongoRankFusion`, or `mongoScoreFusion`; a separate `rerank.enabled` option defaults false and reranks no more than the requested page size (bounded by `PageSize.Max`). Preserve the fusion score as `retrievalScore`; unsupported stage/version failures map to sanitized search unavailability without fallback.

|---|---|---|---|
| HSE-01 | A candidate creates or updates their profile with current residence, availability, and recruiter-search consent | Values validate, persist, round-trip through `me`, participate in idempotency fingerprints, and never alter profile embedding text; legacy profiles default to no consent | Unit/service/GraphQL contract and Mongo integration tests; migration restart/verification test |
| HSE-02 | A recruiter requests matches for an owned open job with optional natural-language text and filters | Retrieval combines job vector, optional query vector, and optional lexical results; applies required skills and active-account filters before ranking; private filters alter only opted-in candidates' results; rejects non-owner/closed-job access before provider/search work | Service, Atlas-pipeline construction, GraphQL auth, and Mongo integration tests |
| HSE-03 | Ranked jobs or candidates are returned | `matchedSkills` is deterministic, case-insensitive, trimmed, and derived only from the candidate/job skill sets | Unit and GraphQL contract tests |
| HSE-04 | Search fusion strategy is default or explicitly configured | Default app RRF remains behaviorally unchanged; opt-in Mongo rank/score fusion sends one aggregation pipeline and maps ranked scores safely; unsupported server errors remain sanitized and never silently switch ranking | Unit pipeline tests, config tests, and Atlas integration test when available |
| HSE-05 | Native reranking is disabled or explicitly enabled after fusion | Disabled path makes no reranker call; enabled path reranks only a bounded top-N result set and preserves original fusion score separately; preview/runtime incompatibility is surfaced as search unavailability | Unit pipeline/config tests and Atlas 8.3+ test when available |
| HSE-06 | Search is evaluated on a bounded synthetic dataset | A reproducible harness compares ANN to ENN ground truth and records Recall@K/NDCG, throughput, errors, latency percentiles, CPU/memory, filters, concurrency, vector/index size, query metrics, and environment; no performance claim is made without captured run results | Harness/unit checks; live Atlas metrics only if authorized Atlas configuration is available |
| HSE-07 | Manual and Automated Embedding are compared | A disposable Atlas-only procedure creates an isolated Automated Embedding index, measures indexing/query latency and provider calls/cost against the existing manual path, and can be removed without altering application collections or data | Documented procedure and Atlas run record; remain explicitly unverified if no Atlas environment is configured |

## Workload assumptions and gates

- Use a bounded synthetic dataset of up to 10,000 jobs/candidates, 100 fixed queries, and concurrency levels 1 and 8; report warm and cold runs separately. Record observed provider calls/cost only from provider/Atlas billing telemetry; label calculated estimates as estimates. This is a comparison workload, not a production-scale claim.
- Keep page sizes and rerank count within existing API bounds. Do not provision infrastructure, spend money, or create a real Atlas project as part of implementation.
- Required local evidence: focused service/config/pipeline/GraphQL tests, `sbt test`, configured formatting checks, and `sbt 'IntegrationTest / test'` for Mongo persistence and migration behavior. Atlas-only fusion/rerank/automated-embedding execution is separately reported as unverified when unavailable.
