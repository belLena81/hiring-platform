## Behavior and contracts

### Actors and public boundaries

- Candidate retains access only to their own hiring data; recruiters initiate work only for owned jobs/applications; singleton Admin has authorized repair visibility. Background workers use narrowly scoped service identities.
- Actor identity comes from trusted authentication. Workflow records retain the minimal initiating authority/audit reference, and sensitive steps recheck current resource ownership, account state and permitted application transition at their guarded write.
- Ordinary application mutations return according to their current local transaction. Kafka/provider unavailability does not undo a committed hiring write; failure to commit its required Mongo outbox does fail the transaction.
- The local GraphQL contract is `scheduleInterview(input)`, `interviewWorkflow(workflowId)` and `repairInterviewWorkflow(input)`. Inputs require typed application/workflow IDs, UTC instants, idempotency keys and an expected revision for Admin repair. The active SDL and representative operations live in `src/test/resources/graphql/`.
- Operator inspection and repair use a scoped service boundary, with expected revision, bounded selection and safe audit. Admin authorization is required; a caller-supplied workflow ID is never authority. Decide CLI versus API delivery before exposing this boundary.

### Pure workflow state and typed outcomes

A selected workflow defines a closed state ADT and pure decision function:

```scala
// Illustrative application-independent policy shape, not an approved wire schema.
def decide(
    state: WorkflowState,
    input: WorkflowInput,
    now: Instant
): Either[WorkflowError, (WorkflowState, List[WorkflowCommand])]
```

Use capability-specific states for waiting on a result, retry due, compensating, completed, and repair required. Keep progress separate from `ApplicationStatus`. Transition policies cannot read the clock, invoke providers, allocate IDs, log, or inspect Mongo/Kafka types. Commands describe effects; the interpreter executes them.

Expected results distinguish applied, duplicate, stale revision, denied/deleted subject, retry scheduled, and repair required. Validation, unavailable dependencies and conflicts remain typed at service/repository ports. A stale reply never moves state backwards or issues another external command. Unrecognized/inconsistent messages are recorded as bounded quarantine outcomes before acknowledgment, or remain unacknowledged if durable recording fails.

### Transaction and acknowledgment frontier

1. Validate record size/shape and authorized producer routing before interpretation; never execute embedded instructions from message text.
2. Load the workflow and authoritative deletion/authorization guards; invoke the pure decision using explicit time/identity inputs.
3. In one Mongo transaction, insert the inbox deduplication identity, compare-and-set workflow revision, and insert outgoing outbox commands. Unique constraints protect deduplication and command identity.
4. Commit durable state before acknowledging Kafka. A failed transaction must not leave a completed inbox marker. A crash after commit and before acknowledgment produces a harmless replay.
5. Process each ordered key sequentially and bound concurrency across keys. Commit only the contiguous durable completion frontier per partition; a later completed record cannot advance past an unresolved earlier record.
6. Persist terminal rejection/quarantine when it is safe to consume a poison record. Never skip an earlier unrecorded failure merely to improve lag.

Mongo failure leaves the Kafka record available for replay. Kafka transaction success alone cannot certify Mongo or calendar/email completion. Inbox retention covers the maximum permitted replay horizon; older replay is denied or requires a separate reviewed recovery procedure.

### Claims, timeouts, retries and cancellation

- Persist deadlines, attempts, next due time, revision and claim fencing identity. A timeout is durable work discovered after restart, not just a sleeping fiber.
- Only the interpreter owns workflow retries. Provider adapters perform one logical attempt and classify outcomes; account for any unavoidable SDK internal retry in the same total budget.
- Configure bounded attempts, capped backoff, bounded in-flight calls and claim durations. A deterministic retry policy takes attempt/time/jitter input; independent invalid settings accumulate at startup.
- A completion must match current step, revision and claim token. An expired worker cannot write success over a newer owner. External fencing depends on provider capabilities; reconciliation is required when local fencing cannot prevent an already sent external request.
- Cancellation stops new claims and awaits owned fibers/resources. Do not mark unfinished work complete; another worker may recover after claim expiry. Cancellation during uncertain external completion enters reconciliation rather than blind retry.
- Attempt exhaustion and compensation failure produce durable repair state with reason, last safe observation and permitted operator actions. Repair itself is idempotent, guarded and audited.

### Recovery and deletion

For every step document its durable precondition, idempotency key, timeout, retry budget, success observation, compensating action or reason it is irreversible, and repair action. Reuse the same key after a network timeout. If the provider cannot prove whether an effect happened, query its state or retain an explicit uncertain outcome; do not assert duplicate-free delivery.

Deletion prevents new subject work and replay from recreating derived data. Inventory commands/results, inbox, outbox, quarantines, provider state, logs and backups in retention/deletion analysis. Preserve sufficient minimized deduplication/fencing evidence to deny replay without retaining prohibited payloads. Reversible reservations can be released; sent notifications, account tombstones and elapsed retention need forward recovery. Never resurrect deleted content to compensate.

For interview scheduling, an authorized recruiter requests a reservation for an owned application. Validate interval/time-zone interpretation, participants, idempotency and currently permitted transition before reserving. Persist intent before calling the calendar. Only after a confirmed reservation, atomically commit the guarded move to `Interview`, history and notification intent. Recheck authorization/status inside that transaction.

If the guarded status write fails or the deadline expires before it can commit, release the reservation idempotently. If release fails, preserve compensation/repair work. If the transaction outcome is uncertain, inspect its durable receipt/state before deciding to release. A confirmed hiring commit must not accidentally lose its reservation through speculative compensation. Admin repair reconciles existing effects and resets bounded attempt accounting; it does not reopen a released reservation or extend the immutable deadline. A compensated workflow can return to visible RepairRequired after repair, without a new reservation or hiring commit.

Candidate/recruiter notifications occur after commit. Partial delivery tracks each recipient independently; sent messages cannot be recalled. Unknown delivery requires provider lookup/idempotency or visible repair. Restart and replay cannot generate another reservation for the same accepted step. Existing `moveApplicationToInterview` remains a status/history operation with its existing semantics; it does not silently acquire calendar/provider dependencies.

Local scheduling uses future UTC intervals, `[start,end)` participant availability, persistent fake provider receipts and completion only after both participant notifications. Cancellation/rescheduling and real providers are deferred.

## Code style and boundaries

Apply [engineering quality](../engineering-quality.md) and [schema evolution](../schema-evolution.md).

- Domain owns immutable state/transition/error ADTs. Use typed IDs and exhaustive matches; `Option` models legitimate absence. Avoid null/sentinel outcomes, business exceptions, unchecked `.get`, and mutable global progress.
- Application services retain `UseCaseIO[A] = EitherT[IO, UseCaseError, A]`; repositories retain `RepositoryIO[A] = EitherT[IO, RepositoryError, A]`. Preserve aliases through helpers/transaction callbacks; unwrap only at owning adapter/runtime boundaries.
- Adapters own Mongo codecs/sessions, Kafka serializers/offsets and provider protocol translation. Driver exceptions are classified once; retryable business outcomes are not thrown and immediately recovered.
- `Resource` owns consumers, producers, clients, workers and timers; managed FS2 streams provide backpressure. No detached fibers or unbounded queues. `Ref` can coordinate a live process but cannot become the durable workflow store.
- Prefer capability names such as interview reservation and embedding recovery over phase names. Introduce shared machinery only after concrete repeated behavior warrants it.
- No new schema version field, dual readers/writers or legacy contract backfills before MVP. Operational Mongo collection/index changes still need versioned repeatable migration, restart/concurrent-start verification and recovery procedures.
- For operational migration, define uniqueness and due-work query indexes, bounded initialization, verification before worker enablement, mixed-binary restrictions, and forward recovery. An application rollback is not a database rollback.

### Decisions and assumptions

User-authoritative decisions: (D1) add cancellation and rescheduling of a scheduled interview; (D2) the calendar slot counts as released only after the calendar provider's cancellation is **confirmed**, never on request; (D3) prepare Amazon SES behind the existing `InterviewNotificationProvider` port, but tests and local runs use the fake, with no live AWS calls and no credentials in the repository; (D4) the real calendar provider is chosen by a separate cost comparison, so the port is provider-neutral; (D5) non-local notification delivery is **at-least-once** (duplicates possible, never silently lost) with idempotency keys retained, and calendar reserve stays idempotent; (D6) keep FS2/fs2-kafka and add no workflow beyond interviews; (D7) production Kafka sizing is deferred to Phase 14.

Further user decisions (2026-10-08, later): (D8) the candidate on the application, the owning recruiter and Admin may **cancel**; (D9) a candidate cannot reschedule directly but may submit a **reschedule request**, which only flags/notifies the recruiter and changes no slot; (D10) a recruiter or Admin **reschedule is a proposal that requires the candidate's acceptance**: propose, then the candidate accepts or declines; accept runs the hold-first, guarded-swap, confirm-cancel-old flow; decline, expiry or withdrawal return to `Completed` with the old slot intact.

(D11, resolves A1) **Cancelling an interview, by the candidate, the owning recruiter or Admin, is a rejection of the application**: it moves `Interview -> Rejected` through the existing permitted transition (verified: `ApplicationLifecycle` permits `Interview -> Set(Hired, Rejected)`; `Rejected` is terminal; the README matrix agrees). No transition is added. Reschedule (request, propose, accept, decline, withdraw, dismiss) never changes the application, which stays `Interview`. The existing rule "rejection requires feedback" applies, so `cancelInterview` records **system-generated** feedback (closed initiator ADT, fixed text, see "Cancel feedback" below); the input carries no user-supplied text (user correction 2026-10-08). The user approved the remaining defaults (A3, A5–A8, 72-hour proposal lifetime) on 2026-10-08.

### Domain design

Keep one workflow per interview. Add state without a new aggregate or Saga engine. The pure workflow policy still never reads or writes `ApplicationStatus`; the only status change in this scope is `Interview -> Rejected` on cancel, performed by the existing `ApplicationLifecycle.changeStatus` inside the guarded cancellation transaction below.

**Cancellation ordering (decision).** Commit-first, provider-confirm-second, notify-last:
1. One guarded Mongo transaction (in the `cancelInterview` service call) rechecks the application is `Interview`, the actor's authority, the workflow revision and phase (`Completed` or `ProposalPending`) and the start is in the future. It then writes the application as `Rejected`, the append-only history event (previous `Interview`, new `Rejected`, actor, UTC time, system-generated feedback), the existing `statusChanged` operational outbox event, the workflow as `CancelPending` (proposal cleared) and the `CancelCalendarSlot` command intent plus the request receipt. All or nothing.
2. The worker confirms the provider cancel (same key, lookup on unknown). Only then is the slot reported released.
3. Both participants are notified after confirmation; the workflow ends `Cancelled`.

Justification. Provider-first (cancel the slot, then commit `Rejected`) can leave the slot gone while the application is still `Interview` if the commit fails, for example because the recruiter hired the application in between (`Hired` is terminal, so the cancel cannot be completed), and that state has no clean compensation because the released slot cannot be restored. Commit-first removes the race: `Rejected` is terminal, so nothing else can change the application after the commit, and a concurrent hire or generic reject committing first makes the cancel return the existing invalid-transition outcome without touching the provider. The cost is a bounded, visible window in which the application is `Rejected` while the slot is still held; the user rule (slot released only after confirmed provider cancel) holds throughout. That window is never silent: the workflow `progress` shows `CancelPending`, the cancel command is durable and retried, and exhaustion enters `RepairRequired` (application stays `Rejected`; repair resumes the provider cancel, never reverts the status).

- New fields: `generation: Int` (reservation generation, 0 for the original), `pendingInterval: Option[InterviewInterval]` (the replacement being held after acceptance), `cancelledAt: Option[Instant]`, `proposal: Option[InterviewRescheduleProposal(interval, proposedBy: UserId, expiresAt: Instant)]` (at most one), `rescheduleRequestedAt: Option[Instant]` (advisory flag, no text). Reservation key for generation `n` is `<id>:reserve` when `n = 0` (unchanged) and `<id>:reserve:g<n>` otherwise. Cancel keys are `<id>:cancel:g<n>`; notification keys include the kind and generation, for example `<id>:cancelled:notify:<participant>` and `<id>:rescheduled:g<n>:notify:<participant>`.
- New phases: `ProposalPending` (stable waiting state: old slot untouched, no hold; ends by accept, decline, withdraw, expiry or cancel), `CancelPending`, `CancelNotificationsPending`, `Cancelled` (terminal), `RescheduleHoldPending` (after acceptance), `RescheduleSwapPending` (new hold confirmed; guarded workflow write moves the live interval), `RescheduleCancelOldPending`, `RescheduleNotificationsPending`, `RescheduleCompensationPending` (cancel the unneeded new hold). Cancel and propose start from `Completed`; cancel also from `ProposalPending` (A5).
- New commands: `CancelCalendarSlot(key)`, `LookupCalendarCancellation(key)`, `HoldReplacementSlot(key, interval)` (idempotent reserve for the new generation), `CommitRescheduledInterval`, `LookupRescheduleCommitReceipt`, `ExpireProposal` (durable due work with `availableAt = proposal.expiresAt`, issued in the same transaction as the proposal), and kind-qualified `Notify`. New events mirror them (`CancelConfirmed`, `CancelOutcomeUnknown`, `CancelLookupConfirmed/Absent`, `HoldConfirmed/Rejected/OutcomeUnknown`, `SwapCommitted`, `ProposalExpired`, and so on). All remain pure; `decide` still returns `Either[InterviewWorkflowError, Decision]`.
- Informational notifications (proposal made, declined, withdrawn, expired, reschedule requested, reschedule could not be booked) do not gate a phase: they are kind-qualified `Notify` commands issued in the transition's transaction, applicable in any phase except `RepairRequired`, each with its own key (`<id>:<kind>:r<revision>:notify:<participant>`). Exhaustion marks that command `RepairRequired`, which Admin inspection and repair expose; it never changes the workflow phase and is never silently dropped.
- New requests (validated purely): `Cancel(actorRole, now)`, `Propose(newInterval, proposedBy, now, ttl)`, `AcceptProposal(now)`, `DeclineProposal`, `WithdrawProposal`, `RequestReschedule(now)`, `DismissRequest`. `Cancel(initiator, now)` carries a closed `InterviewCancellationInitiator` (`Candidate`, `Recruiter`, `Admin`) derived by the service from the trusted actor (the application's candidate, the owning recruiter, or the Admin role), never from input. **Cancel feedback:** a pure total function `InterviewCancellationFeedback.text(initiator)` returns a fixed constant per initiator (for example "Interview cancelled by the candidate.", "Interview cancelled by the recruiter.", "Interview cancelled by an administrator."), always non-blank, containing no user data or ids, and the service passes it to `ApplicationLifecycle.changeStatus(Rejected, ..., Some(text), None)`, so the existing "rejection requires feedback" rule holds without free text. It is stored only in the status history, not in workflow state, notifications, logs or messages. New typed errors: `InterviewAlreadyStarted` (`startsAt <= now`), `InterviewAlreadyCancelled`, `InterviewNotSettled`, `RescheduleIntervalUnchanged`, `ProposalAlreadyOpen`, `NoOpenProposal`, `ProposalExpired`, plus existing `StartMustBeInFuture`/`EndMustFollowStart`. Acting-party authorization is a service concern; the domain receives only the validated actor role. Re-delivery of the same request key returns the existing workflow (not an error).

Invariants: a cancel commits `Rejected` (with history and the existing outbox event) atomically with its provider-cancel intent, and the slot is released only after confirmed provider cancel; an application is never `Interview` with a cancelled slot, and a `Rejected` application with a live slot is always visible as `CancelPending` or `RepairRequired`; no replacement is held without the candidate's acceptance; the old reservation is cancelled only after the replacement is confirmed and committed (a participant never loses a slot without a replacement); the live interval changes only in the guarded swap; a slot is reported released only on provider-confirmed cancel; at most one open proposal exists; exactly one of cancel, propose, accept, decline, withdraw and expiry can leave a given revision because each exit is a revision CAS.

Recipients per event (all after the event is durable, at-least-once): cancel confirmed notifies both participants; proposal notifies the candidate; decline notifies the recruiter; withdrawal notifies the candidate; expiry notifies both; reschedule request notifies the recruiter; successful reschedule notifies both after the old slot is confirm-cancelled; an accepted proposal that cannot be booked notifies both. The initiating actor is not excluded, which keeps recipient rules uniform and independent of actor role.

### Provider-neutral calendar port

Change `InterviewCalendarProvider` (and `InterviewCalendarLedger`) by adding, keeping `reserve` semantics unchanged:

- `cancel(workflowId, idempotencyKey, now, execution): InterviewProviderIO[InterviewCalendarCancellation]` returning a confirmed outcome `Cancelled(at)` or `AlreadyCancelled(at)`, or a typed unknown-reservation outcome. Success means the provider confirmed the cancellation; a timeout is `Unavailable` and triggers lookup, never a local assumption.
- `lookup(workflowId, idempotencyKey)` (replacing the per-workflow lookup) returning the reservation with its state (held or cancelled, with timestamps).
- Conflict check for `reserve` ignores holds with the same `workflowId`.
- The existing `release` is retained for the scheduling compensation path and implemented as the same confirmed cancel; it is not removed in this scope (avoids reopening DHW-10).

Required real-provider capabilities (decision-register input, not a choice): idempotent reserve, lookup by key, confirmed cancel.

### Notification port and at-least-once guarantee

Add a closed kind (`Scheduled`, `Cancelled`, `Rescheduled`, `RescheduleProposed`, `RescheduleDeclined`, `RescheduleWithdrawn`, `RescheduleExpired`, `RescheduleRequested`, `RescheduleUnavailable`) to `notify` and to the receipt. Guarantee for non-local providers: a notification is attempted until a receipt is durably recorded or repair is visible; a crash after the provider accepted a message but before the receipt is stored causes a resend, so duplicates are possible and loss is not silent. The idempotency key is retained for fake deduplication and as a message correlation header; amazon SES offers no send-time idempotency or lookup by key, so SES `lookup` consults only the local receipt store, and `Absent` means "may or may not have been sent". The fake keeps its exactly-once receipts. The guarantee is documented in `docs/use-cases.md`.

### Persistence, migration and Kafka impact

- Mongo: add the workflow fields above (including the embedded `proposal` and `rescheduleRequestedAt`), new phase/command strings (including `ProposalPending` and `expireProposal`), receipt `kind` and generation-aware reservation uniqueness. Migration `018_interview_cancellation_reschedule` (preceded by `017_interview_ledger_collections`, which renames the ledger collections to business names; ids 011-016 were already taken) is a versioned, restartable, concurrent-start-safe step: (1) expand the command-type validator and any phase validator, (2) replace any workflow-only reservation unique index with a unique `(workflowId, idempotencyKey)` index and keep participant-overlap index semantics, (3) verify index definitions before workers start, failing closed on unknown definitions. - Deletion and Admin repair: cleanup purges the new fields (proposal, request flag), receipts, pending `ExpireProposal` and informational notification commands, and reservations; an open proposal of a deleted subject is cleared without notification; when a non-fake provider holds a live reservation, cleanup performs a confirmed cancel before purging local evidence and sends no notification to a deleted subject. An expiry or accept racing deletion is denied by the permanent subject fence. Admin repair covers every new phase and any command-level `RepairRequired` informational notification through lookup-first reconciliation and attempt-generation reset, never re-opens a cancelled slot, and records the actor. `ProposalPending` is not a failure state; Admin resolves it by withdrawal.

### SES adapter preparation

- Typed config under the interview notifications scope: `provider` (`ledger` default or `ses`), `ses.enabled` (default `false`), `ses.region`, `ses.fromAddress`, optional `ses.configurationSet`. Both `provider = ses` and `ses.enabled = true` are required to select SES; independent invalid settings accumulate at startup and fail closed. Configuration has no key, secret or token fields; credentials come only from the AWS default credential chain at runtime (role or environment), and tests must not read it. Examples contain placeholders only.
- Adapter implements `InterviewNotificationProvider`: resolves the recipient address from the user store at send time (never in messages, logs or workflow records), builds a minimal template (role, interval, kind; no resume or unnecessary personal data), sends through a thin `Resource`-owned client trait so tests use an in-memory stub, wraps blocking calls with `IO.blocking`, classifies outcomes (accepted, throttled/5xx/timeout as `Unavailable`, rejected address as `Conflict`) once, and disables SDK-internal retry so the interpreter owns the budget. A deleted or tombstoned subject yields no send.
- Dependency decision: use `software.amazon.awssdk:sesv2` with the `url-connection-client` HTTP client, rather than a hand-rolled REST/SigV4 client. Rationale: SigV4 signing, credential-chain resolution, region/endpoint handling and error modeling are security-sensitive and costly to reimplement and maintain; the concrete capability gap is justified by AGENTS.md. Costs to review: transitive size, blocking IO (isolated by `IO.blocking`), and provenance/license; Security Engineer approves the dependency before merge. Rejected alternative: a SigV4 hand-rolled client (higher defect and security risk).
- Preparation delivers code, config, tests with the stub, and an operations note (required SES verified identity and sandbox exit, least-privilege `ses:SendEmail` permission scoped to one identity, bounce/complaint handling, at-least-once duplicates). It provisions no AWS resource and makes no live call; production activation is a separate gate.

### Failure and recovery cases

| Case | Required behavior |
|---|---|
| Crash after provider confirmed cancel, before DB write | Replay re-issues the same-key `cancel`; the provider reports `AlreadyCancelled`, treated as confirmed; no second effect. |
| Cancel response lost or provider unavailable | Outcome unknown: lookup by key, then retry the same key; slot is not reported released until confirmation; budget exhausted gives visible `RepairRequired`. |
| Proposal declined, withdrawn or expired | Back to `Completed`, old slot untouched, no provider call; the other party is notified. Expiry is durable due work, so it fires after a restart; a late accept returns `PROPOSAL_EXPIRED`. |
| Accept races expiry, withdraw or cancel | Revision CAS: the first committed transition wins; the loser gets `STALE_REVISION` or `NO_OPEN_PROPOSAL`/`PROPOSAL_EXPIRED` with no provider effect. Accept after `expiresAt` is rejected even if the expiry command has not yet run. |
| Cancel while a proposal is open | Cancel wins, proposal cleared, cancel flow runs; a later accept returns `NO_OPEN_PROPOSAL`. |
| Accepted replacement conflicts at the calendar | Old interval and hold stay valid; nothing held; workflow returns to `Completed`; both notified (`RescheduleUnavailable`). |
| Hold confirmed, swap rejected or deadline passed | Cancel the new hold (compensation); if that fails, repair with both holds visible. |
| Swap committed, old-cancel fails | Retry same key; exhaustion enters repair; the new hold already holds the participants' slot. |
| Crash after the cancellation transaction commits, before any provider call | Application is `Rejected` and workflow `CancelPending` with a durable command; the worker resumes on restart; slot is released only after confirmation. |
| Crash after provider cancel confirmed, before the workflow records it | Same-key cancel returns `AlreadyCancelled`, treated as confirmed; no second effect. |
| Cancel transaction fails or loses a race (hire, generic reject, other cancel) | Nothing is written, provider is never called; typed outcome. The application is never `Interview` with a cancelled slot, because the provider is called only after the commit. |
| Provider cancel permanently fails | `RepairRequired` with application `Rejected` and slot still held, visible to Admin and in `progress`; repair resumes the cancel and never reverts the rejection. |
| Generic `rejectApplication`/`hireApplication` on an application with a live interview workflow | Pre-existing gap, unchanged by this scope: those mutations do not touch the workflow, so the slot stays held. Documented known gap and follow-up, explicitly out of scope; no behavior is invented here. |
| Concurrent cancel and reschedule, or duplicate requests | Revision CAS lets one leave `Completed`; the other returns `INTERVIEW_NOT_SETTLED` or `STALE_REVISION`; same-key replay returns the existing workflow. |
| Interval already started, or already cancelled | Typed `INTERVIEW_ALREADY_STARTED` / `INTERVIEW_ALREADY_CANCELLED`, no command issued. |
| Notification crash after provider accept | Resend; duplicate possible, documented (at-least-once). |
| Deleted subject mid-flow | New work is denied by the permanent subject fence; live provider holds are cancelled with confirmation; no notification. |

- Provider effects: cancel is reported released only by the provider's confirmed or already-confirmed answer; every unknown outcome is answered by a lookup of the same key and then the same-key retry; a replacement hold is held before the swap, the swap is a guarded approval receipt (`approveRescheduledInterval`: live application `Interview`, both holds live, old interval not started) followed by the `SwapCommitted` transition that moves the live interval, then the old slot is confirm-cancelled; a refused swap or conflicting hold compensates; informational notifications are looked up first, retried with backoff and, once their budget is spent, repaired per command without changing the workflow phase.
- Admin repair persists the exhausted phase (`repairOrigin`) and resumes it by lookup (never a new cancel, hold or send before the lookup answers), resets the retry budget through the attempt epoch, supersedes the gating intents, and records the actor. `ProposalPending` is not repairable; Admin withdraws the proposal.
- Known gap, unchanged and documented, not fixed: generic `rejectApplication` and `hireApplication` do not touch a live interview slot or workflow.

### Review remediation of the service and executor slice (2026-10-09, local, unreviewed)

Code review failed and security review passed with required fixes; all are addressed below. Nothing here is independently re-reviewed yet.

| Finding | Resolution |
|---|---|
| CODE-HIGH-1: a failed expiry left a proposal open and could starve the claimer | Expiry has no external effect, so every failure path expires the proposal: `InterviewCommands.giveUpEvent` turns an exhausted publication or execution, and a message past the replay window, into `ProposalExpired(now)` (every other step still enters repair). An expiry message that is too early (clock skew) puts its row back to `Pending`, due at its own expiry time, and is acknowledged (not quarantined), so the partition does not restart-loop; because the row is due again as soon as the publisher's clock passes the expiry, a consumer clock that stays behind by more than the skew tolerance republishes it until its clock catches up (bounded by the skew, not a failure). A give-up that expired the proposal marks the expiry row `Superseded`, not `RepairRequired`. If expiry is no longer possible the row alone is marked, so the claim loop cannot spin. `WithdrawProposal` now succeeds after `expiresAt`, so an unexpired-but-late proposal can always be closed; accept and decline stay refused after `expiresAt`. |
| CODE-MED-2: informational notifications were dropped once the workflow entered repair | Informational `Notify` is applicable in every phase (revision-fenced only), and the ledger fence permits it in every phase. Admin repair of the workflow does not touch them; if their own budget is spent they are command-level `RepairRequired` and visible through `notificationRepairs` / `repairNotifications`. |
| CODE-LOW-3: swap deadline | `InterviewCalendarFence.swapDeadline` is the earlier of the old and the replacement start; used by the worker and the repository approval. |

Dismissing a request that was never made returns `NoRescheduleRequest` (`NO_RESCHEDULE_REQUEST`). The found, absent or unknown reading of a lookup is one function in the worker; the two in-memory test repositories keep their separate, small implementations. |
| SECURITY-M1: no-op request flooding | A request whose flag is already set writes nothing: no receipt and no retention update, so a fresh key per repeat grows nothing (repeating is idempotent without a receipt; a key first used for a no-op is not remembered for conflict detection). | SECURITY-M2: a compensated attempt poisoned every later reschedule | `skippedGenerations` on the workflow: a compensated attempt consumes its generation (its cancelled reservation stays stored), the next acceptance holds under `replacementGeneration = generation + 1 + skippedGenerations`, a committed swap makes that the live generation, and the gap locates the retired reservation while the old slot is cancelled (`retiredGeneration`). | SECURITY-M3 | `InterviewCancellationAccessIntegrationSpec` on the real replica set: by direct id another candidate and a non-owning recruiter get `NotVisible` for every action and nothing is written; participants and Admin are refused every action outside their role (Admin cannot accept or decline for the candidate; a forged proposer or cancel initiator is refused); user events from the system and system events from a person are refused. |
| SECURITY-L1 | Propose, accept and request read the application inside the lifecycle transaction, and the swap approval re-reads it, without a guarded write. Accepted risk, recorded: the only effect of write skew against a concurrent hire or reject is a proposal, hold or swap on an application that is no longer `Interview`, which is the known gap already documented (generic reject and hire do not touch a live interview slot); the cancel, which must exclude a concurrent hire, does write the application with a status guard. ### Account deletion checkpoint (2026-10-09, local, unreviewed)

Scope: DHW-30 only. No migration, no new collection, field, cleanup state or command type; the cleanup state machine (Pending, ProducersFenced, MongoPurged, AwaitingRetention, Complete), its validator and the 013/018 cleanup proofs are unchanged.

Finding from the source read: the existing deletion path already fenced the subject on every interview write (claim, publication, result, lifecycle commit, hold, swap approval, delivery, repair all fence candidate, recruiter, scheduler and acting user as Active) and the purge already removed workflow, request receipts, commands, inbox, reservations, receipts and the subject's lock by workflow id. The one real gap was that a live provider hold was deleted locally without any confirmed cancel, which would leak a slot at a real provider (and is not covered by the ledger's own cancel, which a deleted subject is fenced out of).

Implemented:

- `InterviewHoldCanceller` (port): confirms the cancellation of a live hold under its own cancel key. `ledgerOwned` (default; the platform ledger is the provider, so the cleanup's own guarded local release is the confirmation) and `external(calendar)` for a future adapter. `InterviewCalendarKeys.cancellationKeyFor` derives the cancel key from a canonical reserve key.
- `MongoInterviewSubjectCleanup.purge`: for every batch of discovered workflow ids, every unreleased reservation (original, replacement, compensated or retired generation) is paged in identity order and cancelled with confirmation, then marked released locally by a guarded update, before any child or workflow row is deleted. A provider failure fails the purge as `Unavailable`; an unknown reservation fails it as `Conflict` (fail closed, consistent with the open decision above); either leaves all evidence in place and the cleanup state unchanged, so the next sweep retries. A row without a canonical provider identity was never created by a provider call and is purged without a cancel. The lookup uses the reservation identity index.
- Admin is a singleton that cannot delete its account (`SingletonAdminViolation`), so Admin appears only as an actor: Admin-keyed request receipts, repair audit rows and cancel history are covered through the workflow id (receipts, inbox) and the existing rule that committed application history and outbox rows are not touched by interview cleanup.
