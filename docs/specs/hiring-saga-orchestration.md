## Source facts (verified 2026-10-14)

Interview scheduling (`domain/workflow/InterviewScheduling.scala`):

- `InterviewWorkflow.decide(workflow, expectedRevision, event)` (`:207`) checks `revisionMatches` (`:199`: equal revision and not `Long.MaxValue`), returns `StaleRevision` otherwise, calls the private `transition` (`:223`) and bumps the revision by 1.
- `transition` is a total table over `(InterviewWorkflowPhase, InterviewWorkflowEvent)`: `ReservationPending`, `StatusCommitPending`, `CompensationPending`, `NotificationsPending`, plus the terminal `Completed` and `RepairRequired`. Anything else is `InvalidTransition`.
- Unknown outcome moves to a lookup command for the same key (`ReservationOutcomeUnknown` -> `LookupCalendarReservation`); lookup absent re-issues the original command with the same key (`:246-247`, `:256-257`, `:270-271`).
- `RetryExhausted(step)` in a forward phase goes to `RepairRequired`; in `CompensationPending` it goes to `RepairRequired` with `CompensationFailed` (`:250-251`, `:264-265`).
- `StatusCommitRejected` starts compensation: `ReleaseCalendarSlot(s"${id}:release")`; release success goes to repair with `StatusNotCommitted` (`:258-263`). `ReservationRejected` goes to repair without compensation (`:248-249`).
- Stable keys: `reservationKey` (`:161`), `cancellationKey` (`:164`), `notificationKey` (`:203`), release key (`:230`). Commands carry an expected phase and revision (`commandIsApplicable`, `:136`).

Interview lifecycle (`domain/workflow/InterviewLifecycle.scala`):

- `InterviewLifecyclePolicy.decide` (`:126`) uses the same revision rule, then `transition` (`:134`). It mixes actor-initiated events (`Cancel`, `RequestReschedule`, `Propose`, `AcceptProposal`, `DeclineProposal`, `WithdrawProposal`, `ProposalExpired`, `Repair`) with step outcomes. The provider-cancel family (confirmed, lookup confirmed, unknown, lookup absent) is shared by three phases (`cancelOutcome`, `:169`).
- Repair resume (`resume`, `:182`): Admin `Repair` in `RepairRequired` resumes `repairOrigin` by lookup (never by repeating the effect), clears `repairOrigin`, and never reopens a cancelled slot.
- Reschedule compensation: `RescheduleCompensationPending` cancels the replacement hold by its generation key; `skippedGenerations` makes the next attempt use a fresh generation (`:117-121` of `InterviewScheduling.scala`).
- Informational notifications never move the workflow phase: failure retries, then command-level repair (`InterviewNotificationSettlement`, `service/port/InterviewWorkflowRepository.scala:76-83`).

Forward-only cleanup (`domain/workflow/InterviewSubjectCleanup.scala`):

- `decide` (`:107`) walks `Pending -> ProducersFenced -> MongoPurged -> AwaitingRetention -> Complete` with a revision, and has no compensation: erasure cannot be undone. `command` (`:99`) derives the next command from the state.

Application and persistence:

## Decision record

- Status: accepted by the user, 2026-10-14.
- Context: four workflows implement the same ideas (revisioned pure decision, unknown outcome -> lookup, retry budget, compensation, repair) by separate tables and separate workers. The idea is correct but repeated; each new workflow re-derives the rules.
- Options considered:
  1. Keep per-workflow tables (the documented default; existing `StateT`/named-decision approach). No risk; repetition remains.
  2. Generic engine with a step catalogue (chosen). The generic rules live once; each workflow supplies only its steps and graph.
  3. Event sourcing or a workflow framework. Rejected: new storage model, migration, much larger.
- Tradeoffs accepted: a generic layer over existing, working code; risk of silent behaviour drift (managed by golden tables); some workflow-specific behaviour (actor-initiated proposal events, notification rounds, lease-based erasure persistence) must stay in definitions rather than the engine.
- Evidence required: golden tables identical before and after (SAG-01, SAG-04), all existing workflow/recovery integrations green (SAG-07).
- Revisit trigger: more than a small number of existing transitions cannot be expressed without definition-specific escape hatches (see SAG-09 decision gate), or the engine cannot compile on both Scala versions if analytics sharing is revived.

## Design

### Pure engine (`domain/saga`)

- `SagaDefinition[Phase, Event, Command]`: a pure value describing a workflow type.
  - `steps: List[SagaStep]`, the step catalogue. A `SagaStep` has: `name`, `idempotencyKey` (a pure function of the instance and step), `undo: StepUndo`, `retryBudget`.
  - `StepUndo` is `Compensate(step: SagaStep)` or `Irreversible(reason: String)`. A step must declare one; there is no default.
  - `graph`: for each non-terminal phase, the step run in it and the phase after each generic outcome.
  - `triggers`: workflow-specific, actor-initiated events (for example `Cancel`, `Propose`, `Repair`), each a pure function of the instance and the event.
- `SagaInstance[Phase]`: `id`, `revision: Long`, `phase`, `status: SagaStatus`, `repairOrigin: Option[Phase]`, plus the workflow's own payload. `SagaStatus` is `Running | Compensating | Completed | RepairRequired`. Persisted shapes keep today's phase names (`InterviewWorkflowPhase`, `InterviewCleanupState`, `ErasurePhase`); the status is derived from the phase by the definition, not stored as a new field.
- `StepOutcome` (generic): `Confirmed`, `Rejected`, `OutcomeUnknown`, `LookupFound`, `LookupAbsent`, `RetryExhausted(step)`. Each definition maps its existing events to these (for example `ReservationOutcomeUnknown` -> `OutcomeUnknown`) without renaming the events.
- `SagaEngine.decide(definition, instance, expectedRevision, input): Either[SagaError, SagaDecision]` owns, once:
  1. the revision compare-and-set rule (`revision == expected && expected != Long.MaxValue`, else `StaleRevision`) and the `+1` bump;
  2. `OutcomeUnknown` -> emit the lookup command for the same idempotency key, stay in the phase;
  3. `LookupAbsent` -> emit the original command again with the same key, stay in the phase;
  4. `RetryExhausted` -> `RepairRequired` with the exhausted reason, whatever the step's undo; inside a compensation step: `RepairRequired` with the compensation-failed reason (spec correction 2026-10-14, driven by the characterization tables: exhaustion never enters compensation);
  5. a rejected step with `Compensate` runs the declared compensation; a rejected step with nothing to compensate goes to `RepairRequired` (as `ReservationRejected` does today);
  6. admin repair resumes `repairOrigin` by lookup of the same key, clears `repairOrigin`, and never re-opens a compensated or cancelled effect;
  7. any pair not in the graph is `InvalidTransition`.
- All of this is pure: no clock, ID, I/O or logging. Time and IDs are inputs.

### Application layer (`service/saga`, over `F[_]`)

- `SagaStore[F[_], Phase]` port: `load(id)` and `advance(next, expectedRevision, cause, commands, now) -> F[SagaAdvanceResult]` where `SagaAdvanceResult = Applied | Duplicate(existing) | StaleRevision`. The store applies state, inbox receipt (`cause`) and emitted commands in one transaction; it enforces step and message uniqueness, revision CAS and fencing. This is exactly the existing `InterviewWorkflowAdvanceResult` contract.
- `SagaCommandDispatch[F[_]]`: sends one step's command through the existing command queue and receives its outcome; owns lease/fencing and publication. It wraps `MongoInterviewCommandQueue` behaviour; it does not change command states.
- `SagaOrchestrator[F[_]: Temporal]`: receives an outcome, loads the instance, derives the `StepOutcome` and attempt count, calls `SagaEngine.decide`, calls `SagaStore.advance`, and returns `Applied | Duplicate | StaleRevision | Quarantined`. It sequences effects only; no business decision lives here. Capabilities: `Temporal` for backoff and timers; `Concurrent` is not needed.
- Mongo adapters implement `SagaStore` and `SagaCommandDispatch` over the existing collections and documents. There is no new collection, field or index. The existing codecs (`MongoInterviewWorkflowCodec`, `MongoInterviewWorkflowLifecycleCodec`, `MongoInterviewWorkflowCommandCodec`, `MongoInterviewCleanupSweepCodec`) stay the stored shapes.

## Rules

1. **Behaviour is frozen first.** Before any port, the current `decide` output for every reachable `(phase, event)` pair is captured as a golden table (new revision, new phase, `notified`, `repairOrigin`, commands in order with their keys and messages, or the error). The tables are committed before the engine exists. After porting they must be identical.
2. **One revision rule.** The engine is the only place that compares and bumps revisions. Definitions never touch `revision`.
3. **Every step declares its undo.** A missing declaration does not compile. `Irreversible` carries a reason string recorded in the catalogue, not in stored data.
4. **Same key on retry and lookup.** Retries and lookups reuse the step's idempotency key; a compensation has its own stable key. No key changes, and no new key is invented for repair.
5. **Compensation is bounded.** A compensation has a retry budget; its exhaustion goes to `RepairRequired` with the compensation-failed reason, never an infinite loop and never silent.
6. **Repair never repeats an effect blindly.** It resumes by lookup.
7. **No data migration.** Stored documents, phase names, command names, indexes and Kafka messages are unchanged. A rolled-back application reads the same data.
8. **Authorization stays in services.** Actor checks, participant predicates and Admin-only repair stay in the application services and repository predicates exactly as today. The engine receives only trusted inputs; it never reads actor identity from a caller-supplied ID.
9. **Cleanup and erasure stay forward-only.** The engine never emits a compensation for an `Irreversible` step.
10. **Domain stays free of infrastructure.** `domain/saga` does not import Mongo, Kafka, JSON, GraphQL or Spark.

## Unknowns

- Whether every existing transition fits the generic rules. Known edge cases: actor-initiated lifecycle events (`Propose`, `AcceptProposal`, `ProposalExpired`), notification rounds with a `notified` set, informational notifications that never move the phase, and `ReservationRejected` going to repair without compensation.
