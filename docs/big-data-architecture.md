# Hiring Analytics Architecture

[Runtime reliability](specs/hiring-security-and-runtime-reliability.md) reconciles uncertain mutex acquisition only for its original owner, using majority reads and bounded retries; unresolved ownership still requires manual recovery. Report receipt compaction checks candidate pages of at most 500 against all lineages and active replay dependencies under the existing mutex, rechecks report controls transactionally and deletes at most 1,000 per pass. Memory is bounded; scan duration is not fixed. DNS preflight is effectful and runs on the blocking boundary.

The [architecture wiki](wiki/README.md) connects analytics to hiring use cases; its [storage page](wiki/mongodb-and-analytics.md) inventories MongoDB control collections and Delta datasets.

## Producer retirement and erasure checkpoint

The [reliability specification](specs/hiring-retrieval-publication-reliability.md) tracks the current cross-build contract. Analytics erasure requires completed operational migrations `012_attributable_producer_registrations` and `036_producer_generation_registrations` (generation-keyed rows) and the `producer_registrations` collection before readiness (`MongoAnalyticsErasureQueue`). The pre-MVP active contract uses registry-backed deletion requests; it has no legacy fallback. Stop incompatible operational and analytics writers before cutover.

Erasure fences and checkpoints bounded producer batches before advancing barriers or physical cleanup. Active producer attribution has no TTL. Failed broker fencing retains pending work. Erasure reads a subject's Active producer generations (transactional id plus generation id), fences the transactional ids on the broker, then marks Fenced only the generation rows it read, so a replacement generation that registered after the fence stays attributed. Operator retirement takes a cut-off time, fences the transactional id, then marks Fenced the Active rows registered before the cut-off (`MongoProducerGenerationMaintenance`). Existing analytics retention and physical deletion gates remain required; operational success alone does not prove lakehouse erasure.

Account-deletion recovery runs through `scripts/run-local-tests.sh recovery` using manifest-verified test services, generated database/topic namespaces, synthetic keys and a Resource-owned local API process. It does not use developer `.env`, application databases or durable proof directories. [Search/publication reliability](specs/hiring-search-publication-reliability.md) owns the new local recovery evidence; deployed erasure gates remain separate.

## Kafka topic contract

Local topics are created by `docker/kafka/provision-access.sh` (Compose) and by the `initialize` service of `compose.test.yaml`. Production values are recommendations for an infrastructure-as-code definition outside this repository; they are not verified here.

| Topic | Key | Partitions (local / production recommendation) | Replication, min ISR (local / production) | Retention, segment | `max.message.bytes` | Creation owner |
|---|---|---|---|---|---|---|
| `hiring.operational-events` | aggregate id | `KAFKA_TOPIC_PARTITIONS`, default 1 / 6 | 1, broker default / 3, 2 | 7 d (`retention.ms` 604800000), 1 d (`segment.ms` 86400000) | 1048576 | `provision-access.sh` locally; infrastructure as code in production |
| `hiring.interview-commands` | workflow id | same variable, default 1 / 3 | 1, 1 / 3, 2 | 7 d, broker default segment | 65536 | same |
| `hiring.interview-results` | workflow id | same variable, default 1 / 3 | 1, 1 / 3, 2 | 7 d, broker default segment | 65536 | same |

The broker's `transaction.max.timeout.ms` (default 900000) bounds the producer transaction timeout the application derives from its lease, so a publisher lease or interview claim window is capped at 905 s in configuration.

Rules: consumer `partition-concurrency` is bounded by the partition count, so the local value of 4 is only effective with 4 or more partitions. `--if-not-exists` never changes an existing topic, so a new partition count applies only to a topic created after the change. Raising a partition count remaps keys to partitions and the erasure barriers cover only the partitions present when they were captured, so it is an operator procedure: drain erasure work and stop producers first. Retention plus segment roll is the deduplication window the consumer receipt must outlive.

## Boundary

MongoDB remains the operational source of truth. Kafka carries immutable operational events to the local analytics runtime; no GraphQL mutation waits for Spark, Delta, or an analytics projection.

The current local event contract is the seven-field `hiring.operational-events` JSON envelope implemented in `OperationalEvent.scala`, schema version 1 carried in the `hiring-schema-version` record header (absent means 1). Analytics consumes event-specific minimized payloads: job identity/skills/status, application identities/status transitions, and bounded search result identities/ranks/scores. Query text, private filters, job descriptions/requirements/location, feedback and decline reasons are excluded. Minimization is enforced at the producer: typed constructors and the exact encoder emit only the known keys. Readers are tolerant (`OperationalEventWireCodec`, `OperationalEventTransforms.withValidity`): unknown additive keys are ignored, while missing or mistyped known keys, repeated keys, inconsistent identities, invalid ranks, nonfinite scores, a disagreeing header and a version other than 1 are invalid; Spark applies the same rules with native expressions (one known difference: the Circe reader rejects a repeated key at any nesting depth, while Spark checks the envelope, payload, job and result-entry levels, so a repeated key inside an unknown nested object is rejected by the application and accepted by Spark) and quarantines with `INVALID_OPERATIONAL_EVENT_ENVELOPE` or `UNSUPPORTED_SCHEMA_VERSION`. Headers are read (`includeHeaders`) but never written to Bronze, Silver or quarantine, and the event fingerprint stays the SHA-256 of the value bytes, so a resend with different headers is still the same event. Values are bounded to 256 KiB, with a 1 MiB producer/topic ceiling. The evolution rules are in [schema evolution](schema-evolution.md#operational-event-evolution-policy).

Operational facts carry event-time semantics and may be published out of order. A four-claim publication wave renews every lease before and during one Kafka transaction that carries all its records (see [Kafka flow contracts](../ARCHITECTURE.md#kafka-flow-contracts)); fs2-kafka owns native transaction serialization. The operational consumer records a consumer receipt by a unique Mongo insert before it commits an offset; a duplicate key means the event is already handled, and the receipt must outlive the topic's retention plus segment roll ([duplicate delivery containment](specs/duplicate-delivery-containment.md)). Quarantine must also be durable before progress. Workflow revision/inbox ordering remains separate from analytical fact ordering.

Streaming event-time admission (OPEN; CLOSED for an event in a UTC day already closed by the watermark; FUTURE for an event more than 5 minutes ahead of the observed instant, or with no event time) is the built-in Spark expression `EventTimeAdmissionExpression`, not a UDF. It uses epoch-microsecond arithmetic that does not depend on the session time zone, and `EventTimeAdmissionExpressionSpec` proves it equal to `AnalyticsEventTimePolicy.admit` over generated and boundary inputs. The CLOSED boundary is the durable watermark, which trails the greatest admitted event time by the typed `analytics.streaming.allowed-lateness` (default 24 hours, 1 hour to 7 days, part of the streaming activation identity), so a fact is tolerated for one to two allowed-lateness periods depending on its position in its UTC day. The effective tolerance can therefore reach about twice the configured lateness (up to 14 days at the 7-day maximum) while Bronze keeps 7 days, so replaying a very late fact may depend on Kafka retention rather than on retained Bronze. A CLOSED fact is stored only in the late-fact dataset and a FUTURE fact only in quarantine; each ingest logs `STREAMING_EVENT_TIME_ADMISSION closedDay=N future=N allowedLatenessMillis=M batch=<id> generation=<g> revision=<r>` (taken from the batch's publication reservation, which exists even when the batch ends quality-blocked or erasure-pending), and a closed-day fact missed by a published generation is corrected by explicit operator replay, which publishes a newer revision of the pinned report generation (`generation`, `revision` and `runId` are recorded in the Mongo snapshot and the replay journal).

## Implemented Local Lakehouse

```text
Kafka retained range -> Bronze -> Silver -> Gold -> Mongo analytics projection -> Admin GraphQL
```

- The batch module reads an explicit, bounded Kafka offset range, preserves Kafka record coordinates, parses analytical facts, deduplicates, and quarantines malformed/conflicting input. A quality-blocked range cannot advance Gold or the published Mongo snapshot. K=10 suppression is checked per output cell using distinct pseudonymized subjects; it is not a formal anonymity guarantee. See the [implementation specification](specs/hiring-analytics-lakehouse.md) for exact metric, retry, and acceptance contracts.
- The batch driver uses Scala 3.7.4 with Spark/Delta's Scala 2.13 artifacts. Cats Effect owns one bounded driver executor for synchronous Spark/Delta and Kafka client calls, including client creation and close. Spark actions run in per-operation job groups that are canceled when their owning effect is canceled; Kafka calls retain their configured request/API timeouts. A Scala 3.9 driver compiled but failed a local Spark runtime check because Spark's 2.13 reflection requires the older standard library.
- The standalone `analytics` build uses `domain` for pure contracts, ranges, retention rules, key-retirement evidence, pseudonymization, and digest helpers; `errors` owns the shared `AnalyticsError`; and `config` decodes HOCON with PureConfig into one section per command (batch, erasure worker, streaming, late-fact replay, key-retirement audit). Independent settings accumulate as `ValidatedNec` problem lists carried by `AnalyticsError.InvalidConfiguration`; the HMAC key ring is validated once into a `SubjectPseudonymizer`. `service.batch`, `service.erasure`, `service.streaming` and `service.keyretirement` hold use-case ports and policies, and `app` wires the runtimes (including `StreamingMaintenanceTick` and `StreamingBatchPreparation`). Spark-coupled batch/erasure workflows live in `adapter.spark`, Kafka readers and fencing in `adapter.kafka`, and Mongo repositories and reactive-stream bridges in `adapter.mongo`. Mongo persistence uses typed mongo4cats collections and Circe codecs over the reactive driver, with strict BSON numeric-width and malformed-record validation; raw BSON remains at query/update and fidelity-sensitive audit boundaries. Production `IOApp` entry points are exposed from `cli`; local HMAC retirement proof and authorization commands are test-scoped and run with `Test / runMain`. Dockerfiles and operator scripts use the corresponding command names. These namespaces sit in one SBT project, so package visibility narrows access where useful but does not enforce the complete dependency graph.
- Delta Bronze, Silver, quarantine, Gold, and run-manifest datasets are written beneath a caller-selected local lakehouse root. The opt-in `analytics-batch` Compose profile persists that root at `.local/data/analytics/`.
- Every Delta table is declared once in `AnalyticsDeltaCatalog` as a `DeltaTableSpec`: ordered columns with real nullability, named CHECK constraints, table properties, the statistics allow-list and the subject-attributed classification. The 13 tables are Bronze, quarantine, Silver, late facts, application stage times, the four Gold tables (funnel, time to hire, hiring stage durations, job skills), run manifests, streaming progress and decisions, and the HMAC key registry. The target is validated strictly: column names, types (including nested nullability), top-level nullability, the exact `delta.constraints.*` set and, for subject-attributed tables, the exact statistics allow-list with no positional `delta.dataSkippingNumIndexedCols`. Any difference raises `DeltaSchemaMismatch`. Source frames are validated loosely (names and types), and Delta enforces NOT NULL and CHECK at write time. The CHECK constraints are: event and aggregate types limited to the domain wire values; a valid new status or none; non-negative Kafka partition and offset; expiry after ingestion; stage-time expiry after the terminal instant; non-negative counts; ordered percentiles; the five stage-duration metric names; at least 10 on a stage-duration `eligibleCount` (K=10); and the run-manifest status and offset order.
- Constraints are added after the table is created, with `ALTER TABLE ... ADD CONSTRAINT`, so creation and constraint registration are separate Delta commits. A crash between them can leave an empty table without some constraints. Create-or-validate completes exactly that case (columns equal, stored constraints a subset of the declared ones, no data files) and fails closed for any other difference.
- Gold writes create or validate the target and then overwrite data only, without `overwriteSchema`, so a drifting Gold schema fails instead of being replaced; Gold `day` is a UTC `DATE`. Array elements stay nullable because Delta cannot enforce NOT NULL there, and lambda constraints are avoided because Delta does not round-trip them.
- **Parse and tokenize once.** The batch's parsed frame (`OperationalEventTransforms.analyzed`) carries `isValidEvent`, `eventFingerprint`, `subjectToken` and `subjectTokens`, each computed once. Bronze, quarantine, conflict detection and Silver read those columns, and each transform keeps a column that is already present. The envelope is parsed into a VARIANT once; the raw-JSON extractions and key-set checks that VARIANT cannot express run once per batch, and the parse intermediates are dropped before the frame is persisted. Subject tokens come from a deterministic Scala UDF (`AnalyticsSubjectPrivacy.SubjectTokenFunction`) that creates one HMAC tokenizer per Spark task. The HMAC key is never written to a DataFrame, log, manifest or Delta table.
- The batch materializes deletion markers and verifies/registers HMAC key continuity before reserving a generation/revision; that reservation precedes analytical dataset and run-manifest mutation. It writes bounded Gold results into MongoDB with compare-and-set publication and records a `PUBLISHED` manifest only after Mongo confirms the snapshot. Active erasure markers keep the report hidden and make the batch emit `ERASURE_PENDING`.

The first batch metrics are systemwide lifecycle transition activity, time-to-hire percentiles, per-stage hiring durations, and job-created skill posting activity. Time to hire and the stage durations are computed from `silver/application_stage_times` (one row per application, earliest time per status, kept 30 days after a terminal status or 180 days after the last event of an open application), so hires later than the 30-day Silver retention still count; both are suppressed below 10 distinct candidate subjects. `CANDIDATE_HIRED` is not a second lifecycle fact; it remains available for its own event use cases. Recruiter, job, and location enrichment are deferred until an event-time dimension policy exists.

**Application stage times.** `silver/application_stage_times` has one row per `applicationId`: the earliest time the application entered each status (`createdAt`, `acceptedAt`, `declinedAt`, `interviewAt`, `hiredAt`, `rejectedAt`), `lastEventAt`, the candidate `subjectToken` (set when the row is created and never updated) and `subjectTokens` (candidate and actor tokens). Batch, streaming and late-fact replay each pre-aggregate their lifecycle facts per application and MERGE them on `applicationId`: a stage keeps its earliest time, `lastEventAt` its latest, and the tokens their union. `terminalAt` (the earliest of declined, hired and rejected) and `expiresAt` are recomputed from the merged row: the terminal instant plus `stage-times-terminal-days` (default 30), or, for an open application, the last event plus `stage-times-open-days` (default 180). Both are configured between 1 and 3650 days. A matched row is rewritten only when a stage, the last event or the token set changes. The stage times are merged before Silver in the same batch, so a crash between the two commits leaves Silver as a subset that the idempotent replay repairs. `CANDIDATE_HIRED` is not a lifecycle event here. The table is backfilled from Silver only when it does not exist and Silver does, leaving out applications that name an active deletion marker. An existing table, even an empty one, is never backfilled.

**Hiring stage durations.** `gold/hiring_stage_durations` has one row per metric (`TIME_TO_ACCEPT`, `TIME_TO_INTERVIEW`, `TIME_TO_HIRE`, `ACCEPTED_TO_INTERVIEW`, `INTERVIEW_TO_HIRE`) with P50, P75, P90 and P95 hours and `eligibleCount` as distinct candidate subjects. Only applications with both stages present and a non-negative duration count, so an application that skipped a stage contributes to no metric that involves it. A metric with fewer than 10 subjects is omitted. Time to hire and the stage durations are rebuilt from the stage-time rows that have not expired at the report's as-of instant. When the stage-times table is absent, both are cleared, whether or not Silver exists. The report carries the rows as `stageDurations`.

## Erasure and limits

Account deletion writes a durable erasure request, account tombstone, and recruiter job-close events in the receipt-owned Mongo transaction, then returns a durable random receipt in `PENDING`. The `accountDeletionStatus(receiptId)` query requires a verified token belonging to the receipt owner and returns only that owner's `PENDING`, `COMPLETE`, or `NOT_FOUND` status; a still-valid token remains usable after the account is tombstoned. The separate `analytics-erasure` Compose profile runs a resource-managed worker. It waits for a deleted subject's publisher fence and bounded Kafka send timeout, purges subject-attributed outbox rows, records a Kafka end-offset barrier, purges attributed Delta rows (whole un-attributable datasets), and rebuilds Gold. It keeps the report hidden while the broker's earliest offsets pass the barrier and the configured Delta vacuum and log-retention horizons pass, then verifies the surviving Delta snapshots, rebuilds/publishes the bounded report, and atomically marks the request complete with its non-TTL completion ledger, deleting that request's per-file `analytics_erasure_delta_files` evidence (read through the analytics-owned `analytics_erasure_delta_files_request_v1` index) in the same transaction. That delete is bounded by the configured erasure-evidence cap (`maximum-erasure-evidence-files`, the same bound as the bulk write in `persistDeltaFiles`); revisit batching it if the completion transaction times out or the cap is raised. Markers remain active for the configured number of days after completion. Runtime defaults and environment overrides for analytics retention horizons, report reservation expiry, Mongo transaction duration, evidence limits, publisher buffering, and erasure-worker lease, delivery-timeout, and poll timings are defined under `analytics.operational` in `application.conf`. The default Delta vacuum horizon is seven days; configuring a shorter horizon disables Delta's built-in seven-day safety check, as required for the configured shorter horizon to take effect. The default Delta log-retention horizon is 14 days (`delta-log-retention`, env `ANALYTICS_RETENTION_DELTA_LOG_RETENTION`), reconciled onto existing tables at every start; it was 30 days before the [completion-window specification](specs/analytics-erasure-completion-window.md) (AEC-02, AEC-03).

Erasure completion budget: `erasure-completion-budget` (default 21 days, env `ANALYTICS_RETENTION_ERASURE_COMPLETION_BUDGET`) is the configured upper bound on the time from the Delta purge to verified physical erasure, derived from the retention horizons. The worst case is the maximum of three terms: `kafka-retention + kafka-segment-roll` (defaults 7 d + 1 d = 8 d, env `ANALYTICS_RETENTION_KAFKA_RETENTION` and `ANALYTICS_RETENTION_KAFKA_SEGMENT_ROLL`; this term is also the readable age of raw Kafka records, which the consumer receipt TTL of 9 days must outlive), one UTC day plus `delta-log-retention` (1 d + 14 d = 15 d), and `delta-vacuum-safety` (7 d). With defaults the worst case is 15 days, set by the Delta log term; the Kafka term is 8 days. Startup configuration decoding fails with the problem "worst-case erasure completion <computed> exceeds erasure-completion-budget <budget>" when the worst case exceeds the budget, and with "erasure-completion-budget <budget> exceeds the one-month response period 30 days" when the budget itself is above 30 days. The erasure worker logs the computed worst case and the budget once at start. The Kafka terms are configured estimates used only for this check; the runtime gate still reads the broker's actual earliest offsets against the captured barrier. The pure rule is `ErasureCompletionRule` (`deltaDeadline`, `worstCaseCompletion`). The retention of `silver/application_stage_times` (30 days after a terminal status, 180 days after the last event of an open application, by default) does not enter this budget, because erasure deletes rows by subject token rather than waiting for expiry.

The Delta log deadline is the start of the UTC day after the purge plus the log retention. Delta truncates the log-cleanup cutoff to a UTC day and removes expired logs only after a checkpoint, so a purge late in the day still waits for the next day. The worker's reclamation recheck interval is `reclamation-recheck-interval` (default 5 minutes, env `ANALYTICS_ERASURE_RECLAMATION_RECHECK_INTERVAL`), no longer a literal.

Motivation: GDPR Article 17 requires erasure "without undue delay", and Article 12(3) allows one month to respond to a request. The budget keeps the default worst case inside that period for the local configuration. The trade-off is that the 14-day log window limits Delta time-travel and rollback to 14 days. Local tests do not prove deployed horizons; every production gate in this document still applies.

Raw Kafka records cannot be selectively deleted and expire on broker retention. Erasure remains active through the publisher fence/drain, the captured broker retention barrier, the configured Delta data-file safety horizon, and the configured Delta log-retention horizon. Bronze and quarantine are classified `PseudonymousSubjects`, and every subject-attributed table sets `delta.dataSkippingStatsColumns` to an explicit allow-list of non-subject columns (and no `delta.dataSkippingNumIndexedCols`), so tokens never enter Delta transaction-log statistics; see the file layout and compaction paragraphs below. Bronze persists only Kafka coordinates and timestamp, event identity and type, occurred-at, aggregate type and ID, `eventFingerprint` (SHA-256 of the envelope bytes, used for replay and coordinate-conflict checks), application and job identities, new status, job skills, subject tokens and retention timestamps. It holds no raw envelope (`rawValue`), actor ID, payload, raw candidate ID, or search result IDs, ranks and scores. A Bronze table with the earlier shape fails closed with `DeltaSchemaMismatch`; pre-MVP the exact local lakehouse is reset explicitly, with no migration. `delta.enableDeletionVectors` is set to `false` on every managed table; a table where it is `true` fails closed, because deletion-vector rows need `REORG TABLE … APPLY (PURGE)` before VACUUM. Rewrite plus VACUUM remains the physical removal path. Raw subject identifiers still exist in Kafka (seven-day retention with a one-day segment roll, so a record stays readable for at most eight days, also on a topic that receives no further appends: the broker rolls a new segment and deletes the expired one, verified on `apache/kafka:3.9.2`), the outbox, the erasure request and completion collections, subject fences and the account tombstone; no Delta table holds them. Legacy log files are checkpoint-cleaned and verified absent before completion.

**File layout and statistics.** Bronze, quarantine, Silver, late facts and the application stage times are subject-attributed. Each sets `delta.dataSkippingStatsColumns` to an explicit allow-list and no `delta.dataSkippingNumIndexedCols`, so Delta gathers min/max statistics only on: Bronze `topic, partition, offset, occurredAt, ingestedAt, expiresAt`; late facts the same plus `eventId`; Silver `eventId, occurredAt, ingestedAt, expiresAt`; quarantine `topic, partition, offset, expiresAt`; stage times `lastEventAt, terminalAt, expiresAt`. Token columns (`subjectToken`, `subjectTokens`) and the raw identifiers `aggregateId`, `jobId` and `applicationId` can never be listed. The stored list must equal the declared list exactly. A table with a different list, a positional `dataSkippingNumIndexedCols` or a forbidden column fails create-or-validate with `DeltaSchemaMismatch`; pre-MVP the local lakehouse is reset. Delta 4.4.1 OSS honors the property on path-based tables (the AC-04.1 test checks the `_delta_log` add-action `stats`). Statistics only prune a MERGE when the condition carries literal bounds, so the Bronze and late-fact coordinate merges add per topic-partition offset bounds taken from the source batch (`MergeKeyBounds`), built with the Column API so that a topic name is a literal value. The match result is unchanged, and a batch with more than 256 topic partitions keeps the plain condition. Merges keyed on random identifiers (Silver `eventId`, `quarantineId`, and `applicationId` in the stage times) still read every file: random keys overlap every file's min/max range, and `applicationId` is on no allow-list.

**Compaction and the erasure horizon.** The streaming maintenance tick runs `OPTIMIZE` on each subject-attributed table (the five above; control and Gold tables are not compacted) once `analytics.streaming.optimize-interval` has elapsed since the table property `analytics.lastOptimizedAt`. The default is 6 hours (`ANALYTICS_STREAMING_OPTIMIZE_INTERVAL`); `0` disables compaction, and any other value must be at least `maintenance-interval`. The run holds the lakehouse mutex, precedes the vacuum step, and is skipped while an erasure request is pending or processing. A run first sets `analytics.optimizePendingAt`, then records `analytics.lastOptimizedAt` (scheduling time), `analytics.lastOptimizeCompletedAt` (wall-clock time after the commit) and `analytics.lastOptimizeCompletedVersion` (the table version the run produced), and removes the pending marker. It logs `DELTA_COMPACTION table=<name> filesBefore=<n> filesAfter=<m>`, which carries counts and no tokens. If compaction fails, the tick logs `DELTA_COMPACTION_FAILED` with the error class only and continues with vacuum and authorization.

The files `OPTIMIZE` replaces still hold subject tokens until VACUUM. The erasure worker therefore starts the Delta data-file horizon at the later of the purge and the latest `OPTIMIZE` completion across the subject-attributed tables. It reads the recorded completion time and version, then the table history after that version, so an `OPTIMIZE` run by hand later also extends the horizon. It reads the full history when the pending marker is set (a crash or a run in progress), when the completion time or version is missing or unparsable, or when the recorded version is ahead of the table snapshot. The horizon is the later of two instants: the vacuum safety after the anchor, and the start of the UTC day after the anchor plus the Delta log retention. The scheduled tick cannot start an `OPTIMIZE` during an erasure, but `erasure-completion-budget` does not model an `OPTIMIZE` run by hand after a purge, so such a run can move the horizon past the budget.

**Statistics repair.** Batch ingestion and the maintenance tick's table configuration refuse a subject-attributed table whose statistics properties drifted, including a positional `dataSkippingNumIndexedCols`, because create-or-validate runs first. The erasure, purge and reclaim paths (`configureRawTablePrivacy`) remove such a property and log one `DELTA_STATS_PROPERTY_REPAIRED table=<name>` WARN line per table. Files written while the property was set keep their statistics in the log until a purge or `OPTIMIZE` rewrites them and the log checkpoint ages out; the repair only stops new ones.

Marker exclusion is two equality joins: a semi join finds the rows whose `subjectTokens` contain an active marker, then an anti join removes them by their Kafka coordinate (the event ID for a frame without one). It may shuffle event rows into the private `spark.local.dir`.

Publication after erasure (D3): the marker port returns `ActiveDeletionMarkers(exclusionTokens, erasureInProgress)`. A `Complete` marker still excludes replayed or late events at ingestion, batch, streaming, late-fact replay and maintenance purge, but it no longer blocks publication. Only `Pending` and `Processing` requests set `erasureInProgress`, hide the report and produce `ERASURE_PENDING`. The worker logs a sanitized backlog line (`erasure backlog: pending=<n> processing=<n> oldestRequestedAgeHours=<h> phase=<p>`) without identifiers whenever the counts or oldest phase change or `backlog-log-interval` (default 1 hour, env `ANALYTICS_ERASURE_BACKLOG_LOG_INTERVAL`) has elapsed; a failing backlog query only produces a warning and never stops the worker. The repair CLI `inspect` prints `receipt=<receiptId>` instead of the subject UUID, and `requeue` takes that receipt ID. `docker/kafka/provision-access.sh` declares explicit `cleanup.policy=delete`, `retention.ms=604800000` and `segment.ms=86400000` (one day) on the operational topic, matching the `kafka-retention` (7 days) and `kafka-segment-roll` (1 day) settings the budget check uses; the `KAFKA_LOG_RETENTION_HOURS=168` broker setting remains the fallback for topics without explicit configuration. A deployed broker's topic settings are an operator responsibility and are not proven by local evidence. A permanent Deleted-account tombstone denies delayed/manual outbox replay, and generation-guarded snapshot publication prevents a stale run from restoring a hidden report. New analytics rows emit only the active HMAC primary token; erasure matching retains aliases for configured retiring keys so old rows can still be purged. HMAC material must be at least 32 random bytes. A non-TTL Delta control registry anchors each key ID to a domain-separated HMAC verifier; changing key material without changing its ID fails before report reservation. Before full MVP, preserve current-key continuity; if stored registry entries exist, any missing key entry fails closed. Local implementation closure uses accelerated physical erasure proof and simulated-clock boundary tests. Guarded old-key retirement, its real-horizon proof, and a new-key-only restart remain operational activation gates; key removal stays unsupported until those gates pass. Before full MVP, API and analytics schema changes are direct changes without migrations, backfills, or legacy compatibility. Existing lakehouses without trustworthy anchors fail closed; reset/rebuild only the exact local lakehouse when explicitly in scope. Production batch, erasure, and key-retirement audit entry points share a Mongo mutex row keyed by a hash of the normalized lakehouse URI. The row has no TTL or automatic takeover; after a crash, an operator must stop and verify all old owners before deleting the matching row from `analytics_lakehouse_mutexes`. After the existing operator lock-recovery procedure, maintenance inventories abandoned `control/purge-rewrite-<UUID>` copies under the mutex, bounds discovery, rejects unsafe paths, removes recognized copies, and verifies absence before continuing. Read-only key-retirement audits reject unresolved copies. Driver cancellation retains ownership until running work finishes. The mutex does not exclude unmanaged Delta writers. Cleanup and key retirement require inventorying and stopping every writer, plus effective storage-access revocation where the deployment supports it; otherwise retirement remains blocked. The current transactional publisher uses a distinct `hiring_publisher_v2` SASL identity. ACL initialization grants it topic/idempotence/transactional-ID rights and removes those rights from the legacy `publisher` identity; old publisher processes must be stopped before this revocation. A scoped authenticated Compose check verifies current publisher sends/fencing, rejects legacy publisher writes and transaction initialization, verifies invalid fencer credentials fail closed, and denies reader writes/fencing. ## Local interview streams

`hiring.interview-commands` is produced by the orchestrator and consumed by `hiring-interview-workers`; `hiring.interview-results` is produced by workers and consumed by `hiring-interview-orchestrator`. Topic ACLs separate these principals. Both use workflow keys, one local partition, replication/minimum ISR one, delete cleanup, seven-day retention and 64 KiB records. The operational seven-field analytics envelope is unchanged; analytics does not interpret workflow commands as hiring facts. Sequential processing stops/restarts on an undurable record before any later offset is acknowledged. Interview publication uses initialized transactional generations and read-committed consumers. Separate command/result principals own their transactional prefixes; a dedicated fencer can fence those prefixes but cannot write either topic. Mongo authorization registers the generation before send and deletion traverses all attributable generations through bounded registry pages. Interview deletion captures both topic barriers after broker-confirmed fencing and Mongo purge and waits for physical retention, in addition to existing analytics deletion. Old nontransactional publishers must lose write credentials before maintenance cutover. Local redundancy and accelerated checks do not establish deployed retention or production availability.


Operational Kafka null values are explicitly represented at the adapter boundary and quarantined with `MalformedEnvelope`, reason `null event envelope`, and non-null empty bytes. Empty non-null payloads retain the separate `malformed event envelope` reason. Quarantine persistence must succeed before offset acknowledgment; failed persistence prevents later offsets in that partition from advancing. Follow-up raw Mongo and broker recovery evidence belongs to [retrieval and publication reliability](specs/hiring-retrieval-publication-reliability.md#account-erasure-and-recovery-follow-up).
