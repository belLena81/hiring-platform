# Hiring Analytics Architecture

[Runtime reliability](specs/hiring-security-and-runtime-reliability.md) reconciles uncertain mutex acquisition only for its original owner, using majority reads and bounded retries; unresolved ownership still requires manual recovery. Report receipt compaction checks candidate pages of at most 500 against all lineages and active replay dependencies under the existing mutex, rechecks report controls transactionally and deletes at most 1,000 per pass. Memory is bounded; scan duration is not fixed. DNS preflight is effectful and runs on the blocking boundary.

The [architecture wiki](wiki/README.md) connects analytics to hiring use cases; its [storage page](wiki/mongodb-and-analytics.md) inventories MongoDB control collections and Delta datasets.

## Boundary

MongoDB remains the operational source of truth. Kafka carries immutable operational events to the local analytics runtime; no GraphQL mutation waits for Spark, Delta, or an analytics projection.

The current local event contract is the unversioned `hiring.operational-events` envelope implemented in `OperationalEvent.scala`. Analytics consumes that exact seven-field shape with event-specific minimized payloads: job identity/skills/status, application identities/status transitions, and bounded search result identities/ranks/scores. Query text, private filters, job descriptions/requirements/location, feedback and decline reasons are excluded. Typed constructors and strict decoders reject extra fields, inconsistent identities, invalid ranks and nonfinite scores; Spark validates the same contract with native expressions. Values are bounded to 256 KiB, with a 1 MiB producer/topic ceiling. A future envelope evolution is a separate compatibility slice.

Operational facts carry event-time semantics and may be published out of order. Four-claim waves start lease renewal immediately and bound per-poll work; fs2-kafka owns native transaction serialization. Consumers record receipts atomically under Mongo uniqueness before committing offsets; quarantine must also be durable before progress. Workflow revision/inbox ordering remains separate from analytical fact ordering.

## Implemented Local Lakehouse

```text
Kafka retained range -> Bronze -> Silver -> Gold -> Mongo analytics projection -> Admin GraphQL
```

- The batch module reads an explicit, bounded Kafka offset range, preserves Kafka record coordinates, parses analytical facts, deduplicates, and quarantines malformed/conflicting input. A quality-blocked range cannot advance Gold or the published Mongo snapshot. K=10 suppression is checked per output cell using distinct pseudonymized subjects; it is not a formal anonymity guarantee. See the [implementation specification](specs/hiring-analytics-lakehouse.md) for exact metric, retry, and acceptance contracts.
- The batch driver uses Scala 3.7.4 with Spark/Delta's Scala 2.13 artifacts. Cats Effect owns one bounded driver executor for synchronous Spark/Delta and Kafka client calls, including client creation and close. Spark actions run in per-operation job groups that are canceled when their owning effect is canceled; Kafka calls retain their configured request/API timeouts. A Scala 3.9 driver compiled but failed a local Spark runtime check because Spark's 2.13 reflection requires the older standard library.
- The standalone `analytics` build uses `domain` for pure contracts, ranges, retention rules, key-retirement evidence, pseudonymization, and digest helpers; `errors` owns the shared `AnalyticsError`; and `config` decodes HOCON with PureConfig into one section per command (batch, erasure worker, streaming, late-fact replay, key-retirement audit). Independent settings accumulate as `ValidatedNec` problem lists carried by `AnalyticsError.InvalidConfiguration`; the HMAC key ring is validated once into a `SubjectPseudonymizer`. `service.batch`, `service.erasure`, `service.streaming` and `service.keyretirement` hold use-case ports and policies, and `app` wires the runtimes (including `StreamingMaintenanceTick` and `StreamingBatchPreparation`). Spark-coupled batch/erasure workflows live in `adapter.spark`, Kafka readers and fencing in `adapter.kafka`, and Mongo repositories and reactive-stream bridges in `adapter.mongo`. Mongo persistence uses typed mongo4cats collections and Circe codecs over the reactive driver, with strict BSON numeric-width and malformed-record validation; raw BSON remains at query/update and fidelity-sensitive audit boundaries. Production `IOApp` entry points are exposed from `cli`; local HMAC retirement proof and authorization commands are test-scoped and run with `Test / runMain`. Dockerfiles and operator scripts use the corresponding command names. These namespaces sit in one SBT project, so package visibility narrows access where useful but does not enforce the complete dependency graph.
- Delta Bronze, Silver, quarantine, Gold, and run-manifest datasets are written beneath a caller-selected local lakehouse root. The opt-in `analytics-batch` Compose profile persists that root at `.local/data/analytics/`.
- Every Delta table (Bronze, quarantine, Silver, late facts, the three Gold tables, run manifests, streaming progress and decisions, and the HMAC key registry) is declared once in `AnalyticsDeltaCatalog` with real nullability, named CHECK constraints, properties and its subject-attributed classification. The target is validated strictly (names, types, nullability and the exact `delta.constraints.*` set; any difference raises `DeltaSchemaMismatch`) and source frames loosely (names and types), and Delta enforces NOT NULL and CHECK at write time. Gold writes create or validate the target and then overwrite data only, without `overwriteSchema`, so a drifting Gold schema fails instead of being replaced; Gold `day` is a UTC `DATE`. Array elements stay nullable because Delta cannot enforce NOT NULL there, and lambda constraints are avoided because Delta does not round-trip them.
- The batch materializes deletion markers and verifies/registers HMAC key continuity before reserving a generation/revision; that reservation precedes analytical dataset and run-manifest mutation. It writes bounded Gold results into MongoDB with compare-and-set publication and records a `PUBLISHED` manifest only after Mongo confirms the snapshot. Active erasure markers keep the report hidden and make the batch emit `ERASURE_PENDING`.

The first batch metrics are systemwide lifecycle transition activity, time-to-hire percentiles, per-stage hiring durations, and job-created skill posting activity. Time to hire and the stage durations are computed from `silver/application_stage_times` (one row per application, earliest time per status, kept 30 days after a terminal status or 180 days after the last event of an open application), so hires later than the 30-day Silver retention still count; both are suppressed below 10 distinct candidate subjects. `CANDIDATE_HIRED` is not a second lifecycle fact; it remains available for its own event use cases. Recruiter, job, and location enrichment are deferred until an event-time dimension policy exists.

## Erasure and limits

Account deletion writes a durable erasure request, account tombstone, and recruiter job-close events in the receipt-owned Mongo transaction, then returns a durable random receipt in `PENDING`. The `accountDeletionStatus(receiptId)` query requires a verified token belonging to the receipt owner and returns only that owner's `PENDING`, `COMPLETE`, or `NOT_FOUND` status; a still-valid token remains usable after the account is tombstoned. The separate `analytics-erasure` Compose profile runs a resource-managed worker. It waits for a deleted subject's publisher fence and bounded Kafka send timeout, purges subject-attributed outbox rows, records a Kafka end-offset barrier, purges attributed Delta rows (whole un-attributable datasets), and rebuilds Gold. It keeps the report hidden while the broker's earliest offsets pass the barrier and the configured Delta vacuum and log-retention horizons pass, then verifies the surviving Delta snapshots, rebuilds/publishes the bounded report, and atomically marks the request complete with its non-TTL completion ledger, deleting that request's per-file `analytics_erasure_delta_files` evidence (read through the analytics-owned `analytics_erasure_delta_files_request_v1` index) in the same transaction. That delete is bounded by the configured erasure-evidence cap (`maximum-erasure-evidence-files`, the same bound as the bulk write in `persistDeltaFiles`); revisit batching it if the completion transaction times out or the cap is raised. Markers remain active for the configured number of days after completion. Runtime defaults and environment overrides for analytics retention horizons, report reservation expiry, Mongo transaction duration, evidence limits, publisher buffering, and erasure-worker lease, delivery-timeout, and poll timings are defined under `analytics.operational` in `application.conf`. The default Delta vacuum horizon is seven days; configuring a shorter horizon disables Delta's built-in seven-day safety check, as required for the configured shorter horizon to take effect. The default Delta log-retention horizon is 14 days (`delta-log-retention`, env `ANALYTICS_RETENTION_DELTA_LOG_RETENTION`), reconciled onto existing tables at every start; it was 30 days before the [completion-window specification](specs/analytics-erasure-completion-window.md) (AEC-02, AEC-03).

Erasure completion budget: `erasure-completion-budget` (default 21 days, env `ANALYTICS_RETENTION_ERASURE_COMPLETION_BUDGET`) is the configured upper bound on the time from the Delta purge to verified physical erasure, derived from the retention horizons. The worst case is the maximum of three terms: `kafka-retention + kafka-segment-roll` (defaults 7 d + 7 d = 14 d, env `ANALYTICS_RETENTION_KAFKA_RETENTION` and `ANALYTICS_RETENTION_KAFKA_SEGMENT_ROLL`), one UTC day plus `delta-log-retention` (1 d + 14 d = 15 d), and `delta-vacuum-safety` (7 d). With defaults the worst case is 15 days, previously about 31 days. Startup configuration decoding fails with the problem "worst-case erasure completion <computed> exceeds erasure-completion-budget <budget>" when the worst case exceeds the budget, and with "erasure-completion-budget <budget> exceeds the one-month response period 30 days" when the budget itself is above 30 days. The erasure worker logs the computed worst case and the budget once at start. The Kafka terms are configured estimates used only for this check; the runtime gate still reads the broker's actual earliest offsets against the captured barrier. The pure rule is `ErasureCompletionRule` (`deltaDeadline`, `worstCaseCompletion`). The 210-day worst-case retention of `silver/application_stage_times` (180 days open, or 30 days after a terminal status) does not enter this budget, because erasure deletes rows by subject token rather than waiting for expiry.

The Delta log deadline is the start of the UTC day after the purge plus the log retention. Delta truncates the log-cleanup cutoff to a UTC day and removes expired logs only after a checkpoint, so a purge late in the day still waits for the next day. The worker's reclamation recheck interval is `reclamation-recheck-interval` (default 5 minutes, env `ANALYTICS_ERASURE_RECLAMATION_RECHECK_INTERVAL`), no longer a literal.

Motivation: GDPR Article 17 requires erasure "without undue delay", and Article 12(3) allows one month to respond to a request. The budget keeps the default worst case inside that period for the local configuration. The trade-off is that the 14-day log window limits Delta time-travel and rollback to 14 days. Local tests do not prove deployed horizons; every production gate in this document still applies.

Raw Kafka records cannot be selectively deleted and expire on broker retention. Erasure remains active through the publisher fence/drain, the captured broker retention barrier, the configured Delta data-file safety horizon, and the configured Delta log-retention horizon. Bronze and quarantine are classified `PseudonymousSubjects`, and every subject-attributed table sets `delta.dataSkippingNumIndexedCols = 0` so tokens never enter Delta transaction-log statistics. Bronze persists only Kafka coordinates and timestamp, event identity and type, occurred-at, aggregate type and ID, `eventFingerprint` (SHA-256 of the envelope bytes, used for replay and coordinate-conflict checks), application and job identities, new status, job skills, subject tokens and retention timestamps. It holds no raw envelope (`rawValue`), actor ID, payload, raw candidate ID, or search result IDs, ranks and scores. A Bronze table with the earlier shape fails closed with `DeltaSchemaMismatch`; pre-MVP the exact local lakehouse is reset explicitly, with no migration. `delta.enableDeletionVectors` is set to `false` on every managed table; a table where it is `true` fails closed, because deletion-vector rows need `REORG TABLE … APPLY (PURGE)` before VACUUM. Rewrite plus VACUUM remains the physical removal path. Raw subject identifiers still exist in Kafka (seven-day retention), the outbox, the erasure request and completion collections, subject fences and the account tombstone; no Delta table holds them. Legacy log files are checkpoint-cleaned and verified absent before completion.

Marker exclusion is an equality semi/anti join on the Kafka coordinate and may shuffle event rows into the private `spark.local.dir`.

Publication after erasure (D3): the marker port returns `ActiveDeletionMarkers(exclusionTokens, erasureInProgress)`. A `Complete` marker still excludes replayed or late events at ingestion, batch, streaming, late-fact replay and maintenance purge, but it no longer blocks publication. Only `Pending` and `Processing` requests set `erasureInProgress`, hide the report and produce `ERASURE_PENDING`. The worker logs a sanitized backlog line (`erasure backlog: pending=<n> processing=<n> oldestRequestedAgeHours=<h> phase=<p>`) without identifiers whenever the counts or oldest phase change or `backlog-log-interval` (default 1 hour, env `ANALYTICS_ERASURE_BACKLOG_LOG_INTERVAL`) has elapsed; a failing backlog query only produces a warning and never stops the worker. The repair CLI `inspect` prints `receipt=<receiptId>` instead of the subject UUID, and `requeue` takes that receipt ID. `docker/kafka/provision-access.sh` declares explicit `cleanup.policy=delete`, `retention.ms=604800000` and `segment.ms=604800000` on the operational topic, matching the `kafka-retention` and `kafka-segment-roll` settings the budget check uses; the `KAFKA_LOG_RETENTION_HOURS=168` broker setting remains the fallback for topics without explicit configuration. A deployed broker's topic settings are an operator responsibility and are not proven by local evidence. A permanent Deleted-account tombstone denies delayed/manual outbox replay, and generation-guarded snapshot publication prevents a stale run from restoring a hidden report. New analytics rows emit only the active HMAC primary token; erasure matching retains aliases for configured retiring keys so old rows can still be purged. HMAC material must be at least 32 random bytes. A non-TTL Delta control registry anchors each key ID to a domain-separated HMAC verifier; changing key material without changing its ID fails before report reservation. Before full MVP, preserve current-key continuity; if stored registry entries exist, any missing key entry fails closed. Local implementation closure uses accelerated physical erasure proof and simulated-clock boundary tests. Guarded old-key retirement, its real-horizon proof, and a new-key-only restart remain operational activation gates; key removal stays unsupported until those gates pass. Before full MVP, API and analytics schema changes are direct changes without migrations, backfills, or legacy compatibility. Existing lakehouses without trustworthy anchors fail closed; reset/rebuild only the exact local lakehouse when explicitly in scope. Production batch, erasure, and key-retirement audit entry points share a Mongo mutex row keyed by a hash of the normalized lakehouse URI. The row has no TTL or automatic takeover; after a crash, an operator must stop and verify all old owners before deleting the matching row from `analytics_lakehouse_mutexes`. After the existing operator lock-recovery procedure, maintenance inventories abandoned `control/purge-rewrite-<UUID>` copies under the mutex, bounds discovery, rejects unsafe paths, removes recognized copies, and verifies absence before continuing. Read-only key-retirement audits reject unresolved copies. Driver cancellation retains ownership until running work finishes. The mutex does not exclude unmanaged Delta writers. Cleanup and key retirement require inventorying and stopping every writer, plus effective storage-access revocation where the deployment supports it; otherwise retirement remains blocked. The current transactional publisher uses a distinct `hiring_publisher_v2` SASL identity. ACL initialization grants it topic/idempotence/transactional-ID rights and removes those rights from the legacy `publisher` identity; old publisher processes must be stopped before this revocation. A scoped authenticated Compose check verifies current publisher sends/fencing, rejects legacy publisher writes and transaction initialization, verifies invalid fencer credentials fail closed, and denies reader writes/fencing. The regular local broker was restarted with its preserved KRaft data and no legacy PLAIN mapping; its legacy ACL grants were revoked. Post-horizon physical reclamation evidence with populated Delta and real elapsed retention remain release gates. The 2026-09-27 guarded Compose run historically created the erasure request through the authenticated deletion mutation, observed a production publisher hold and fencing result, and passed its scoped checks. The production commit-pause hook used for that observation has since been removed. The maintained Compose proof still verifies the deletion lifecycle, Kafka barrier, targeted outbox purge, and subject-specific Delta purge through `DeltaPurged`; it no longer exercises a production publisher's in-flight commit. See the [analytics specification](specs/hiring-analytics-lakehouse.md) for current evidence.

## Local execution

`analytics-batch` is an opt-in one-shot profile that requires an explicit run ID, partition, and inclusive/exclusive offset range. `analytics-erasure` is a separate long-running profile; start the API once first so Mongo migrations/control documents exist, then keep the worker running while account deletions are accepted. Both share the ignored `.local/data/analytics/` Delta root. See the [README analytics commands](../README.md#local-analytics-batch) and the spec. The acceptance workload is a fixed-seed, 100,000-record local range; its environment and measured resource use are recorded without claiming a performance SLO.

## Remaining roadmap boundary

After the existing Phase 7 functional obligations, Phases 8–12 complete MongoDB/vector retrieval, AI/search evaluation and discovery, Kafka business workflows and operational resilience. Further Spark/Delta architectural refinement, independent report reconciliation and capacity planning belong to Phase 13; production hardening is Phase 14 and real deployed latency/cost optimization is final Phase 15. Existing privacy, correctness and production activation gates apply whenever the runtime is used. See [development milestones](development-milestones.md).

Detailed ownership is split between [analytics reconciliation and recovery](specs/analytics-reconciliation-recovery.md), [production readiness](specs/production-readiness.md) and [deployed analytics performance](specs/deployed-analytics-performance.md). The first defines a bounded independent verifier and pure recovery policies, the second defines deployment and deletion-safe recovery evidence, and the third owns real-environment latency/drain qualification and tuning. Their decision registers retain unresolved environment, budget and operational choices as draft. Existing HAL/HCS and erasure specifications continue to own their acceptance IDs and source-qualified evidence.

The Phase 11 [planned Kafka workflow contracts](../ARCHITECTURE.md#planned-kafka-workflow-contracts) keep workflow commands/results separate from analytical facts when their ownership/retention requires it. Analytics must not consume commands as committed business facts. Before changing operational topic routing, cover every affected partition and stream in publisher fencing, retention barriers, deletion and replay evidence, and update the active consumer contract. Spark is not required to run an operational saga.

## Local interview streams

`hiring.interview-commands` is produced by the orchestrator and consumed by `hiring-interview-workers`; `hiring.interview-results` is produced by workers and consumed by `hiring-interview-orchestrator`. Topic ACLs separate these principals. Both use workflow keys, one local partition, replication/minimum ISR one, delete cleanup, seven-day retention and 64 KiB records. The operational seven-field analytics envelope is unchanged; analytics does not interpret workflow commands as hiring facts. Sequential processing stops/restarts on an undurable record before any later offset is acknowledged. Interview publication uses initialized transactional generations and read-committed consumers. Separate command/result principals own their transactional prefixes; a dedicated fencer can fence those prefixes but cannot write either topic. Mongo authorization registers the generation before send and deletion traverses all attributable generations through bounded registry pages. Interview deletion captures both topic barriers after broker-confirmed fencing and Mongo purge and waits for physical retention, in addition to existing analytics deletion. Old nontransactional publishers must lose write credentials before maintenance cutover. Local redundancy and accelerated checks do not establish deployed retention or production availability.


Operational Kafka null values are explicitly represented at the adapter boundary and quarantined with `MalformedEnvelope`, reason `null event envelope`, and non-null empty bytes. Empty non-null payloads retain the separate `malformed event envelope` reason. Quarantine persistence must succeed before offset acknowledgment; failed persistence prevents later offsets in that partition from advancing. Follow-up raw Mongo and broker recovery evidence belongs to [retrieval and publication reliability](specs/hiring-retrieval-publication-reliability.md#account-erasure-and-recovery-follow-up).
