# Hiring Analytics Architecture

## Boundary

MongoDB remains the operational source of truth. Kafka carries immutable operational events to the local analytics runtime; no GraphQL mutation waits for Spark, Delta, or an analytics projection.

The current local event contract is the unversioned `hiring.operational-events` envelope implemented in `OperationalEvent.scala`. Analytics consumes that exact seven-field shape. A future envelope evolution is a separate compatibility slice.

## Target Lakehouse

```text
Kafka retained range -> Bronze -> Silver -> Gold -> Mongo analytics projection -> Admin GraphQL
```

- The batch module reads an explicit, bounded Kafka offset range, preserves Kafka record coordinates, parses analytical facts, deduplicates, and quarantines malformed/conflicting input. A quality-blocked range cannot advance Gold or the published Mongo snapshot. K=10 suppression is checked per output cell using distinct pseudonymized subjects; it is not a formal anonymity guarantee. See the [implementation specification](specs/hiring-analytics-lakehouse.md) for exact metric, retry, and acceptance contracts.
- The batch driver uses Scala 3.7.4 with Spark/Delta's Scala 2.13 artifacts. Cats Effect owns its blocking actions and client lifetimes; a Scala 3.9 driver compiled but failed a local Spark runtime check because Spark's 2.13 reflection requires the older standard library.
- The standalone `analytics` build keeps shared contracts, runtime configuration, and privacy rules in `com.example.hiring.analytics`. Batch orchestration, Kafka-to-Delta transforms, lakehouse helpers, and the report-publishing port live in `.batch`; erasure orchestration, its persistence port, claim/phase types, and Kafka retention/fencing controls live in `.erasure`; Mongo report publication and erasure persistence adapters live in `.mongo`. This package split follows runtime responsibilities while keeping package-scoped internals available across the analytics module.
- Delta Bronze, Silver, quarantine, Gold, and run-manifest datasets are written beneath a caller-selected local lakehouse root. The opt-in `analytics-batch` Compose profile persists that root at `.local/data/analytics/`.
- The batch materializes deletion markers and verifies/registers HMAC key continuity before reserving a generation/revision; that reservation precedes analytical dataset and run-manifest mutation. It writes bounded Gold results into MongoDB with compare-and-set publication and records a `PUBLISHED` manifest only after Mongo confirms the snapshot. Active erasure markers keep the report hidden and make the batch emit `ERASURE_PENDING`.

The first batch metrics are systemwide lifecycle transition activity, bounded time-to-hire percentiles, and job-created skill posting activity. `CANDIDATE_HIRED` is not a second lifecycle fact; it remains available for its own event use cases. Recruiter, job, and location enrichment are deferred until an event-time dimension policy exists.

## Erasure and limits

Account deletion writes a durable erasure request, account tombstone, and recruiter job-close events in the receipt-owned Mongo transaction, then returns a durable random receipt in `PENDING`. The `accountDeletionStatus(receiptId)` query returns `PENDING`, `COMPLETE`, or `NOT_FOUND` without requiring the deleted account's active login. The separate `analytics-erasure` Compose profile runs a resource-managed worker. It waits for a deleted subject's publisher fence and bounded Kafka send timeout, purges subject-attributed outbox rows, records a Kafka end-offset barrier, purges attributed Delta rows (whole un-attributable datasets), and rebuilds Gold. It keeps the report hidden while the broker's earliest offsets pass the barrier and Delta's seven-day vacuum horizon passes, then verifies the surviving Delta snapshots, rebuilds/publishes the bounded report, and atomically marks the request complete with its non-TTL completion ledger. Markers remain active for 31 days after completion. Retry failures persist only a fixed category and attempt count; exhausted or invalid-state work stays `PENDING` in a repair-required state. A local inspect/requeue command requires the observed attempt count and no live lease, and preserves the current durable phase.

Raw Kafka records cannot be selectively deleted and expire on broker retention. Erasure remains active through the publisher fence/drain, the captured broker retention barrier, the seven-day Delta data-file safety horizon, and the 30-day Delta log-retention horizon. Bronze/quarantine writes disable column statistics so future raw values do not enter Delta transaction logs; legacy log files are checkpoint-cleaned and verified absent before completion. A permanent Deleted-account tombstone denies delayed/manual outbox replay, and generation-guarded snapshot publication prevents a stale run from restoring a hidden report. New analytics rows emit only the active HMAC primary token; erasure matching retains aliases for configured retiring keys so old rows can still be purged. HMAC material must be at least 32 random bytes. A non-TTL Delta control registry anchors each key ID to a domain-separated HMAC verifier; changing key material without changing its ID fails before report reservation. Before full MVP, preserve current-key continuity; if stored registry entries exist, any missing key entry fails closed. Old-key rotation and retirement are outside this milestone because there is no old product data. Before full MVP, API and analytics schema changes are direct changes without migrations, backfills, or legacy compatibility. Existing lakehouses without trustworthy anchors fail closed; reset/rebuild only the exact local lakehouse when explicitly in scope. Production batch, erasure, and key-retirement audit entry points share a Mongo mutex row keyed by a hash of the normalized lakehouse URI. The row has no TTL or automatic takeover; after a crash, an operator must stop and verify all old owners before deleting the matching row from `analytics_lakehouse_mutexes`. The mutex does not exclude unmanaged Delta writers. Cleanup and key retirement require inventorying and stopping every writer, plus effective storage-access revocation where the deployment supports it; otherwise retirement remains blocked. The current transactional publisher uses a distinct `hiring_publisher_v2` SASL identity. ACL initialization grants it topic/idempotence/transactional-ID rights and removes those rights from the legacy `publisher` identity; old publisher processes must be stopped before this revocation. A scoped authenticated Compose check verifies current publisher sends/fencing, rejects legacy publisher writes and transaction initialization, verifies invalid fencer credentials fail closed, and denies reader writes/fencing. The regular local broker was restarted with its preserved KRaft data and no legacy PLAIN mapping; its legacy ACL grants were revoked. Post-horizon physical reclamation evidence with populated Delta and real elapsed retention remain release gates. A guarded proof creates the erasure request through the authenticated `deleteMyAccount` mutation; the production publisher claim registers and publishes the fixture event; and the actual Compose worker captures/fences the registered ID, persists the Kafka barrier, purges the matching outbox row, and leaves public status `PENDING` at `DeltaPurged`. A separate test producer holds a transaction under that registered ID, so the application publisher itself is not shown holding an open transaction through deletion. See the [analytics specification](specs/hiring-analytics-lakehouse.md) for current evidence.

## Local execution

`analytics-batch` is an opt-in one-shot profile that requires an explicit run ID, partition, and inclusive/exclusive offset range. `analytics-erasure` is a separate long-running profile; start the API once first so Mongo migrations/control documents exist, then keep the worker running while account deletions are accepted. Both share the ignored `.local/data/analytics/` Delta root. See the [README analytics commands](../README.md#local-analytics-batch) and the spec. The acceptance workload is a fixed-seed, 100,000-record local range; its environment and measured resource use are recorded without claiming a performance SLO.

## Non-goals

Structured Streaming, cloud storage, Databricks deployment, search evaluation, and reports beyond the 30-day retained window are not part of this slice.
