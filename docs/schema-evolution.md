# Current Contract and Persistence Evolution

## Authentication receipt protection and trusted Admin seed


Receipt fingerprints are keyed by `auth.jwt.receipt-fingerprint-secret` (`AUTH_RECEIPT_FP_SECRET`, at least 32 bytes), falling back to the JWT secret when unset. Pre-MVP there is no receipt conversion: older receipt shapes expire by TTL. Changing the receipt key (or the JWT secret when no separate receipt secret is set) invalidates existing authentication receipt matches, so use new idempotency keys. Key rotation is manual and out of scope before MVP. Public GraphQL `bootstrapAdmin` is removed under the pre-MVP single-active-shape policy; trusted `auth.admin-seed` startup configuration owns provisioning and never resets an existing singleton. Existing users and non-authentication mutation receipts are preserved. See [acceptance evidence](specs/hiring-security-and-runtime-reliability.md).

## Candidate residence integrity

Migration `016_candidate_residence_integrity` supplements the unchanged `002_candidate_search_profile_verification` ledger. Stop incompatible user writers before cutover. The user validator requires display/canonical city fields to be both absent or both present; a bounded restartable audit verifies their existing canonical values using the application's normalization. It changes only its ledger, preserving user data and revisions. Failed batches retain the preceding checkpoint and block startup until explicit repair. Completed proof and the exact installed validator are checked before the audit is skipped; validator drift is not silently overwritten. No public or stored field shape changes, normalization backfill or data reset is introduced. Evidence is tracked in [candidate discovery and interview integrity](specs/candidate-discovery-and-interview-integrity.md).

## Deleted account embedding cleanup

Migration `014_deleted_account_embeddings` removes `embedding` and `embeddingMeta` from existing Deleted-account tombstones in guarded batches of at most 500. Stop older writers before initialization. Both fields are unset atomically; successful removal is the restart checkpoint. Existing active accounts and every other tombstone field remain unchanged. This privacy maintenance operation deliberately preserves aggregate revisions as an exception to ordinary aggregate writes. Existing validation stays enabled; malformed data or an unsupported ledger blocks startup without bypassing validation or repairing revisions implicitly.

Completion requires acknowledged writes and absence verification. Every completed startup checks for a residual matching document and fails closed if fields reappear. Recovery from Running resumes the remaining records. A Complete ledger with reintroduced data requires explicit maintenance repair before startup; application rollback cannot restore purged vectors. Follow-up evidence belongs to [retrieval and publication reliability](specs/hiring-retrieval-publication-reliability.md#account-erasure-and-recovery-follow-up).

## Workflow reliability cutovers

The October 7 reliability slice adds `012_attributable_producer_registrations` and `013_hiring_workflow_integrity`; applied migrations remain unchanged. Stop incompatible operational and analytics writers before cutover. Migration 012 transfers attribution before removing old arrays, verifies strict validators and preserves unresolved generations without TTL. Analytics accepts the single registry-backed shape only after the completed version-one proof.

After migration 013 audits existing commands/outbox rows and installs equivalent strict validators, startup verifies the exact definitions before skipping completed 010 command and 003 outbox audits. Validator drift fails closed; startup does not silently restore a changed validator. Migration `015_interview_cleanup_integrity` separately audits cleanup records in bounded restartable batches and installs the strict cleanup validator. Only its exact completed proof, configured physical topic pair and validator permit skipping the completed 011 cleanup scan. Maintenance audits still check raw BSON with durable checkpoints.

Operational event payloads now have one minimized active shape, validated by typed payload constructors and the wire decoder. The seven envelope fields and event names are unchanged. Incompatible existing event bytes are preserved and terminally failed during claim, retaining subject attribution for deletion. Invalid control metadata fails closed. There is no legacy reader, event backfill or automatic lakehouse reset. Stop incompatible writers before this cutover and update consumers together; see [event and test reliability](specs/hiring-event-and-test-reliability.md).

Run the explicit `MongoWorkflowIntegrityAudit` maintenance entrypoint for bounded resumable checks. Failed audit batches retain their previous checkpoint for repair and rerun; a completed run starts a fresh audit next time. Canonical UUID identities are required at cutover, so incompatible existing command rows require explicit repair before proof completion. No application rollback is a database rollback; preserve the database and stopped-writer recovery evidence.


The API and analytics schemas have one active shape before full MVP. Implement their schema changes directly; do not add migration, backfill, dual-read/write, or legacy-compatibility code before full MVP. If incompatible local analytics data exists, reset/rebuild only the exact local lakehouse when explicitly in scope; otherwise preserve it and fail closed. After full MVP, apply the schema evolution requirements in `AGENTS.md`.

GraphQL, cursor, operational-event, and embedding contracts therefore have one active shape before MVP. User and job Mongo documents also carry an internal version: Long concurrency revision. This field is not a schema revision and is not exposed through GraphQL or events.

## Aggregate revisions

- New user/job documents start at revision 0. `version` is the content revision: it advances once, in the same atomic Mongo write, only when the content of the user or job changes (profile, job edit, status change, closure, account deletion). Jobs carry a separate optional `admissionFence` (Int64 >= 0, absent = 0, internal) that application submission and interview scheduling `$inc` instead; those writes change neither `version` nor `updatedAt`, so a concurrent submission never stales a recruiter edit. Content writes are targeted `$set`/`$unset`/`$inc version` updates that never touch `embedding`, `embeddingMeta` or `admissionFence`.
- Compare-and-set writes filter by aggregate _id and expected version; stale snapshots return the existing typed conflict result. Embedding writes use the same revision guard but do not increment the revision: derived data is guarded by `version` and never advances it, so background embedding cannot fail a user edit. Interview writes and admin authorization fence users through the subject fence (`outbox_subject_fences.fencingVersion`) and leave `users.version` alone.
- Startup runs migration 001_user_job_revisions before repository reads and gates the durable embedding worker until setup completes. It backfills missing revisions in bounded _id batches, verifies every revision is a non-negative BSON long, and records completion in hiring_migration_ledger only after verification. Once the ledger records Complete, later startups skip the backfill and verification scans.
- The backfill is restartable and safe across concurrent startup instances: each batch updates only documents whose revision is still missing, so it cannot reset a revision advanced by a live write. Verification or write failure aborts startup and leaves the migration resumable. Explicit mongo.reset-on-start still drops all owned collections, including the ledger.
- All binaries using the old document shape must be stopped before this migration runs. The new strict codecs require revisions, and old binaries reject the added field; this change is not compatible with mixed-version application instances.

## Outbox subjects, analytics control, receipt indexes and closure work

- `003_event_outbox_subject_references` adds `subjectIds` and `subjectRefsVersion: 1` to existing `event_outbox` rows. These internal subject facts drive fencing and purge; the Kafka envelope is unchanged. The step reads stored events in bounded `_id` batches, derives the actor and any candidate IDs the payload names (a search click is resolved through its retained search session), and advances a checkpoint per event. An undecodable event, an incompatible aggregate type or an unresolvable click fails the run. A completed proof is reopened when rows without `subjectRefsVersion: 1` reappear. The step is skipped while the `013_hiring_workflow_integrity` proof is trusted ([source](../src/main/scala/com/example/graphQL/cats/repository/mongo/MongoHiringMigrations.scala)).
- `004_analytics_report_control` seeds the singleton `analytics_report_control` document `analytics-report` with `generation`, `nextRevision` and `lastPublishedRevision` at 0. Its `state` is `Published` only when the legacy `current` report snapshot is published and unexpired, and otherwise `Unpublished`; `lastRunId` is `legacy` or empty. It also adds `generation`, `revision` and `runId` to the legacy `current` snapshot when they are missing. Every startup verifies the control document's numeric fields and that its state is `Unpublished`, `Hidden` or `Published`.
- `005_analytics_deletion_receipts` rewrites no documents. It creates the unique partial indexes on `receiptId` for `analytics_erasure_requests` (`analytics_erasure_request_receipt_unique`) and `analytics_erasure_completions` (`analytics_erasure_completion_receipt_unique`). Their definitions are declared once in `MongoHiringIndexSetup` and verified on every startup.
- `020_recruiter_job_closure_work` is expand-only. It creates the empty `recruiter_job_closure_work` collection and installs its strict validator: `_id` is a UUID string, `requestedAt` and `notBefore` are dates, `attempts` is a non-negative integer, and no other fields are allowed. The collection has no secondary index. Row lifecycle, retry state and the local-draft reset note are described in [deleted recruiter job closure](mongodb-design.md#deleted-recruiter-job-closure).
- `021_job_admission_fence` is expand-only. It installs the jobs validator V2, which permits an optional `admissionFence` long >= 0 (absent means 0, so there is no backfill) and leaves the users validator unchanged. The cutover audits every stored `admissionFence` (any value that is not a non-negative long fails the step) before the proof completes; other legacy job defects keep their own typed errors. The completed proof is read-only: it trusts the step while the exact V2 validator holds, and the same validator is installed at every startup, so a restart writes nothing to the ledger. Stop writers that run an earlier binary first: they reject the new field and would keep using `version` as a fence. Recovery is forward-only (run the current binary); an application rollback does not remove `admissionFence`. Evidence: MSC-01 and MSC-10.1 in [schema consolidation](specs/hiring-mongo-schema-consolidation.md).
- `022_interview_subject_attribution` backfills `interview_workflow_inbox` hiring receipts (the `{workflowId}:hiring` rows that earlier binaries wrote without `documentType`) with `documentType: "hiringReceipt"` and `subjectIds` (candidate and recruiter), and removes their separate `candidateId`/`recruiterId` fields so each fact is stored once. Subjects come from the receipt itself, never from the workflow, so a receipt whose workflow already expired is attributed and purgeable. The scan walks `_id` in 500-row batches with a ledger checkpoint; each update is conditional on `documentType` still being absent, so replays and two concurrent starters converge. An inbox row that lacks `documentType` and is not a complete hiring receipt fails the step closed with its identity (the step stays Running and every later start reports it). The completed proof is read-only: no inbox row may lack `documentType`, and a regression (an earlier binary still writing receipts) reopens the step. The proof is one `_id`-ordered pass over a TTL-bounded collection; revisit it if the inbox outgrows its completed-evidence retention. The new index `interview_workflow_inbox_hiring_subject_ids` (partial on `hiringReceipt`) is an additive entry in `MongoHiringIndexSetup`; workflow lookups reuse the existing candidate and recruiter indexes. If the final check finds an unattributed row below the saved checkpoint (a late write by an earlier binary), the step rescans once from the start before failing. The failure text names only the workflow UUID part of the row identity. **Deploy precondition: stop every writer that runs an earlier binary before upgrading.** An earlier binary writes hiring receipts in the old shape; once their workflow is gone they cannot be attributed to a subject and are not purged by the erasure until 022 reruns (the next start of the current binary reopens the step and repairs them). Recovery is forward-only. Evidence: MSC-02.1/02.2 in [schema consolidation](specs/hiring-mongo-schema-consolidation.md).
- `023_consumer_receipt_identity` verifies that every `consumer_receipts` `_id` equals `consumerGroup:eventId` (bounded `_id` batches with a checkpoint; a violating receipt fails the step closed and keeps the index), then drops the redundant unique `(consumerGroup, eventId)` index `consumer_receipts_group_event`. An absent index or namespace (codes 26/27) is the expected outcome on a fresh database or restart. Duplicate delivery still reports "seen" because the insert fails on `_id`. The completed proof is read-only: the index must be absent, and its reappearance reopens the step. The index is removed from `MongoHiringIndexSetup`, so nothing recreates it. Stop the earlier binary first (it would recreate the index); recovery is forward-only. Evidence: MSC-03.1.
- `024_optional_field_absence` makes absent values absent and gives every user an `updatedAt`. Writers (codecs and `auditActorId`) omit optional fields instead of storing `null`, new users store `updatedAt = createdAt`, and workflows and notification receipts stop writing the unread `subjectIds` copy. The step repairs stored rows in bounded `_id` batches (500) per target with a ledger checkpoint `<target ordinal>:<_id>`: `$unset` of a stored `null` on outbox `leaseOwner`/`leaseToken`, `search_sessions` `query`/`model`, `search_session_work` `session.query`/`session.model` and inbox `auditActorId`; `$unset` of `subjectIds` on `interview_workflows` and `interview_notification_receipts` (hiring receipts keep theirs, the erasure purge reads them); `updatedAt = createdAt` where a user lacks it (a user without a `createdAt` date fails the step closed naming the collection). Each update repeats its pending predicate, so a replay or a second starter converges. The completed proof is read-only: no target may have a pending row (one document read per target on every start; the scans are unindexed, an accepted deviation in [MongoDB design](mongodb-design.md#accepted-deviations)); a regression reopens the step, and one rescan from the start repairs rows below the saved checkpoint. Stop writers that run an earlier binary first: they store `null` again and write users without `updatedAt`. Recovery is forward-only. Evidence: MSC-04.1 and MSC-10.1.
- `025_operational_collection_validators` installs strict validators (`validationLevel: strict`, `validationAction: error`) on `applications`, `application_events`, `embedding_work`, `search_sessions`, `search_session_work`, `mutation_receipts`, `consumer_receipts`, `interview_workflows`, `interview_workflow_inbox`, `interview_calendar_reservations` and `interview_notification_receipts`, and replaces the users validator with V2. Closed shapes use `additionalProperties: false` (applications, application events, the three receipt collections); the evolving embedding-work, search and interview documents list required fields and types only. `interview_workflows` has one `oneOf` branch per `documentType` (`workflow`, `requestReceipt`), and `interview_workflow_inbox` one per `inboxReceipt`, `hiringReceipt` and `quarantine`; a document without a known type matches none. Users V2 types `name`, `nameCanonical`, `email`, `emailCanonical`, `passwordHash` (strings) and `createdAt`, `updatedAt`, `deletedAt` (dates), requires `name`, `nameCanonical`, `createdAt` and `updatedAt`, and its Deleted branch forbids `email`, `emailCanonical`, `passwordHash`, `profile`, `embedding` and `embeddingMeta`. The step audits every collection with `$nor` before installing (the first violating collection fails the step naming only that collection, and nothing is installed), installs, and audits again to close the window between audit and install. The completed proof is read-only and compares every definition exactly; later drift fails closed with the drifted collection and is never overwritten. `016_candidate_residence_integrity` completed against the earlier users validator (kept as `userValidatorV1`); its startup proof accepts V1 or V2, and any other definition is drift. Stop writers that run an earlier binary first: the new validators reject their writes. Recovery is forward-only. Evidence: MSC-05.1/05.2/05.3 and MSC-10.1.
- `026_outbox_envelope_source` makes `envelopeBytes` the only stored copy of an operational event body. Writers stop storing the `payload` JSON string on `event_outbox` rows and on the event embedded in `search_session_work`; readers (`readOperationalEvent`, used by the claim, duplicate detection, the search-session-work reader and migration `003`) decode `envelopeBytes` with the wire codec and reject a row whose queried top-level fields (`_id`, `eventType`, `aggregateType`, `aggregateId`, `actorId`, `occurredAt`, `partitionKey`) disagree with the envelope. The top-level fields that queries and analytics read stay; analytics reads only `subjectIds` and `subjectRefsVersion` from the outbox. The step `$unset`s `payload` and `event.payload` in bounded `_id` batches (checkpoint `<target ordinal>:<_id>`, each update repeats the pending predicate and bypasses document validation, because the `025` search-session-work validator still requires the field being removed), rescans once from the start before failing, audits both collections with `$nor` against the successor validators (a violating row fails the step naming only the collection), installs them, and audits again. Outbox validator V2 forbids `payload`, requires `envelopeBytes` (binData) and types `leaseOwner`/`leaseToken` (string) and `leaseUntil` (date) so they are absent or typed, never `null`; it is also installed at every start. Search-session-work validator V2 requires `event.envelopeBytes` and forbids `event.payload`. The completed proof is read-only: both successor validators must be installed unchanged (drift fails closed) and no `payload` may remain, otherwise the step reopens. The proofs of `013` (outbox V1 or V2) and `025` (search-session-work V1 or V2) accept the successors. `003` runs only while the `013` proof is untrusted, so a database upgraded through `013` never reruns it; its reader decodes `envelopeBytes` and ignores a not-yet-removed `payload`. Stop every writer running an earlier binary first: it stores `payload`, which the validators reject. Recovery is forward-only; the event body stays recoverable from `envelopeBytes`. Evidence: MSC-06.1 and MSC-10.1.
- `027_job_canonical_filters` makes the job `skills` and `location.city` filters case-insensitive, matching candidate filters. Job writers (insert codec and `MongoJobContentUpdate`) store `skillsCanonical` (one canonical value per skill, in the order of `skills`) and `location.cityCanonical` (absent exactly when `location.city` is absent), both produced by `SearchTerm.canonical` (trim, lower-case with the root locale; the function candidate sidecars and filter inputs use), in the same update as their display fields, so the staleness bound is zero. The list filter, discovery filter, facet pipeline, vector-search filter, lexical filter and the in-application eligibility recheck compare canonical values and normalize filter inputs the same way. Facets group by the canonical value: `skills` buckets report the canonical spelling and `cities` buckets report one display spelling per canonical city (the smallest), so `Kyiv` and `kyiv` count as one city. The step scans every job in bounded `_id` batches (checkpoint `<last _id>`), repairs a job whose stored canonical values differ from the derived ones with one `updateOne` guarded by `_id` and the display values that were read (a concurrent edit that already wrote its own canonical values is not overwritten), rescans once from the start if the `$nor` audit against jobs validator V3 still finds a job, audits, installs V3, audits again, creates the replacement indexes `jobs_open_city_canonical_created_id` (status, `location.cityCanonical`, createdAt desc, `_id` desc) and `jobs_embedding_meta_canonical_filters` (`embeddingMeta.model`, status, `location.cityCanonical`, recruiterId), then drops the superseded `jobs_open_city_created_id` and `jobs_embedding_meta_filters` (an absent index or namespace is accepted). Jobs validator V3 requires `skills` and `skillsCanonical` (string arrays of equal size) and `location`, and a `location.city` is present exactly when `location.cityCanonical` is; it cannot check that each canonical value equals the lower-cased display value because `$toLower` is ASCII-only, so that equality rests on the single writer and the backfill. The completed proof is read-only and does not scan: jobs validator V3 or V4 installed unchanged (the `021` proof accepts V2, V3 or V4; `021` itself installs V2) and the superseded indexes absent, otherwise the step reopens. Atlas Search definitions move to new index names (`vector-search.indexes.jobs` default `jobs_embedding_vector_canonical_v1`, `vector-search.indexes.lexical` default `jobs_text_search_canonical_v1`) with filter paths `location.cityCanonical` and `skillsCanonical`; a same-name definition with other paths still fails startup and is never replaced, and the old-named Atlas indexes `jobs_embedding_vector` and `jobs_text_search` are left in place. Operator step after the Atlas Local gates pass and the canonical indexes (`jobs_embedding_vector_canonical_v1`, `jobs_text_search_canonical_v1`) are verified queryable: drop the superseded `jobs_embedding_vector` and `jobs_text_search` search indexes (they only cost index storage and mongot work). Canonical text bound: jobs V3/V4 allow canonical values of up to 512 characters, because lower-casing expands only U+0130 to two characters. Stop writers that run an earlier binary first: it does not write the canonical fields, which V3 rejects. Recovery is forward-only. Evidence: MSC-08.1 and MSC-10.1 (Atlas gates MVR-04.L and MVR-09.L pending a user run).
- `028_binary_embedding_vectors` stores `users.embedding` and `jobs.embedding` as BSON binary vectors (binData subtype 9, float32; driver `BinaryVector.floatVector`) instead of float64 arrays; the domain element type is `Float`, so the stored form is exact for every value the application wrote. Codecs write the vector separately from the generated document codecs and read it back through `MongoEmbeddingVectors`, which accepts only a float32 vector and fails closed (`InvalidField(embedding)`) on any other form. The embedding write stays a targeted `$set` that never advances `version`. The step converts users, then jobs, in bounded `_id` batches whose pending predicate is `embedding` of type array (checkpoint `<target ordinal>:<last _id>`), each update guarded by `_id` and the exact array that was read (a concurrent embedding write or a replay is a no-op); a non-numeric or non-finite element fails the step naming only the collection. If a pending row remains after the first scan, one rescan from the start runs before the step fails. It then audits both collections with `$nor` against the successor validators (users V3 and jobs V4: a present `embedding` must be `binData`), installs them, and audits again. The completed proof is read-only and does not scan: both successor validators installed unchanged (the proofs of `016`, `021`, `025` and `027` accept their earlier definitions and these successors). The Atlas vector index definitions keep `path: embedding`, `numDimensions` and `similarity: cosine`; that Atlas Local accepts a binData vector under the unchanged definition is part of the user-run gate (MVR-09.L), not established on the isolated stack. Stop writers that run an earlier binary first: it writes float64 arrays, which the validators reject, and cannot read binary vectors. Recovery is forward-only; the embedding worker can regenerate any vector. Evidence: MSC-09.1 and MSC-10.1 (storage comparison recorded on the isolated stack; Atlas recall and latency gates pending a user run).

## Other contracts and data

The search/publication reliability slice changes internal application-admission ports to a projected ID/status/revision snapshot and adds validated workflow polling configuration; persisted job revisions, public GraphQL/event shapes and applied migrations remain unchanged. Embedding provider model mismatches now fail before use. Candidate outbox indexes are measured on disposable namespaces and require a new repeatable migration only if adoption gates pass; a rejected candidate changes no production index.

GraphQL SDL, cursors, operational-event payloads, and embedding metadata describe only the active shape. No legacy API/event readers or compatibility window are maintained. A contract change updates its implementation, SDL fixture, executable operations, and this document together. The aggregate revision is independent from schema, cursor, event, embedding-model, and analytics-run versions.

Critical integrity remains enforced by MongoDB uniqueness and transactional identity, ownership, status, and state predicates. Resetting local data does not relax authorization, lifecycle, duplicate-application, or closed-job invariants.

## Embedding coverage report contract

The Admin-only `embeddingCoverage(expectedModel: String)` query and its `EmbeddingCoverage*`, `EmbeddingFreshness`, `EmbeddingRepairState`, `EmbeddingFailureReason` and `EmbeddingObservedModel` types are an additive, read-only API change. They add no persisted field, index, migration, event or cursor, and reuse the existing `VECTOR_SEARCH_UNAVAILABLE`, `UNAUTHORIZED` and `VALIDATION_FAILED` codes. The SDL snapshot, the validated `embedding-coverage.graphql` operation, `docs/api.md` and the [specification](specs/embedding-coverage-report.md) change together. Enum labels use SCREAMING_CASE while the internal states keep their existing representation. Each entity page and its queue rows are read at one point in time under snapshot read concern; the report as a whole is a sequence of such pages, not a transaction. The root is an expensive root with fixed complexity, so one coverage scan runs per request. The scan adds no write and no index.

## Geographic discovery and interview scheduling contracts

Job location has one optional geographic point. API inputs validate finite latitude/longitude; MongoDB stores the active GeoJSON Point shape in longitude/latitude order. Existing jobs keep an absent point. Nearby cursors carry full-precision distance, job identity and a fingerprint of the center, radius, normalized structured filters and ordering; mismatched cursors are rejected rather than interpreted under another query. SDL and executable operations describe the current nearby, facet and scheduling fields.

Interview scheduling accepts UTC times at millisecond precision, matching MongoDB dates. Inputs are normalized before future-start and positive-duration validation and before request fingerprinting; an interval that collapses to zero milliseconds is rejected. Mutation responses, inspection and replay therefore use the same canonical interval.

Interview commands/results have one active capability-specific metadata shape containing workflow/message identity, step, revision, causation, occurrence, deadline and optional result. Scheduling details are fetched from MongoDB. The seven-field operational event envelope is unchanged. Workflow revisions and claim fencing tokens are coordination state, not schema versions.

Operational migrations `006_job_geo_points`, `007_interview_workflow_storage`, `008_interview_subject_cleanup` and `009_interview_inbox_identity` preserve local records and verify their required validators/indexes before enabling discovery or workers. Stop incompatible job/workflow writers before cutover. An invalid stored point or unknown existing index definition fails startup; correct the offending data or definition explicitly and rerun the restartable migration. No analytics reset, legacy reader or dual writer is introduced. Scheduling acceptance uses the existing application `updatedAt` field for a transactional write lock and adds no application status or persistence field.

Current evidence and pending gates are maintained in the [discovery specification](specs/hiring-discovery-search-quality.md) and [workflow specification](specs/durable-hiring-workflows.md).

Run sbt test for the Docker-independent contract suite and sbt 'IntegrationTest / test' for disposable MongoDB, migration, transaction, and HTTP checks. Current acceptance and evidence are tracked in [the active specification](specs/pre-mvp-contract-reset.md).

## Interview workflow recovery maintenance

They gate startup, are restartable in bounded batches and reject malformed stored contracts. Before activation stop old interview writers and revoke their nontransactional topic-write credentials. Configure separate command/result publishers and a prefix-scoped fencer; verify migrations, fencing and physical retention on the target environment before declaring erasure complete. Rolling back the application does not roll back migrated budgets or restore the old cleanup proof. Existing local data is preserved; a deployed maintenance migration is outside this local refactoring task. See [current acceptance criteria](specs/hiring-workflow-recovery.md).

## Interview ledger names and cancellation storage

Migration `017_interview_ledger_collections` renames the interview calendar and notification ledgers from their original `fake_`-prefixed names to `interview_calendar_reservations`, `interview_calendar_participant_locks` and `interview_notification_receipts`, preserving every document and recreating indexes under the same names without the prefix. It renames a collection only when the original exists and the new one does not; if both exist it fails closed with a typed `MigrationError`. Migration `018_interview_cancellation_reschedule` extends the strict command validator with the cancellation and reschedule intents (the `013` proof accepts either validator), makes reservation identity unique per `(workflowId, reserveKey)` and verifies the due-command index; unknown reservation indexes and validator drift fail startup. Migration `019_interview_request_receipt_index` adds the sparse `requestWorkflowId` index of the interview workflow collection, so retention and cleanup find request receipts without scanning (an existing index of that name with another definition fails startup). Stop interview workers before cutover. Recovery is forward only.

Justified deviation: `007_interview_workflow_storage` is unchanged in identity, but it creates its collections through the shared name constants, so a fresh installation now creates the business-named ledgers directly. `017` is therefore a no-op on fresh installations and renames on upgraded ones, and it runs immediately after `007` so no later step can create a business-named collection first. Evidence retention for completed or cancelled interview workflows is `max(now, interview end) + eight days` for every interview collection, so evidence outlives the interview it protects.

## Interview cancellation and rescheduling API contract

The seven mutations `cancelInterview`, `requestInterviewReschedule`, `dismissInterviewRescheduleRequest`, `proposeInterviewReschedule`, `withdrawInterviewReschedule`, `acceptInterviewReschedule` and `declineInterviewReschedule`, their inputs `InterviewActionInput` and `ProposeInterviewRescheduleInput`, the `InterviewActionResult` union and the seven nullable or boolean `InterviewWorkflow` fields (`pendingStartsAt`, `pendingEndsAt`, `cancelledAt`, `proposedStartsAt`, `proposedEndsAt`, `proposalExpiresAt`, `rescheduleRequested`) are an additive change: no existing type, field, argument, enum value or code is removed, renamed or made stricter, and `progress` (a string) only gains documented phase values. The SDL snapshot, the executable [operations](../src/test/resources/graphql/interview-cancellation.graphql), [docs/api.md](api.md) and the [specification](specs/durable-hiring-workflows.md) change together. The setting `auth.interview-action-rate-limit` is required (packaged in `application.conf`) and changes no stored data. The storage side (migrations 017 to 019) is described above and in the specification.
