## Identity and authorization

[JwtActorAuthenticator](../../src/main/scala/com/example/graphQL/cats/api/auth/JwtActorAuthenticator.scala) accepts a single Bearer credential, verifies HS256 signature, issuer, audience, expiration and not-before, and parses a typed subject ID. It resolves the actor through [UserAuthenticationService](../../src/main/scala/com/example/graphQL/cats/service/auth/UserAuthenticationService.scala). Stored user state determines role and active identity. Missing credentials allow public fields; protected fields still require authorization. Invalid credentials are rejected; authentication-store unavailability is distinguished from invalid identity.

[UserAccountService](../../src/main/scala/com/example/graphQL/cats/service/auth/UserAccountService.scala) owns registration, login, self-service changes and deletion. The application-owned [PasswordHasher port](../../src/main/scala/com/example/graphQL/cats/service/auth/PasswordHasher.scala) is implemented by the infrastructure [Argon2 adapter](../../src/main/scala/com/example/graphQL/cats/infrastructure/auth/Argon2PasswordHasher.scala), with configured cost, bounded concurrency and blocking native execution. Public signup cannot provision Admin; trusted startup configuration invokes [MongoAdminSeed](../../src/main/scala/com/example/graphQL/cats/repository/mongo/MongoAdminSeed.scala) before workers/HTTP. It is disabled by default, preserves an existing same-name Admin without resetting credentials, and rejects conflicting identity/registry state.

Authentication receipts store domain-separated HMAC fingerprints keyed by the receipt secret (JWT secret when unset); token-producing replay verifies current credentials and the referenced active identity. Changing the key causes old auth receipt conflicts rather than legacy fallback. [AuthRateLimiter](../../src/main/scala/com/example/graphQL/cats/api/admission/AuthRateLimiter.scala) bounds login/signup attempts, and [ClientAddressResolver](../../src/main/scala/com/example/graphQL/cats/api/http/ClientAddressResolver.scala) applies trusted-proxy policy.

| Actor | Main capabilities | Boundary |
|---|---|---|
| Candidate | Discover eligible jobs, apply, inspect own applications/history, manage own account and inspect own interviews | Candidate identity derives from authenticated actor; private profiles are not unrestricted search results |
| Recruiter | Manage owned jobs/applications, match visible candidates for an owned job, schedule/inspect owned-job interviews | Ownership and visibility checks in services and scoped persistence access |
| Admin | Authorized cross-user hiring access, user management, reporting and workflow repair | Singleton persistence constraint and the trusted seed boundary described above; repair uses expected revision, idempotency and reconciliation |

The [operation map](domain-and-use-cases.md) gives field-specific rules. [ActorAuthorization](../../src/main/scala/com/example/graphQL/cats/service/auth/ActorAuthorization.scala), [HiringReadScope](../../src/main/scala/com/example/graphQL/cats/service/read/HiringReadScope.scala), and [MongoAuthorizedReadQueries](../../src/main/scala/com/example/graphQL/cats/repository/mongo/MongoAuthorizedReadQueries.scala) enforce checks below resolvers. Request-local batching does not create a shared cross-user entity cache. Mutation predicates/revisions preserve relevant checks under concurrent writes.

## Errors and sensitive data

[GraphQLFailureCatalog](../../src/main/scala/com/example/graphQL/cats/api/graphql/GraphQLFailureCatalog.scala) and resolver support translate expected errors into meaningful GraphQL failures. Unexpected framework/driver errors become sanitized client messages plus internal diagnostics. [HTTP routes](../../src/main/scala/com/example/graphQL/cats/api/http/GraphQLHttpRoutes.scala) distinguish malformed requests, media negotiation, authentication and unavailable service. GraphQL field errors can appear within HTTP 200 responses.

Event payloads, candidate projections, quarantine and diagnostics have separate minimization rules. [SafeDiagnostics](../../src/main/scala/com/example/graphQL/cats/infrastructure/logging/SafeDiagnostics.scala) and [logging documentation](../logging.md) define the diagnostic boundary. Account erasure includes embeddings, interviews and analytical copies: a user tombstone alone does not establish physical deletion. Kafka/Delta retention and guarded producer/key retirement are downstream barriers; see [storage](mongodb-and-analytics.md).

These are implemented controls, not an OWASP audit, dependency advisory scan or certification of arbitrary deployment settings.

## Configuration and runtime ownership

[AppConfig](../../src/main/scala/com/example/graphQL/cats/config/AppConfig.scala) loads typed PureConfig/HOCON settings and validates them before runtime construction. [Packaged defaults](../../src/main/resources/application.conf), normal `config.file`/`config.resource` selectors and HOCON substitutions control loading. `.local/config/` is an ignored storage convention, not an automatically loaded directory.

Mongo setup creates/verifies owned collections, indexes, validators and versioned migrations. Startup preserves data unless `mongo.reset-on-start` is explicitly enabled. Vector search, operational Kafka publisher/consumer and interview processing have configuration-dependent activation. Voyage provides embeddings when enabled. Interview runtime wires durable fake calendar/notification providers. Spark/Delta runs separately with batch and opt-in continuous modes. Enabling a component does not establish external acceptance.

Use the [README](../../README.md) for startup, [MongoDB design](../mongodb-design.md) for migration/index evidence and [analytics architecture](../big-data-architecture.md) for activation gates. Machine-specific settings, datasets, logs and backups belong in ignored local paths. Existing packaged logging uses `_logs/`, as documented in [engineering quality](../engineering-quality.md).

## Kafka consumer receipt window

The operational consumer starts only when its receipt TTL is at least the operational topic's `retention.ms + segment.ms` plus one hour ([duplicate delivery containment](../specs/duplicate-delivery-containment.md)). The gate also runs on a running consumer every 5 minutes (`ReceiptWindowRecheck`), so an operator who raises `retention.ms` on a live topic is detected long before any receipt written in the meantime can expire. The hour absorbs Kafka's deletion-check delay, `segment.jitter.ms` (default 0) and producer clock skew (the bound uses producer `CreateTime`); a deployment with a large jitter needs a longer receipt TTL. Packaged values: retention 7 days, segment roll 1 day, receipt TTL 9 days (`kafka.consumer.receipt-ttl-days`). `-1` retention is refused.

Access: the consumer reads the topic configuration with the reader principal `analytics_reader`, which is shared with the analytics worker. `docker/kafka/provision-access.sh` grants it READ and DESCRIBE on `hiring.operational-events`, and the topic's DESCRIBE_CONFIGS operation on that topic only (spelled `DescribeConfigs` for `kafka-acls.sh`, which refuses `DESCRIBE_CONFIGS` for a topic). A denied or failed read stops the consumer before it reads any record.

Refusal and diagnosis: a refusal records no beat, so `kafka-consumer` becomes degraded after the staleness limit. Readiness still answers by its Mongo rules; the component is listed in `degraded`. A refusal at a recheck stops the running consumer, and no further record is read until a restart passes the start gate. Each refusal, at the start gate or a recheck, emits `CONSUMER_RECEIPT_WINDOW_REFUSED` (ERROR) with `retentionMs`, `segmentMs` and `receiptTtlMs` (milliseconds, so `-1` stays visible) and `windowRefusal` (`RetentionUnbounded` or `WindowExceedsReceiptTtl`); the log sink allow-lists exactly these values, so any other value renders `[FILTERED]`. Then `RUNTIME_FAILED` with the exception class and source location. An unreadable configuration (ACL denied, broker unreachable, missing or non-numeric entry) reports `RUNTIME_FAILED` with `TopicConfigUnreadable` and no window numbers. Retries repeat with the restart jitter capped by `kafka.restart-max-delay-seconds`, and the configuration is read again on each attempt, so a corrected topic is picked up without a process restart.

Rollout order: alter the topic first. `docker/kafka/provision-access.sh` is idempotent and runs on each local stack start; it sets `segment.ms=86400000` and grants the topic's DESCRIBE_CONFIGS operation (`kafka-acls.sh` spelling `DescribeConfigs`). For a deployed broker these are operator changes outside this repository, and local evidence does not prove them. If the application is deployed first, the consumer stays refused until the topic changes; it does not consume with an unsafe window.

Offset expiry and resets: a group whose offsets expire or are reset rereads what the broker still retains (`auto.offset.reset=earliest`). Each reread is deduplicated by the same receipt rule, so the window does not depend on `offsets.retention.minutes`, and the gate does not read that broker setting (it would need cluster-level DESCRIBE_CONFIGS). A quiet topic is bounded too: the broker deletes an expired active segment without a later append.

Residuals (see the specification): for 14 days after the topic change, records produced before it can stay readable up to 14 days. Receipts stored before the TTL change keep their 8-day expiry unless a later duplicate delivery extends it. A duplicate delivery extends a receipt's `expiresAt` to that delivery plus the TTL and never shortens it, so a re-sent outbox event after a long publisher outage is still deduplicated.

## Kafka authentication (SCRAM-SHA-512)

Decision (2026-11-04, [Kafka flow hardening](../specs/kafka-flow-hardening.md)): Kafka clients authenticate with SASL/SCRAM-SHA-512 instead of PLAIN. Reason: PLAIN keeps every client password in the broker's JAAS configuration; SCRAM stores salted, iterated credentials in cluster metadata and lets a credential rotate without a broker restart. The application default is `kafka.sasl-mechanism = SCRAM-SHA-512` (`KAFKA_SASL_MECHANISM`; `KafkaClientSettings` emits the matching login module), the analytics default is `analytics.kafka.sasl-mechanism` (`ANALYTICS_KAFKA_SASL_MECHANISM`). The application accepts `SASL_PLAINTEXT` only for loopback bootstrap servers (`KafkaConfigValidation.scala` lines 11 and 182–192), and PLAIN on any transport only for loopback (`validKafkaSaslMechanism`, lines 165–180). The analytics build accepts PLAIN only together with `SASL_PLAINTEXT` and `analytics.kafka.allow-plaintext=true` (`allowPlaintext`), and only for a loopback or `kafka:9092` broker (`analytics/src/main/scala/com/example/hiring/analytics/config/KafkaConnection.scala` lines 63–71 for PLAIN, 72–81 for `SASL_PLAINTEXT`). Its config load also runs `KafkaConnection.preflight` (`AnalyticsRuntimeConfig.scala` lines 172–183), which resolves any host other than `kafka:9092` and requires loopback addresses for `SASL_PLAINTEXT` (`KafkaConnection.scala` lines 89–105 and 113–120). A production configuration therefore cannot reach PLAIN or plaintext transport silently; each needs an explicit opt-in and a local broker.

Local broker layout (`compose.yaml`, `docker/kafka/broker-entrypoint.sh`, `docker/kafka/provision-access.sh`; the test stack in `compose.test.yaml` mirrors it): the EXTERNAL listener (host clients) accepts SCRAM-SHA-512 only; the INTERNAL listener (Compose network, inter-broker traffic, provisioning admin) accepts SCRAM-SHA-512 for clients plus PLAIN whose JAAS knows only the broker principal; the CONTROLLER listener is PLAIN with the broker principal only. The broker principal stays on PLAIN because the image formats its KRaft storage itself and no SCRAM credential can be bootstrapped at format time there. `kafka-acl-init` creates the six client credentials (`hiring_publisher_v2`, `analytics_reader`, `analytics_fencer`, `interview_command_publisher`, `interview_result_publisher`, `interview_fencer`) with `kafka-configs --alter --add-config-file`, passing each credential through an owner-only temporary properties file so the password never appears on a command line, in container metadata or in process listings; it runs on every stack start, so rotating a secret file and rerunning `kafka-acl-init` rotates the credential, and it stops with the tool's error after a bounded number of attempts instead of retrying forever. The per-listener JAAS environment names write `-` as `___` (the image maps `___` to `-`). The listener layout, the SCRAM-accepted/PLAIN-refused behaviour and the bracket-free `--add-config-file` credential form were observed on the isolated test stack on 2026-11-05, whose `initialize` service (`compose.test.yaml`) runs the same credential command inline: interview suites 10/10, `kafka` suites 10/10, analytics 24 passed. `kafka-acl-init` (`provision-access.sh`, the local `compose.yaml` stack) stopped at the `--operation DESCRIBE_CONFIGS` line on 2026-11-08, the first start the operator observed. `kafka-acls.sh` on apache/kafka:3.9.2 refuses that spelling for a topic and accepts `DescribeConfigs`. The broken spelling dates from commit `7ac0bf1` (2026-11-03), so earlier local starts since then probably failed the same way without a visible signal, because only the analytics workers wait on `kafka-acl-init` completing (`compose.yaml` lines 53–57); this is an inference. With the corrected spelling the operator's rerun exited 0 (terminal output, one workstation, not an independent capture; see the [Kafka flow hardening checkpoint](../specs/kafka-flow-hardening.md#checkpoint-and-review)).

Production guidance (recommendation, not verified in this repository): `SASL_SSL` on every listener including the controller; bootstrap SCRAM credentials for inter-broker and controller traffic with `kafka-storage format --add-scram` and remove PLAIN entirely; provision with a dedicated admin principal, never the superuser; SCRAM iterations of at least 4096 and a rotation schedule; keep `allow.everyone.if.no.acl.found=false` and the prefixed transactional-id ACLs.

## Producer worker identity

Each publisher instance has a worker id (`kafka.publisher.worker-id` / `KAFKA_WORKER_ID`, `kafka.interview.worker-id` / `INTERVIEW_WORKER_ID`; pattern `[a-z0-9][a-z0-9-]{0,63}`, validated at startup). It forms the stable Kafka transactional id (`hiring-publisher-<id>`, `hiring-interview-orchestrator-<id>`, `hiring-interview-worker-<id>`), so a restarted instance fences its predecessor through Kafka's producer epoch. Rules: one worker id per running instance, taken from a per-instance identity such as a pod ordinal, never from an environment variable shared by all replicas; two instances with the same id fence each other in a loop. A single fence is expected and harmless: account erasure and operator retirement fence the running publisher's transactional id, which restarts one generation; only repeated fences within minutes (alert `HiringKafkaProducerFenced`, counting `ProducerFencedException` and `InvalidProducerEpochException` send failures over 15 minutes; the local pipeline carries no per-instance label, so the count is across the deployment) point at a shared worker id. One local operator drill on 2026-11-08 (two publishers sharing `fence-drill`) saw the alert fire 40m12s after the drill started, deliver to the ticket receiver, and resolve 9m32s after one publisher was stopped. That is one measurement on one workstation, not a general latency: the 40m12s includes the time for the count to reach and hold at least 3. The drill is not reproducible from the repository. Its publishers used host networking, a drill-only workaround for the loopback-only SASL rule and not a deployment pattern, and listened on every host interface in both recorded runs. The git-ignored drill configuration was later edited to bind the publishers to 127.0.0.1; that edit was not run. Details and sources: [Kafka flow hardening checkpoint](../specs/kafka-flow-hardening.md#checkpoint-and-review). Operator retirement of a transactional id (`ProducerGenerationRetirementMain`) fences a live process and leaves its successor's registrations Active; see [MongoDB design](../mongodb-design.md#producer-generation-registry-ledger-step-036).

## Health and observability

`GET /health` reports liveness. `GET /ready` returns 503 only for a failed Mongo ping or an open Mongo-writes breaker; other components, including the enabled embedding worker, stalled background workers and aged outbox or closure work, are listed in the 200 body's `degraded` array (alert on it; keep the path off the public edge). It does not prove Kafka freshness, real interview delivery, analytical retention completion or search relevance. [TelemetryRuntime](../../src/main/scala/com/example/graphQL/cats/infrastructure/telemetry/TelemetryRuntime.scala) composes OpenTelemetry tracing/metrics; [Diagnostics](../../src/main/scala/com/example/graphQL/cats/service/Diagnostics.scala) defines structured events/fields and correlation.

Local alert delivery is opt-in and workstation-only: Prometheus evaluates the rules in `docker/observability/alerts.yaml`, and a local Alertmanager sends `page` and `ticket` alerts to two local receivers that only log them. The rule tests, the fault drills and their limits are in [local observability](../local-observability.md#alert-rules-routing-and-drills). Alertmanager's API and the alert sink are unauthenticated, so this is for a single-user workstation only. No production routing, on-call contact or paging provider is defined, and no rule in `alerts.yaml` reads the `degraded` list of `/ready`.

Durable failure states, quarantines, revision conflicts and repair states expose recovery needs. Repair should follow the owning workflow contract rather than arbitrary document edits. Analytics persistent writer/maintenance ownership can intentionally require operator reconciliation instead of automatic takeover.

## Embedding coverage report

`embeddingCoverage(expectedModel)` is the Admin's read of embedding health for searchable Jobs and Candidates. It is Admin-only and read-only: the service checks the live Admin record, and the query writes, enqueues and repairs nothing. The response holds counts, ages, lag percentiles and two named checks (`NO_ORPHANED_GAP`, `NO_STUCK_WORK`). It holds no ids, names, text, vectors or provider payloads. Non-Admin callers receive `UNAUTHORIZED`; with vector search disabled the caller receives `VECTOR_SEARCH_UNAVAILABLE`, not zero counts.

How to read it:
- Freshness (`freshness`) and repair state (`repairState`) are separate dimensions. Read them together: an entity can be non-current with work queued, which is expected while repair runs. Only a non-current entity with no queued work (orphaned gap) can never be repaired.
- A check is `PASSED` only when its scan was complete. If the bounded scan reached its cap (`truncated`, `queueTruncated`), the check is `INCONCLUSIVE` and its offending count is a lower bound.
- The entity pages read each entity with its queue row at one point in time under snapshot read concern. The database must be a replica set or sharded cluster. A standalone server fails the query, which is the intended fail-closed result.

Pass `expectedModel` set to the configured embedding model. Without it, an embedding from a previous model counts as `Current`, while semantic search returns only the configured model's embeddings. After a model switch, the default report can therefore show full coverage that search does not deliver. The code does not enforce this advice.

Sizing is measured locally only: a full scan of 36,000 searchable entities (18,000 Jobs and 18,000 Candidates) took 3.8 to 10.8 s on a disposable MongoDB 8.0 replica set. The HTTP `request-timeout-ms` default is 5000, so a scan at that size can time out. The cap, page size and timeout for a cloud deployment are an open decision. See the [specification](../specs/embedding-coverage-report.md) and the [API reference](../api.md#embedding-coverage-report).

## Validation and readiness

The [root build](../../build.sbt) separates unit `test` from live HTTP/disposable MongoDB `IntegrationTest / test`; analytics has its own build. Local checks establish only exercised behavior on that source/environment. Atlas fusion/reranking, real providers, genuine Kafka/Delta retention, external-writer exclusion, key retirement and deployed SLOs have additional [roadmap gates](../development-milestones.md).

This wiki is source-derived documentation. Its validation covers source correspondence, local links and required root unit/format checks. It does not activate services, reset data, rerun live provider/Atlas checks, or refresh historical analytics benchmarks.
