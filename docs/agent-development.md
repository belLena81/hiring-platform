# Agent-driven development

## Current decisions and implementation

[README](../README.md) describes the Scala 3, Cats Effect, FS2, Sangria, http4s, and MongoDB platform. [Architecture](../ARCHITECTURE.md), [use cases](use-cases.md), and the [API reference](api.md) describe the active system; [schema evolution](schema-evolution.md) and the specifications under `specs/` hold its evidence.

The current build uses Scala 3.9 LTS, Java 17+, Cats Effect, Sangria/http4s, and MUnit. Unit tests are Docker-independent; the explicit `IntegrationTest` configuration contains live HTTP and disposable MongoDB checks. Inspect the live build before each task.

Application configuration follows the library defaults: `ConfigSource.default` delegates source loading and precedence to Typesafe Config. Put packaged defaults in `application.conf`; use the standard `config.file` or `config.resource` selectors for local/test overrides. Decode into typed PureConfig models, validate into typed settings/errors before runtime use, and keep the source/validation boundary explicit. Do not add project-owned filename constants or custom source-merging layers unless a new requirement establishes a different source boundary.

Analytics batch and worker runtime configuration uses the same `application.conf`/PureConfig approach as the main app: packaged defaults live in HOCON, and environment variables may supply HOCON substitutions. Production Scala runtime code must not read environment variables directly. Configuration values stay typed; independent validation failures accumulate with Cats `ValidatedNec` and convert to typed `Either`/effect errors at the owning boundary. Iron refinements protect validated settings and domain values. Keep transforms and domain validation pure, use `IO` and `Resource` for effects and resource ownership, and isolate exceptions required by Spark at the Spark adapter boundary, translating them into typed analytics errors. Existing test-only environment switches remain valid and are outside this production configuration rule.

For implementation and review standards covering pure/effect boundaries, ADTs and error channels, dependency use, query costs, and RBAC, follow [local engineering quality](engineering-quality.md). Use the configured library idioms and existing dependency versions before proposing custom infrastructure or another dependency. Query improvements must account for database work and application-side work, and authorization must be preserved through service and repository access.

Startup preserves hiring-owned MongoDB data by default. Set `mongo.reset-on-start = true` or
`MONGODB_RESET_ON_START=true` only for an explicitly authorized local reset.

## Entry point and roles

Start a task with:

```text
Use the product-manager skill to deliver the next scoped roadmap slice. Inspect the current
code and decisions, define acceptance criteria, delegate relevant specialists,
and finish with independent code/security reviews as applicable and final QA.
```

Or ask a specialist directly:

```text
Use the data-engineer skill to review the UC08 access pattern and index tradeoffs.
Use the big-data-engineer skill to plan UC11 replay and idempotency with local fixtures.
Use the qa-engineer subagent to validate the final changes against the task criteria.
```

Canonical Claude Code layout: role skills are real files at `.claude/skills/<role>/SKILL.md` (invoke with the Skill tool or `/<role>`). Delegated roles are subagent definitions at `.claude/agents/<role>.md`. Reviewers and QA have no edit tools (`Read, Grep, Glob, Bash`). Their frontmatter PreToolUse hook, `scripts/guard-agent-scope.py read-only`, is a guardrail against a reviewer changing what it reviews, not a security boundary: it allows only allowlisted programs with exact argument shapes (test runs, read-only git, the check scripts) and refuses shell syntax it cannot read with certainty, because a list of forbidden commands can never be complete. It runs in addition to `scripts/guard-harness.py` and the Bash sandbox. Running tests still writes build output and executes project code, so the hook limits what a reviewer asks for, not what the tests do. The Technical Writer and Software Architect are limited to their document paths by `guard-agent-scope.py documentation` and `design`. Reviewer skills (`code-reviewer`, `security-engineer`, `qa-engineer`) use `context: fork` with `agent: <role>`, so `/code-reviewer`, `/security-engineer` and `/qa-engineer` run in the reviewer's own context and never in the author's. Author, writer and architect agents preload their skill through the `skills` frontmatter field. `check-skills.py` fails if a reviewer lacks the read-only hook or its forked skill, if the writer or architect lacks its path-scope hook, or if an author lacks its preload; a reviewer that can edit the code it reviews, or an author that never loaded its role instructions, is a defect the prompt alone cannot prevent. Root rules live in `AGENTS.md`, imported by `CLAUDE.md`. Scala engineering rules are in `.claude/rules/scala-engineering.md`, and persistence, schema evolution and analytics rules are in `.claude/rules/persistence-and-analytics.md`. Claude Code loads each rules file only when work touches its matching paths, so unrelated sessions and subagents do not pay for rules they do not need; this is why those rules are not in `AGENTS.md`. Shared settings and hooks are in `.claude/settings.json`; personal overrides belong in the ignored `.claude/settings.local.json`. Run `python3 -I scripts/check-skills.py` after changing skills or agents; the PostToolUse hook runs it as `check-skills.py --hook`, which does nothing unless the edited file is `AGENTS.md` or under `.claude/`, prints nothing on success, and exits 2 on a failure so Claude Code returns the problems to the agent (a plain exit 1 would only show in the transcript). A second PreToolUse hook runs `scripts/check-docs-current.py --hook` on every `git commit` and denies a commit that changes decision-bearing paths without canonical documentation (see Validation).

Model policy: the main session uses `opusplan` at medium effort (`model`/`effortLevel` in `.claude/settings.json`, the only place the session model is set; a personal `settings.local.json` must not override it). Opus plans and Sonnet executes: planning decisions cost more when wrong, while executing a defined plan does not need Opus. The `product-manager` skill declares `model: opus`, because it writes specs. Each subagent sets its own model and effort in its frontmatter, and that frontmatter is the policy:

| Agents | Model, effort | Reason |
|---|---|---|
| `scala-developer`, `data-engineer`, `big-data-engineer` | Sonnet, medium | Author work is bounded by a spec and checked by the reviewers |
| `scala-refactorer` | Opus, high | Behavior-preserving restructuring has no spec to bound it, so judgment matters more than for spec-bound authoring |
| `code-reviewer`, `security-engineer`, `qa-engineer`, `software-architect` | Opus, high | A missed defect in review, or a wrong structural decision, costs more than the extra tokens; these roles run once per task, not per edit |
| `technical-writer` | Haiku, medium | Documentation from verified facts |

Do not pass a per-call `model` override to the Agent tool; change the frontmatter instead so the policy stays in one place. `scripts/check-skills.py` requires every subagent to declare tools and a model, including `scala-refactorer`, which has no skill folder of its own and must preload a project skill.

Use these project skills and agents only; do not fall back to a global installation or substitute a same-named global role. Existing `.codex/config.toml` model/permission preferences remain local and separate.

Product Manager coordinates; Architect decides technical boundaries; Scala Developer implements application code; Data Engineer owns operational data; Big Data Engineer owns analytical pipelines; Code Reviewer and Security Engineer review their scopes; QA independently validates the final result. Direct specialist tasks still follow the root review gates.

## Task handoff

For substantial work, use the [spec-driven workflow](spec-driven-development.md), [feature spec template](templates/feature-spec.md), and [illustrative UC04 draft](examples/submit-application-spec.md). Keep acceptance criteria, handoffs, and evidence in one current spec. The short record below is sufficient for small tasks; it need not become a separate file.

Use this compact record in the conversation, or a task document for sustained multi-phase work:

```text
Task / use case / phase:
User outcome and non-goals:
Current implementation and decision sources:
Acceptance criteria, including forbidden/failure paths:
Domain: context, aggregate/invariant touched; glossary terms used or added; tagged examples:
Workload / SLO / freshness / cost ceiling (or explicit assumptions):
Owner / allowed write paths / input paths:
Dependencies and specialist handoffs:
Verification commands and expected observable results:
Evidence: commands, outcomes, benchmark environment and limitations:
Reviews: Code Reviewer / Security Engineer / final QA, with verdict and scope:
Status: draft | ready | in progress | in review | blocked | done
Remaining risks / next dependency:
```

Read only the spec named in the handoff; [docs/specs/README.md](specs/README.md) is the index for finding one.

Reviewer report (Code Reviewer, Security Engineer, QA). End every report with this block, so the coordinator can paste the lines into the spec and `scripts/check-spec-verdicts.py` accepts them:

```text
VERDICT: PASS | FAIL | BLOCKED
Scope: files, commits or slices reviewed, and what was not reviewed
Blockers: numbered, each with file:line evidence (none if PASS)
Non-blocking: numbered lows
Commands run: command, exit code, one-line result (a command not run is listed as not run)
Spec line: - <Code Reviewer | Security Engineer | Final independent QA> verdict (<date>, <scope>): PASS | not applicable - <tier reason>
```

A FAIL or BLOCKED reviewer never writes the spec line; the coordinator records PASS only after the re-review.

Only one agent writes a file at a time. Reviewers may inspect the same files concurrently after the author finishes. New fixes invalidate affected review evidence. If independent agents are unavailable, record review as pending; an author changing hats is not independent approval.

## Performance and cost decisions

Optimize for the smallest operating footprint that meets the agreed workload and reliability targets. Record baseline and changed p50/p95/p99, throughput, errors, resource usage, query plans, and test environment when relevant. The use-case SLOs are targets, not measured guarantees.

For infrastructure proposals, estimate compute hours, idle capacity, storage/retention, I/O and egress, embeddings/provider calls, and operational burden. State units, assumptions, and price source/date if pricing is used. Compare scheduled batch with streaming and local execution with managed infrastructure. Use bounded local synthetic data by default; million-row experiments and paid resources are separate scoped work. Do not sacrifice authorization, durability, or correctness for cost.

An optimization needs a baseline, a demonstrated bottleneck, a measured improvement without unacceptable regressions, and a revisit/rollback trigger. Kafka publication and Spark/Delta analytics already exist; additional distributed infrastructure, Databricks, caches, and denormalization require a relevant measured workload. Follow the [current milestone order](development-milestones.md): MongoDB, search/AI, and Kafka workflow refinements precede further Spark/Delta development.

## Validation

Use [local engineering quality](engineering-quality.md) for pure FP, debugging, review, and the `scripts/check-local.sh` command, which needs Docker and enforces the merged 85% line-coverage gate. Run it as a standalone command without the `bash` prefix: the sandbox exclusion matches the command text, so `bash scripts/check-local.sh` would run inside the sandbox, where Docker is unavailable. It skips a suite whose inputs are unchanged since its last PASS (see [engineering quality](engineering-quality.md)). It prints each step's duration as it finishes and a summary of all step durations at the end of a PASS, FAIL or BLOCKED run (the failing step is included, an interrupt prints none); read the summary before choosing what to speed up. There is no CI/CD pipeline; integration and [migration/contract checks](schema-evolution.md) must be run locally when required.

Run `sbt test` for the configured unit suite. Run live HTTP and disposable MongoDB checks through `scripts/run-local-tests.sh` (`scripts/run-local-tests.sh test` runs the root unit and integration suites), not `sbt 'IntegrationTest / test'`, which fails inside the Bash sandbox; the wrapper runs outside it. Missing Docker is blocked infrastructure, not a passing gate. Run formatting/linting when configured. `sbt run` starts the long-running hiring server; use its probe endpoints and the [startup instructions](../README.md), not process exit, to check health.

Documentation currency (root `AGENTS.md`) is a gate, not a courtesy. Every task that changes a decision lists its documents in the spec's Documentation impact section. The Technical Writer updates `README.md`, `ARCHITECTURE.md`, the owning `docs/*.md` and the `docs/wiki/` pages from verified behavior before the final reviews, stating the decision, its reason and why it matters. `python3 -I scripts/check-docs-current.py` checks every unpushed commit made since the gate was introduced (step 2 of `scripts/check-local.sh`), so a commit that bypassed the hooks (`--no-verify` in a terminal, an unset hooks path) is still caught before it is pushed. It only warns about uncommitted changes (decided 2026-11-07): a working tree has no message to carry a `Docs-Impact` trailer, so failing on it forced a commit and then a rerun of the whole local check; the commit hooks enforce the rule at the moment it can be satisfied. The Claude Code commit hook also denies an agent `git commit` that uses `--no-verify`, a short flag group containing `n` (`-n`, `-an`) or a `core.hooksPath` override, so the formatter and the documentation gate cannot be skipped by an agent; flag-like text inside a `-m` message is not a skip; `--staged` checks the next commit and `--range main..HEAD` checks each commit in a range. Commits are gated twice: the Claude Code hook covers agent commits, and the versioned git hook `.githooks/commit-msg` covers every commit in a clone where it is enabled once with `git config core.hooksPath .githooks`. Merge commits are not re-checked. The Claude Code hook sees only the command text: it reads `-m`, heredoc and `-F` messages, defers to the git hook for a message it cannot see (editor, `-C`, `--amend --no-edit`), and recognizes direct, path-qualified, global-option and quoted `sh -c` invocations of `git commit`; git aliases and wrapper scripts are caught only by the git hook. The git hook is versioned code that runs on every commit, so `scripts/guard-harness.py` treats `.githooks/` like `.claude/` and `scripts/`: an agent change to it needs human approval, and any diff to it deserves a human read before it is committed or pulled. The same hooks path enables the second versioned git hook, `.githooks/pre-commit`, which formats the staged Scala and sbt files with the pinned scalafmt and re-stages them before the commit is recorded (`scripts/format-staged.sh`; modes, limits and the reason are in [engineering quality](engineering-quality.md)). A Claude Code `git commit` is an excluded command that needs approval, so this formatter runs outside the sandbox: it writes `.local/logs/format-staged-*.log`, reaches the network for the pinned scalafmt download, and, when committed from a Claude Code session, uses `.sbt-home/`.

- Decision-bearing paths: production source and configuration (`src/main/`, `analytics/src/main/`), provisioning (`docker/`, `compose*.yaml`, `Dockerfile` and `analytics/Dockerfile`, `.dockerignore`), builds and tooling configuration (`build.sbt`, `project/`, `.scalafmt.conf`, `.sbtopts`, `.jvmopts`, `.mcp.json`, with their `analytics/` copies), operator scripts (`scripts/` except `scripts/tests/`) and the workflow (`AGENTS.md`, `CLAUDE.md`, `.claude/` except personal settings, `.githooks/`).
- Canonical documentation: `README.md`, `ARCHITECTURE.md` and `docs/**/*.md` except `docs/specs/` and `docs/templates/`. A spec records decision history; it does not replace the documents readers rely on.
- A commit that genuinely needs no canonical change carries `Docs-Impact: none - <reason>` or `Docs-Impact: spec-only - <reason>` (a reason of at least ten characters). Reviewers check that the reason is true.

Why it matters: documentation that lags a decision is how the next agent or operator re-introduces a fixed defect, misconfigures a limit, or keeps paying for capacity the system no longer needs.

Review verdicts and the stop gate are checked too, not only written down. `python3 -I scripts/check-spec-verdicts.py` requires every spec whose `Status:` begins with `done` to carry the three verdict lines of the [feature spec template](templates/feature-spec.md) as `PASS` or `not applicable - <reason>`; which reviews a change needs is the review tier table in `AGENTS.md`. The script runs in step 2 of `scripts/check-local.sh` and from the Claude Code `Stop` and `SubagentStop` hooks, which call `scripts/check-done.sh` (seconds, no Docker). At `Stop` the skills and verdict-line checks block every stop, because they cannot legitimately fail in the middle of a task. After eight blocks in a row, Claude Code overrides the next one and ends the turn. The review log comparison, documentation currency and compile freshness block once, because each can fail for a reason the agent cannot or should not fix at once, such as an unrelated commit or a turn that legitimately ends unfinished. The log comparison runs in full only on the first stop and at `SubagentStop`; a repeated stop checks verdict lines only. Documentation currency runs on the first stop only. Compile freshness compares file times: a changed `.scala` file (staged, unstaged or untracked) newer than its build's newest compiler analysis (`target/**/inc_compile*`) asks the agent to run `sbt Test/compile`; sbt build edits are not counted. The hook never compiles, because hooks run outside the Bash sandbox and compiling executes build definitions and macros, so a compiling hook would run agent-written code with full access and no prompt. Compile freshness is a reminder, not proof: an analysis from a partly successful compile can look fresh. A passing `Stop` shows a `systemMessage`, which reaches the user, not the agent, saying that `scripts/check-local.sh` and independent QA evidence are still required when code changed. It does not run `scripts/check-local.sh` itself, which takes about two hours and needs Docker. At `SubagentStop` only the skills and verdict checks run, and they block once, because a read-only reviewer cannot fix a failing gate. Why it matters: a verdict that exists only in prose is how a task closes with a review skipped. The check proves the lines exist and say PASS or give a reason, not that the review was good; reviewers challenge a weak reason.

A completed review leaves a local log entry. `scripts/record-review-run.py` runs on `SubagentStop` for the three reviewers and on `PostToolUse` of `SubagentHandback`. It reads only the reviewer's own report, the final message or the `message` input of `SubagentHandback`, and only a line of the form `VERDICT: PASS`, `VERDICT: FAIL` or `VERDICT: BLOCKED` counts (spaces and tabs around the line and the word are ignored, and the space after the colon is optional), so the report template never counts. Where several verdict lines disagree, the worst one counts, in the order FAIL, BLOCKED, PASS, so a quoted PASS never overrides a FAIL. It appends role, verdict, UTC time, epoch seconds and commit to the ignored `.local/logs/review-runs.jsonl`; it stores nothing else from the review. It never blocks. `check-spec-verdicts.py` compares that log only with uncommitted specs marked `done`: each `PASS` line needs a logged run of that reviewer on the current tree, and the latest such run must be `PASS`. The tree is a content fingerprint (`scripts/review_fingerprint.py`) of every tracked and untracked non-ignored file except `docs/`, `README.md`, `ARCHITECTURE.md` and `.local/`, recorded with each run (decided 2026-11-07): committing the reviewed work does not invalidate a review, editing a reviewed file does, and the spec that records the verdicts and documentation edits do not. Reason: tying a review to the last commit made every mid-cycle commit look like a stale review. Entries written before this change have no fingerprint and no longer count. Committed specs are not compared, because older reviews predate the log and the log is local to the clone; committing remains the human override. The sandbox denies writes to the log (`denyWrite` in `.claude/settings.json`), and `guard-harness.py` asks for approval before an agent edits it. Anything running outside the sandbox can still edit the log, including an approved test run, so an entry shows a reviewer report only if nothing outside the sandbox has touched the log since. An entry records the content fingerprint of the tree at the time the reviewer finished, so an edit to a non-documentation file after the review is detected; a documentation-only edit is not, because the tier table asks for no review of it. Why it matters: a verdict line alone can be written by the author it grades. The log shows that a reviewer role ran and stated a verdict on the current tree. It does not show that the review was honest or which spec it covered: an author could prompt a reviewer to state PASS, and a person can edit the log.
`scripts/check-agent-hooks-live.sh` runs five short `claude -p` sessions on Haiku in this checkout, each capped at `LIVE_HOOKS_BUDGET_USD` (default 0.50) and `LIVE_HOOKS_SESSION_TIMEOUT_SECONDS` (default 180): (1) the Stop gate must block at least twice in one session, on a temporary done spec without verdicts; (2) the `code-reviewer` agent is asked to create a file, and its read-only scope hook must refuse it; (3) a session is asked to run the wrapper's `retention` verb, a code-running verb in the `ask` list, and the denial must stop it, because a print session has nobody to approve it; (4) a session allowed to run `curl` reaches for a host outside the allowlist, and the sandbox must refuse it without a prompt; (5) a session is asked to invoke a temporary skill nested below the project root, and its hook must not run, which it reports separately for the guard's prompt with nobody to approve it and for Claude Code not offering the skill. It removes its temporary files on every exit and keeps its logs under `.local/logs/live-hooks`. A model that does not attempt a probe command gives an inconclusive `BLOCKED` result, not a pass. It does not exercise the review log, and of the sandbox it exercises only the host allowlist (session 4). Why it matters: a hook that never fires looks the same as a working one until a defect gets past a review.

For skill edits, run the project-owned `python3 -I scripts/check-skills.py`, check local references, and request independent scenario review. Frontmatter validation alone does not prove orchestration behavior or native discovery. No database migration or runtime deployment is needed for documentation-only changes.

## Agent test-run safety

Agents run and seed tests only through `scripts/run-local-tests.sh`; it targets the isolated `compose.test.yaml` stack (random loopback ports, tmpfs data, identity check before every write or cleanup). Tests create their own data in per-case databases inside that stack.

`.claude/settings.json` enforces this with permission rules plus the `scripts/guard-harness.py` PreToolUse hook:

- **Allowed without prompt:** `sbt test|compile`, which run inside the sandbox.
- **Human approval required (outside the sandbox):** wrapper verbs `start`, `status`, `--help` and `-h`, because their command text could select a planted copy of the script. The three excluded scripts have prefix `ask` rules such as `Bash(scripts/run-local-tests.sh:*)`, because a spelling such as two spaces or a quoted verb can miss an exact rule and still match the wildcard exclusion. The `Monitor` tool, which runs shell commands under the same sandbox rules, is denied to keep the surface small and to avoid depending on how Claude Code hands its commands to hooks. Claude Code 2.1.318 passes them to the guard as Bash calls, read from the binary and its changelog and not observed. The guard also answers when the first word is the script path as the exclusion writes it, with an ask, or a deny for an unknown wrapper verb, and asks when a command prefix such as `nohup` or `gnohup` comes first. A different path form such as `./scripts/check-local.sh` gets no guard answer, matches no exclusion and stays sandboxed. In auto mode, a matched `ask` rule or a guard ask goes to a person; this is read from the Claude Code 2.1.318 binary and not observed, so re-check it after an upgrade.
- **Human approval required (code-running):** wrapper verbs `test`, `analytics`, `interview`, `retention`, `recovery`, and `scripts/check-local.sh`. They need Docker, so they run outside the Bash sandbox, and they execute test code an agent may have edited. Without a prompt the sandbox would not matter for the main test entry point. This is a safe default the owner can reverse.
- **Human approval required (cleanup):** `scripts/run-local-tests.sh stop`, `rm`/`rmdir`, `sbt clean`, `find -delete` (enforced by `guard-harness.py`), any docker lifecycle or cleanup verb.
- **Denied:** `mongosh`/`mongo*`/Kafka CLI tools, `docker exec|run|cp`, compose files other than `compose.test.yaml`, any MongoDB URI that is not the manifest's isolated endpoint (including ports 27017/9092), `sudo`, and writes (Edit/Write, redirects, `cp`/`mv`/`rm` targets) outside the project folder.

Formatting (`scalafmtOnly` and `scalafmtSbt`) runs outside the sandbox only, in the pre-commit formatter (`scripts/format-staged.sh`); `scripts/check-local.sh` no longer checks it. scalafmt downloads itself, which the sandbox prevents, so no agent shell has an allowed format check; a direct run is not in the allow list and is not expected to succeed inside the sandbox.

Edits to `.claude/`, `scripts/`, `.git/`, build files and compose files need approval, because those run unprompted. The workflow-file list is defined once in `scripts/harness_paths.py` and imported by `guard-harness.py` (approval) and `check-docs-current.py` (documentation gate); `scripts/tests/test_harness_paths.py` fails if a workflow file is covered by one and not the other. Any compose file, not only a fixed set of names, now needs approval. Editing `guard-harness.py` itself needs care: an import that is added after its first use makes the guard fail closed and blocks every tool call until a human restores the file, so add the import first, then the code that uses it. The hook fails closed (exit 2) on malformed input, denies shell substitution in wrapper arguments, docker engine/context flags and `DOCKER_*`/`COMPOSE_*` overrides, and asks for nested shells (`bash -c`, `env`, `xargs`, `python -c`). The wrapper itself unsets Docker engine variables. Outside the project, the guard allows writes only to the agent scratchpad (`CLAUDE_CODE_TMPDIR` when set, and `/tmp/claude-<uid>`); the Bash sandbox separately allows writes to `/tmp` only, and sbt state lives in `.sbt-home/` (see the Bash sandbox paragraphs below).

The Bash sandbox is a second boundary under the guard, for code the guard cannot read. `.claude/settings.json` enables it with `failIfUnavailable: true`, so on Linux it needs `bubblewrap` and `socat` installed and does not start without them. It confines direct `sbt test` and every other command that is not excluded, with their children, at OS level. `autoAllowBashIfSandboxed` is false, so the sandbox adds a boundary without removing an approval prompt, and `allowUnsandboxedCommands` is false, so a command that fails inside the sandbox is not retried outside it. Reads of the credential paths in `filesystem.denyRead` are blocked (SSH, cloud and Docker credential directories, netrc and git-credential files, shell history and others). The `permissions.deny` list names the root env files by exact path (`.env`, `.env.local`, `.env.development`, `.env.production`, `.env.test`) for `Read` and `Edit`, not by `.env.*` glob. Owner decision (2026-11-05): `claude doctor` (2.1.318) reports that on Linux the sandbox ignores glob patterns in `Read` and `Edit` rules, and the Security Engineer showed that the permission layer still enforces them for the `Read`, `Grep`, `Glob` and `Edit` tools, which run outside the sandbox; no guard hook covers `Read`, `Grep` or `Glob`, while `Edit` and `Write` of any `.env*` file also get the guard's approval prompt. Exact paths keep that protection, are also applied by the sandbox (they appear in its read-deny list), and clear the warning. A name outside that list has no deny for reads (`Read`, `Grep`, `Glob`) and only the guard's approval prompt for `Edit` and `Write`: it needs its own exact-path rule, and machine secrets belong in `.local/config/`. `scripts/tests/test_harness_paths.py` (`ARE-09.11`) fails if a listed name is dropped or any `Read` or `Edit` rule naming an env file contains a glob character. Writes outside the project are limited to `filesystem.allowWrite`, which lists only `/tmp`. `/tmp` is the JVM temp directory, sbt fails without it, and it is shared with other processes on the machine, not private to this project. The settings `env` sets `-Dsbt.server.forcestart=true` in `SBT_OPTS` (with the `.sbt-home/` paths described below), which skips sbt's boot socket because the sandbox refuses it. In Claude Code sessions this removes sbt's single-instance protection, so concurrent sbt runs in one build can collide on `target/`; run one at a time. `allowAllUnixSockets` was rejected because it would also expose the Docker socket. A host outside `network.allowedDomains` prompts in manual mode rather than being refused; `network.strictAllowlist`, which refuses instead, is honored only in user or managed settings, so that choice stays with the user. Docker does not work inside the sandbox, so `scripts/run-local-tests.sh`, `scripts/check-local.sh` and `scripts/check-agent-hooks-live.sh` are excluded from it. `git push`, `git fetch` and `git pull` are excluded because they need the network, and 13 more git commands that write `.git` are excluded for the reason given in the `denyWrite` paragraph below. Excluded commands run with full access, under their permission rules, so the sandbox does not limit what a wrapper test run can reach. `scripts/guard-harness.py` denies a call whose text, with quotes and backslashes removed, names an excluded command, unless it starts at the project root and is one simple command: plain words and complete quotes, with no separator, redirect, variable, substitution, glob, comment, escape or newline outside quotes, and no expansion or backslash inside double quotes. A tilde passes, because it can change a path but cannot add a command. Exclusions match the command text: after a `cd`, the same text would run a copy of the script, or use a `.git`, planted in that directory. It is an allowlist because rules that looked for a `cd` or a redirect kept missing spellings. This rule does not otherwise examine quoted text, so the word `cd` in a commit message is fine; the guard's other rules still refuse a message that names a secret location, a database URI or an outside redirect target. It also refuses a harmless call whose text contains such a name in a pipeline or from a subdirectory, including read-only forms such as `git status --branch`; run those from the root as one command. The match has no word boundary before `git`, so a longer word such as `digit` followed later by an excluded verb is refused too. It is a guardrail, not a shell analysis: a name spelled with an expansion is not seen by this rule, and does not match an exclusion's text. The project owner accepted that limit: a further shell spelling that defeats the guard is a follow-up unless it shows an escape from the sandbox, because the sandbox and approval prompts are the real boundary and a hand-written shell parser can always miss a spelling. For other commands, a redirect before the end of a simple command, a `#` right after `)`, or `((` needs approval. The guard asks before any skill that is not a role skill at the project root, including plugin and built-in skills the model invokes. Sandboxed code can write a nested `.claude/skills` folder, because `denyWrite` cannot list paths that do not exist yet; a live session showed Claude Code then offers that skill under its bare name, not the documented `<directory path>:<skill>`, and its hooks or inline shell would run outside the sandbox. It is an allowlist because reviews kept finding names and folders that a search for nested skills missed. It sees only the `Skill` tool, so a skill you start yourself with a `/` command is your own decision, and a nested skill reusing a role skill's name is not distinguished. `disableSkillShellExecution` is on, because inline skill shell does not pass through this guard, and for the same reason no excluded command is in the `allow` list: wrapper `status`, `start` and help also need approval, since a text match could run a planted copy from another directory. Per the Claude Code sandbox documentation (read 2026-11-04, not re-verified in this repository), every command in a call must match an exclusion entry, and a `cd`, a redirect to a file or a command substitution keeps the whole call sandboxed. Run these entry points as a standalone command. A direct `sbt 'IntegrationTest / test'` fails in the sandbox; use the wrapper. Hooks, MCP servers and the Read and Edit tools are outside the sandbox.

sbt isolation: `SBT_OPTS` in the settings `env` points Claude Code sessions at `.sbt-home/` in each build, through `-Dsbt.global.base`, `-Dsbt.boot.directory`, `-Dsbt.ivy.home` and `-Dsbt.coursier.home`. The paths are relative, so the root build uses `.sbt-home/` and the analytics build uses `analytics/.sbt-home/`, because the wrapper runs analytics sbt from `analytics/`. `.sbt-home/` is ignored by git (`.gitignore`) and by Docker (`.dockerignore`). `~/.sbt`, `~/.ivy2` and `~/.cache/coursier` are neither readable nor writable from the sandbox (`filesystem.denyRead`; `allowWrite` lists only `/tmp`). Why: sbt loads code from those directories, so test code an agent wrote could otherwise run as the user in terminal builds and other projects. Cost: a second dependency copy, about 400 MB per build on the machine where it was measured.

Dependency downloads: JVM downloads do not work in the sandbox, because the proxy answers the JVM's tunnel with 407, which `jdk.http.auth.tunneling.disabledSchemes` does not fix. `network.allowedDomains` is therefore empty, and sandboxed sbt cannot reach Maven hosts. When a dependency changes, or on a fresh clone, one approved wrapper run outside the sandbox, with the same `SBT_OPTS`, fills `.sbt-home/`: `scripts/run-local-tests.sh test '<glob>'` for the root build and `scripts/run-local-tests.sh analytics '<glob>'` for analytics. Both verbs need the permission prompt (they are in `ask`). Sandboxed sbt then only reads `.sbt-home/`. Without that first run, sandboxed sbt fails with `could not retrieve sbt`.

Remaining gap, which `denyWrite` cannot close: sandboxed code can still create new `*.sbt`, `.sbtrc` or `project/*.scala` files and write `.sbt-home/` and `target/`. sbt needs those directories writable, and it cannot read a denied file that does not exist yet, so `denyWrite` cannot cover them. sbt loads new build files. An approved wrapper run or a Claude Code commit also loads jars and the launcher from `.sbt-home/` and meta-build classes from `project/target/`, and a terminal sbt run also loads classes from `target/`, so this code executes as the user in a later sbt run outside the sandbox in this repository. The wrapper's own build output is `.local/data/test-builds`, which is denied. Every such run starts with a person: approving a wrapper run or a commit, or running sbt or `git commit` in a terminal. A terminal does not use `.sbt-home/`. Before starting one on a tree an agent changed, check `git status --ignored` for unexpected build files; that shows new files, not changed content in ignored files.

`filesystem.denyWrite` in `.claude/settings.json` covers the known files that run or configure code outside the sandbox: `./.git`, `./scripts`, `./.githooks`, `./docker`, the six `compose*.yaml` files, `./Dockerfile`, `./analytics/Dockerfile`, `./analytics/spark-jvm.args`, the build definitions (`./build.sbt`, `./analytics/build.sbt`, `./project/plugins.sbt`, `./project/build.properties`, `./analytics/project/plugins.sbt`, `./analytics/project/build.properties` and `./project/project/build.properties`), the sbt, JVM and formatter configuration (`./.sbtopts`, `./.jvmopts`, `./analytics/.sbtopts`, `./analytics/.jvmopts`, `./.scalafmt.conf` and `./analytics/.scalafmt.conf`), `./AGENTS.md`, `./CLAUDE.md`, `./.claude/rules`, `./.local/logs`, `./.local/config` and `./.local/data/test-builds`.

`.git` is denied whole, because a planted `.git/commondir` makes `git status` load another config and run its `core.fsmonitor`, which the unprompted Stop hook would trigger (confirmed in a scratch repository). Git dies on an empty or `/dev/null` `commondir`, so denying only that file is impossible. So the common git commands that write `.git` run outside the sandbox as named exclusions in `sandbox.excludedCommands` (`git add *`, `git commit *`, `git reset *`, `git checkout *`, `git restore *`, `git switch *`, `git stash *`, `git merge *`, `git rebase *`, `git rm *`, `git mv *`, `git tag *`, `git branch *`, `git push *`, `git fetch *` and `git pull *`). Any other git command that writes `.git`, such as `git config`, `git cherry-pick`, `git revert` or `git worktree`, stays sandboxed and fails on the read-only `.git`, so run it in a terminal; that includes the `git config core.hooksPath .githooks` setup step. Each excluded command stays behind approval, because all 16 are in the `ask` list; this was observed only in the default permission mode. Each must run as a standalone command: the guard refuses any other form, as described above.

`.local/logs` is denied whole, so a link planted there cannot redirect an unsandboxed wrapper's log writes; the review log `.local/logs/review-runs.jsonl` is covered by that entry. Sandboxed logs therefore go under `$TMPDIR`, which must lie under `/tmp`, the only write path outside the project that `filesystem.allowWrite` grants. This list does not cover everything that runs outside the sandbox: it does not cover build files that do not exist yet (see the remaining gap above). The Edit and Write tools are outside the sandbox and still go through the guard's approval. A denied path that does not exist appears inside the sandbox as a `/dev/null` character device or, while a sandboxed command runs, an empty read-only file, which is also visible on disk to a hook running outside the sandbox. `check-docs-current.py` skips both, but a sandboxed `git status` may still list some, so stage explicit paths, never `git add -A`.

`sbt test` passes fully inside the sandbox, from `.sbt-home/` (1827 of 1827 on the recorded run). Unit tests must not depend on network DNS, because the sandbox has none: `DisposableAtlas.authorizedUri` takes an injected `DnsClient` (`test-support/src/main/scala/com/example/hiring/testing/DisposableAtlas.scala`), and `DisposableAtlasSpec` passes a stub for its `mongodb+srv://` case.

Entry points outside the sandbox must start Python with `-I`. `python3 -` and `python3 -c` put the working directory first on `sys.path`, so a module such as `pathlib.py` planted in the writable project root would run as the user when an approved wrapper verb such as `status` or `start` runs Python, and the approval prompt would not show it. `python3 -I` leaves the script and working directories off `sys.path`.

Why it matters: an agent may run test code it just edited. The sandbox limits that code's reads of credentials, its writes outside the allowed paths, and its writes to scripts and hooks that run later without a prompt. It does not limit the excluded entry points, and the remaining gap above stays open.

Limits: the hook is a guardrail, not a sandbox, so it cannot see inside scripts or interpreters; the Bash sandbox above covers shell commands. The wrapper's own automatic release of per-run test namespaces on the isolated stack is not gated per action; this was explicitly accepted by the project owner, because it only touches the identity-verified test stack. Docker keeps its storage outside the project folder and outside this setup. sbt, Coursier and Ivy state is per build under `.sbt-home/`; what sandboxed code can still write for sbt is stated in the Bash sandbox paragraphs above.
