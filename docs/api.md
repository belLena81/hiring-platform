# API reference

This is a backend-only GraphQL API. The GraphQL equivalent of an OpenAPI contract is its schema (SDL), complemented by introspection and executable operations. The server exports the schema directly; no UI or Node toolchain is included in this repository.

Default base URL: `http://127.0.0.1:8080`.

| Endpoint | Purpose |
|---|---|
| POST `/graphql` | Execute a JSON-encoded GraphQL operation; introspection (`__schema`, `__type`) only when schema exposure is on |
| GET `/schema.graphql` | Download the current SDL without querying MongoDB; 404 unless schema exposure is on |
| GET `/health` | Application liveness, HTTP 200 with UP |
| GET `/ready` | HTTP 200 `{"status":"READY","degraded":[...]}` or 503 `{"status":"NOT_READY"}`; see [Readiness](#readiness) |

## Readiness

`/ready` answers 503 `NOT_READY` only when the MongoDB ping fails or the Mongo-writes circuit breaker is open ([dependency circuit breakers](specs/dependency-circuit-breakers.md) rule 7). Otherwise it answers 200 with `{"status":"READY","degraded":[...]}`. `degraded` is always present and lists, in a fixed order, the stable names of components needing attention; it carries no counts, identifiers, durations or error text, and an empty list means nothing is degraded. Names: `kafka-publisher`, `kafka-consumer`, `interview-publication`, `interview-orchestrator-consumer`, `interview-worker-consumer`, `embedding-worker`, `search-session-handoff`, `interview-subject-cleanup`, `recruiter-job-closure` (a background worker made no successful progress for `readiness.worker-staleness-seconds`, or for `embedding-worker` its health flag is false), `outbox-age` (the oldest due operational event is older than `readiness.max-outbox-age-seconds`) and `closure-work-age` (the oldest pending recruiter job closure is older than `readiness.max-closure-work-age-seconds`). A component whose observation fails is also listed. Only enabled workers are reported. The first appearance of a component in the list is logged once as `READINESS_DEGRADED` with its name. The GraphQL `readiness` field is unchanged.

A heartbeat shows that a worker's loop completed a pass (or, for Kafka consumers, that the consumer stream is running), not that the broker is reachable; the age checks are the end-to-end signal. One answer is shared for `readiness.report-cache-millis` (default 1000 ms) by concurrent and following probes, so a probe flood costs the database one collection per window and a state change can take up to that long to show. Probes are never refused for load: concurrent callers await the shared collection and all receive the real status, so a flood cannot make an orchestrator probe see a synthetic 503. `/ready` and its `degraded` list are for internal probes only: do not expose them on the public edge, block the path at the reverse proxy. Configuration is in the `readiness` section of [application.conf](../src/main/resources/application.conf). Operations: alert on any non-empty `degraded` list for longer than a few probe intervals, and page on `outbox-age` or `closure-work-age`; 503 stays the only signal that removes an instance from traffic.

Health and readiness are HTTP-only. The GraphQL schema has no `health` or `readiness` field; an operation that selects them is invalid. Operations sent to `/graphql` may be restricted by the optional [persisted-query allowlist](#persisted-query-allowlist).

## Browse and track the contract

Schema exposure (`graphql.schema-exposure`, env `GRAPHQL_SCHEMA_EXPOSURE`) is off in the packaged default (production) and no local default is shipped: `src/main/resources/local.conf` is git-ignored, so local developers set `GRAPHQL_SCHEMA_EXPOSURE=true` or put `graphql.schema-exposure = true` in their own `local.conf`. While it is off, an operation selecting `__schema` or `__type` (directly, in a fragment, or inline) is refused before validation or execution with a GraphQL error `extensions.code = FORBIDDEN` and message `Schema introspection is not available`, and `GET /schema.graphql` answers 404 like any unknown path; `__typename` stays available because clients need it for unions. Unknown fields and types in a document are answered with the same generic 400 body (no `Did you mean` suggestions), so a disabled schema cannot be probed through validation messages either. With exposure on, each `__schema` or `__type` selection weighs 200 in the query complexity (cap 1000, and the same weight is charged to the cost budget), so aliasing introspection many times in one request is refused. The rest of this section assumes exposure is on.

An external GraphQL API client can load `/graphql` through introspection or import the SDL from `/schema.graphql`. An HTTP-only client can execute the examples below. Do not use OpenAPI generation as a substitute for the GraphQL schema: GraphQL operations select their own fields and share one execution endpoint.

The checked schema snapshot is [hiring.graphql](../src/test/resources/graphql/hiring.graphql). Backend contract tests compare it with the live schema definition, verify the download endpoint matches, execute the [standard introspection](../src/test/resources/graphql/introspection.graphql) fixture and the [account deletion status](../src/test/resources/graphql/account-deletion-status.graphql) fixture (the latter keeps an executed, health-independent case), and validate the [embedding coverage operation](../src/test/resources/graphql/embedding-coverage.graphql) against the live schema. Update schema and consumer fixtures together when contracts evolve; a schema diff alone does not establish compatible behavior.

Every operation, argument, input field, object type, union and enum value has a non-blank description in the SDL, and a test fails on any missing one. Regenerate the snapshot with `sbt "Test/runMain com.example.graphQL.cats.api.graphql.HiringGraphQLContractCapture"` and review the diff before committing it.

The schema includes Hiring GraphQL operations for jobs, applications, status transitions, cursor connections, application history, and account lifecycle. Identifiers use typed scalars: `UserID`, `JobID`, `ApplicationID`, `ApplicationEventID`, `InterviewWorkflowID`, `SearchID` and `DeletionReceiptID`, and malformed values are rejected at coercion. Other UUID-shaped values (for example `idempotencyKey` and `eventId`) use the named `UUID` scalar. Revisions such as `expectedRevision` use `scalar Long`, a 64-bit integer serialized as a JSON number that rejects fractions and strings. Every mutation input requires an `idempotencyKey: UUID!`; reusing a key with the same caller scope and input replays the authoritative result, while a different input is rejected. GraphQL enum labels use SCREAMING_CASE, while domain and event values retain their existing internal representation. Queries return direct values: `me` and `job` are nullable, while connections remain non-null and contain no error field. Expected mutation domain outcomes are operation-specific unions containing the success type, `ValidationError`, and/or `DomainError`; clients must select union members with inline fragments. Authentication, authorization, availability, repository, account, and search failures are real GraphQL errors with `errors[].extensions.code`, and are not encoded in mutation payloads; the seven interview cancel and reschedule mutations are the exception for authorization and rate-limit refusals (see the interview section). Connection cursors use the `Cursor` scalar: opaque, signed values (see below). `User.profile` is the nullable `UserProfile` union of `CandidateProfile` and `RecruiterProfile`; it is null for the singleton Admin and profile-less deleted accounts, while active Candidates and Recruiters expose only their matching union member. Admin provisioning uses explicit startup `auth.admin-seed` configuration; there is no public `bootstrapAdmin` mutation. `signUp` accepts only Candidates and Recruiters, requires a `profile` `@oneOf` input with exactly one variant matching the role (see [account profiles](#account-profiles-job-edits-and-payloads)), and a password of 12 to 1024 UTF-8 bytes (a short password as the only violation returns `INVALID_PASSWORD` with `password must be at least 12 bytes`; together with other violations the result is `VALIDATION_FAILED` listing every message), while Admin signup returns `ADMIN_BOOTSTRAP_ONLY`. Public `signUp` name collisions return generic `REGISTRATION_FAILED` rather than `NAME_TAKEN`. `login` issues short-lived HS256 bearer tokens with the required `AUTH_JWT_HS256_SECRET`. Login and signup are protected by process-local fixed-window counters configured under `auth.rate-limit` (once `max-buckets` client networks are tracked in a window, unseen ones share `overflow-buckets` striped counters with the same allowance, so flooding distinct addresses cannot reset an exhausted client; newcomers get a shared allowance that an attacker with about `max-buckets` addresses plus `overflow-buckets` times the allowance in attempts can exhaust, limiting unseen clients for the window while tracked clients are unaffected); exhausted fields return a GraphQL error with `extensions.code = RATE_LIMITED` and an `extensions.retryAfter` value in seconds: the remaining window, rounded up to whole seconds, at least 1. The limiter uses the TCP peer by default and accepts trusted RFC 7239 `Forwarded` or fallback `X-Forwarded-For` client addresses only when that peer is in `http.trusted-proxy-cidrs`; configure only the actual trusted proxy networks in [application settings](../src/main/resources/application.conf). `me`, `updateMyProfile`, and initial `deleteMyAccount` calls derive identity from the token subject and stored user role. `updateMyProfile` replaces the caller's whole profile; omitted optional parts are cleared, so it is not a partial update. The deletion mutation returns a durable `DeletionReceipt` with `PENDING`; query `accountDeletionStatus(receiptId: DeletionReceiptID!)` requires a verified token for the receipt owner and returns only that owner's `PENDING`, `COMPLETE`, or `NOT_FOUND` status. A deleted Recruiter's open jobs beyond the first 1000 are closed by background follow-up work, and the status stays `PENDING` until that closure (and the interview cleanup) has finished; a stuck closure keeps it `PENDING` and is retried with backoff. The deleted account can use a still-valid verified token to check status and replay the same deletion result; other operations still require active-user authorization. Credential storage uses Argon2id; password-bearing authentication request fingerprints are HMAC-protected with a key derived from `AUTH_RECEIPT_FP_SECRET` (the JWT secret when unset). Every token-producing receipt replay rechecks the referenced active account, canonical name and password. Changing the receipt key (or the JWT secret when no separate receipt secret is set) invalidates existing authentication receipt matches; use a new idempotency key. Email is optional and is not a login identity. The Admin-only `users` query answers every actor-lookup failure (including non-Admin callers and storage faults) with `UNAUTHORIZED`, deliberately, so callers cannot probe which accounts or roles exist.

Cursors are values of the `Cursor` scalar (the type of every `after` argument, `cursor`, `startCursor` and `endCursor`). A cursor is compact and opaque: `base64url(kind|keyset fields|expiry).base64url(HMAC-SHA256)`, signed with a key derived from the JWT secret, so clients cannot forge, edit or extend one. It carries the connection kind, the keyset timestamp and UUID tie-breaker, and an expiry (`auth.jwt.cursor-ttl-seconds`; one day by default, valid range 60 to 86400; the key name is unchanged although the cursor is no longer a JWT). A cursor is a position, not a credential: every page request is authorized again, so a cursor never grants access. Every list field pages the same way: `PageInfo` has `hasNextPage`, `hasPreviousPage` (true when the page was requested after a cursor, that is, it does not start the list), `startCursor` and `endCursor`. `nearbyJobs` result cursors use the same signed codec with their own cursor kind, carry the distance, job id and a digest of the center, radius, filters and ordering they are bound to, and are rejected with `INVALID_CURSOR` when reused with different criteria; presenting a connection cursor to `nearbyJobs` (or the reverse) returns `WRONG_CURSOR_KIND`. Application, event, job and user cursors are also bound to their list: the signed payload carries the parent id (job, application) or list, and the status or role filter, so a cursor issued for job A, for another status or for another list is refused with `INVALID_CURSOR` when replayed elsewhere. A cursor of another kind, a tampered, truncated or expired cursor is refused with a sanitized error. Search filter validation reports every violated filter field in one `INVALID_SEARCH_FILTER` error message.

Job filtering uses one `JobFilter` input for `jobs`, `nearbyJobs`, `semanticJobSearch` and `jobDiscoveryFacets`; the same invalid filter gets the same `INVALID_SEARCH_FILTER` code, placed as each operation already placed it. Connections have an explicit shape. `jobs` returns `JobSearchConnection`, which carries `searchId: SearchID` and `relaxedFilters: [RelaxedFilter!]!` next to `edges` and `pageInfo`. `nearbyJobs` returns `NearbyJobsConnection`, whose edges carry `node`, `distanceKm` and `cursor`, with `pageInfo` at the connection level; its cursors follow the same continuation rules as other connections. Other connections, such as `ApplicationConnection`, have no `searchId`. All connections, root or nested, are built by one shared helper, so `edges` and `pageInfo` behave identically. `semanticJobSearch` and `recommendedJobs` return a bounded top-N list (`RankedJobResults`): at most `first` results from one ranking pass, with the `searchId` and the ranking `model` stated once on the results type, no per-hit copies, no `pageInfo` and no cursor. Each hit implements the `ScoredHit` interface (`score`, `searchMode`, `matchedSkills`, `missingSkills`, `retrievalScore`). Their descriptions state the bound, so a client must not page them. The fit reasons `matchedSkills` and `missingSkills` split the target's required skills exactly once each, in the target's spelling, ordered by canonical form; comparison trims and lower-cases (`Locale.ROOT`), the same rule as the search filters. For a candidate's job hits (`semanticJobSearch`, `recommendedJobs`) the target is the job and the comparison set is the caller's own profile skills; for a recruiter's candidate hits (`candidateMatches`) the target is the owned job and the comparison set is the candidate's skills already in the result. Fit reasons read no data beyond what the caller can already see, add no provider call, and do not change ranking or the authorization checks, which run first. A forbidden request returns no hits and therefore no fit reasons. `filter.city` and `filter.skills` are compared ignoring case and surrounding spaces (the match is on the trimmed, lower-case form, the same rule candidate filters use), so `scala` matches a job that requires `Scala` and `kyiv` matches `Kyiv`; `skills` still requires every listed skill. In `jobDiscoveryFacets`, `skills` buckets report the lower-case spelling and a `cities` bucket groups every spelling of one city and reports one of them (the smallest), so a bucket value passed back as a filter always matches.

**Zero-result recovery (`jobs`).** `createdAfter` is an inclusive lower bound (`createdAt >= createdAfter`); the SDL states it. When the first page of `jobs` is empty, no cursor was sent, and the filter has a `createdAfter` bound or at least two distinct `skills` after canonical normalization (`{Scala, scala}` counts as one skill and is never widened), the service runs at most two extra searches, each relaxing exactly one filter of the filter as sent: first the `createdAfter` bound is dropped, then `skills` changes from all-of to any-of. A city is never relaxed. An unfiltered search, a city-only search and a non-empty first page are never relaxed, and a single skill is never widened, and a later page (a cursor was sent) is never relaxed. The first non-empty recovery page is returned, and the response names the relaxation in `relaxedFilters: [RelaxedFilter!]!`. Each entry is `{ filter: RelaxableJobFilter!, from: String!, to: String }`: `filter` is `CREATED_AFTER` or `SKILLS`; `from` is the `createdAfter` instant in ISO-8601 or `ALL_OF`; `to` is null when the bound was removed or `ANY_OF`. When nothing is found, the page is empty and `relaxedFilters` is empty. An empty `relaxedFilters` therefore means the page answers the search as sent.

A relaxed page is final: `pageInfo.hasNextPage` is false even when more jobs match the relaxed filter. Its cursor would continue the relaxed query, and `JobFilter` cannot express any-of skills, so the client could not send it back. A client that wants more applies the relaxation itself with a new search. Session recording stores the filter as sent and the jobs actually shown; the relaxation is visible only in the response.

Pricing: each extra search costs exactly what the `jobs` field was charged for this request (1 + first × the cost of the selected subfields, as priced in `QueryAdmission`), recorded per response path, so an aliased `jobs` field is priced on its own. Each extra search is charged to the caller's cost budget. `extensions.cost.requested` is the sum of the query charge and every relaxation charge of the request, where the response reports cost. The receipt depends on the grant: a tracked grant (the caller's own bucket) replaces the receipt numbers, with `requested` equal to the total; a shared grant (the overflow counter, which says nothing about the caller) keeps the receipt already disclosed for the request and only grows `requested`. A shared query charge followed by a tracked relaxation therefore reports the whole requested cost. A relaxation that the budget refuses is still charged to the caller's bucket but is not added to the receipt, so after a refusal `extensions.cost` can report a lower `requested` and a higher `remaining` than the bucket's real state; the refusal itself returns the empty page without an error (open follow-up in the [guided discovery specification](specs/guided-discovery-and-followup.md)). Only if no cost was recorded does the search fall back to the lower bound `1 + first`. If the budget cannot pay for an extra search, that search does not run and the empty page is returned without an error. An authorization failure or a failed base search is still an error and runs no extra search. A failed extra search or a failed admission check also returns the empty page, and logs `JOB_SEARCH_RELAXATION_FAILED` (see [logging](logging.md#job-search-relaxation-failures)). `jobs` is not an expensive discovery root, so recovery does not use the per-request expensive-root allowance. Relaxation is not applied to `semanticJobSearch`, `recommendedJobs` or `nearbyJobs`: each extra semantic search would repeat a paid embedding call, and distance relaxation has no defined radius rule yet.

## Graph access and shared error fragment

The graph can be walked from a parent to its related lists in one request. Every nested field calls the same use case, with the same authorization, as its root query; nothing is read before authorization and a refusal looks exactly like the root one.

| Field | Same as | Who |
|---|---|---|
| `Job.applications(first, after, status)` | `jobApplications` | owning Recruiter and Admin; a Candidate receives `FORBIDDEN` (the role has no such right), a non-owning Recruiter `NOT_FOUND` (as for an unknown job) |
| `Application.events(first, after)` | `applicationHistory` | the application's Candidate, the owning Recruiter and Admin |
| `User.applications(first, after, status)` | `myApplications` | only the calling Candidate's own account; null for any other user (nothing is read), so `candidate { applications }` under a job is always null |
| `InterviewWorkflow.application` | the application itself | whoever may view the application; otherwise null |
| `Application.interview` | `interviewWorkflow` for the application | the workflow's candidate, its recruiter and Admin; null when the application has no interview or the caller does not take part in it |

`Application.interview` reads the workflow through `InterviewSchedulingService.inspectForApplication`, which carries the participant predicate (candidate, recruiter or Admin) into the indexed `applicationId` query; an application of someone else and an application without an interview are both null, so the field reveals neither. It does not see an application the caller cannot reach in the first place.

Nested connections are charged like root ones, plus a base per parent: a nested list field costs 5 plus `first` times the cost of its selection (a root list costs 1 plus that product), so `myJobs(first: 100) { applications(first: 100) }` exceeds the complexity limit and is rejected before execution, and `first` outside 1 to 100 is refused at every nesting level. Related users and jobs (`candidate`, `job`, `recruiter`) are still loaded in batches per request; the per-parent lists are one authorized read per parent (an N+1 by design until keyed list ports exist), priced by the base of 5 per parent: with the cheapest selection about 99 parents fit in the 1000-unit limit, and aliases or fragments repeating a nested list are each charged.

Every refusal returned as data (`ValidationError`, `DomainError`, `SearchUnavailable`) implements `UserError { code message }`, so a client reads the refusals of any mutation or search with one fragment: `fragment Refusal on UserError { code message }`. Mutation results stay per-operation unions of the success type and the typed errors.

## Analytics report: hiring stage durations

`analyticsReport(from, to)` is Admin-only (the service rechecks the live Admin record; any other actor receives `UNAUTHORIZED`). `AnalyticsReport.stageDurations: [AnalyticsHiringStageDuration!]!` sits next to `timeToHire` and is additive. Each entry has `metric: AnalyticsHiringStageMetric!` (`TIME_TO_ACCEPT`, `TIME_TO_INTERVIEW`, `TIME_TO_HIRE`, `ACCEPTED_TO_INTERVIEW`, `INTERVIEW_TO_HIRE`), the percentiles `p50Hours`, `p75Hours`, `p90Hours`, `p95Hours` (`Float!`, finite, non-negative and non-decreasing) and `eligibleCount: Long!`. A metric whose group was suppressed upstream is absent, so the list may be empty (`[]`). It is not filtered by `from`/`to`, like `timeToHire`: it describes the published snapshot. A stored snapshot without `stageDurations`, with an unknown or repeated metric, or with invalid percentiles is unreadable (fails closed as `InvalidStoredData`) and the query returns the sanitized `UNAVAILABLE` error. A stored array longer than the number of metrics is rejected the same way.

```graphql
query { analyticsReport(from: "2026-09-16T00:00:00Z", to: "2026-09-17T00:00:00Z") {
  stageDurations { metric p50Hours p75Hours p90Hours p95Hours eligibleCount } } }
```

## Embedding coverage report

`embeddingCoverage(expectedModel: String): EmbeddingCoverageReport!` is an Admin-only, read-only aggregate query. The service rechecks the live Admin record (role Admin, account Active, singleton Admin); any other actor receives `UNAUTHORIZED`. `analyticsReport` and the `repairInterviewWorkflow` mutation apply the same rule (a non-Admin caller of `repairInterviewWorkflow` receives `UNAUTHORIZED`, previously `FORBIDDEN`). When vector search is disabled the query returns the typed `VECTOR_SEARCH_UNAVAILABLE` error rather than zero counts. `expectedModel` is optional, is trimmed, must be non-blank and at most 128 characters (`VALIDATION_FAILED` otherwise), and no model name is built in; without it `MODEL_MISMATCH` is never produced.

Pass `expectedModel` set to the configured embedding model; the code does not enforce this, it is an operator rule. Without it every stored model counts as `CURRENT` and `MODEL_MISMATCH` is never produced, but semantic search returns only embeddings whose stored model equals the configured model. After a model switch the default report can therefore show full `CURRENT` coverage while search excludes the old embeddings. `observedModels` lists the stored embedding count per distinct model and entity kind, so a mixed population is visible directly.

The report separates two dimensions. `freshness` (`CURRENT`, `CONTENT_CHANGED`, `MODEL_MISMATCH`, `NOT_EMBEDDED`) says whether the stored embedding matches the entity now; `repairState` (`NO_QUEUED_WORK`, `WAITING`, `RETRYING`, `IN_PROGRESS`, `LEASE_EXPIRED`, `FAILED`, with a separate `failureReason` for `FAILED`) says whether a repair is scheduled. `cells` holds one non-zero count per kind, freshness, repair state and failure reason; `kinds` reports searchable and scanned counts, `truncated` and `coverageShare` per kind. The population follows production eligibility: Open jobs, and Active Candidates with a profile (recruiter search opt-in is not applied). The response contains no ids, names, text, vectors or provider payloads.

`checks` contains `NO_ORPHANED_GAP` (a non-current entity has no queued work, so it will never be repaired) and `NO_STUCK_WORK` (queued work older than three durable retry caps past its availability), each `PASSED`, `FAILED` or `INCONCLUSIVE` with an offending count. The scan is bounded per kind by a fixed cap and `maxTime`; when the cap is reached `truncated` (or `queueTruncated`) is true, the affected checks are `INCONCLUSIVE` and never `PASSED`, and the counts are partial. Coverage share, lag percentiles and ages are informational. The entity scan needs snapshot read concern; a deployment without it (for example a standalone MongoDB server) fails the query with the repository-unavailable error. At most one `embeddingCoverage` root is accepted per request (complexity). Only jobs record a change time, so `lagSeconds` and `oldestNotCurrentAgeSeconds` cover the kinds listed in `lagEntityKinds` (jobs).

## Account profiles, job edits and payloads

- `SignUpInput.profile` and `UpdateMyProfileInput.profile` take `ProfileInput`, a `@oneOf` input with the variants `candidate: CandidateProfileInput` and `recruiter: RecruiterProfileInput`. Exactly one variant must be set; both or neither fail input validation. A variant that does not match the caller's role returns `PROFILE_ROLE_MISMATCH`, and the Admin role returns `PROFILE_UNSUPPORTED_FOR_ROLE`. `signUp` requires `profile` for Candidate and Recruiter.
- `RecruiterProfileInput.organizationName` is required (`String!`). `ResidenceInput` is `{ country: String!, city: String }`. `residence: {country: "DE"}` stores no city, and an omitted `residence` clears the stored residence.
- `updateMyProfile` replaces the whole profile for the caller's role. `profile` is required, and omitted optional parts are cleared.
- `updateJob(input: UpdateJobInput!)` takes `{ idempotencyKey, id, job }`. `job` replaces the whole content of the job; there is no partial update.
- `recordJobView` and `recordSearchResultClick` return `InteractionSuccess { eventId: UUID! }` as their success member, alongside the typed `ValidationError` and `DomainError` members.
- `Location.city` is nullable. A job created without a city has `location.city: null`, city-less jobs are excluded from city facets, and a stored empty city reads as null.
- `ApplicationEvent` (application history) exposes `actorRole: UserRole`, the role the actor acted in. Every stored event records it; the field stays nullable in the schema so the published contract does not change. Actor identifiers are not exposed.
- `ValidationError { code, message, field }`: `field` is the GraphQL input path of the first violated rule (for example `profile.candidate.residence.country`, or `job.title` for `updateJob`), or null when that rule has no input counterpart; `message` joins every violated rule and uses domain field names.

- `DomainError.retryAfterSeconds` is set only for an interview-action `RATE_LIMITED` refusal and is null otherwise.

Operation fixtures for these payloads: [account profile](../src/test/resources/graphql/account-profile.graphql), [application history](../src/test/resources/graphql/application-history.graphql) and [jobs, nearby jobs and ranked search](../src/test/resources/graphql/jobs.graphql). The `jobs` operation selects `relaxedFilters { filter from to }` and the ranked search operation selects `missingSkills`.

## Job discovery facets

`jobDiscoveryFacets(query: String, filter: JobFilter, center: GeoPointInput, radiusKm: Float): JobDiscoveryFacetsResult` (nullable union, see [AI search outcomes](#ai-search-outcomes)) is available to active Candidates and the singleton Admin (a Recruiter receives `FORBIDDEN`). Without `query` the counts cover every Open job matching the structured filter and optional radius, and `coverageLimit` is null.

With `query` the text is trimmed (blank is a `ValidationError` with `INVALID_SEARCH_FILTER` for `query`; more than 2048 characters is a `ValidationError` with `INPUT_TOO_LARGE`) and the counts cover the Open jobs matching both the text and the filter, recounted from the jobs collection, never from the search index. The text is matched against title, description, requirements and skills; jobs without a current embedding are counted. `coverageLimit` states what the counts cover. Null means every matching eligible job is counted. A number means more than `coverageLimit` jobs matched the text, so only the highest-scoring `coverageLimit` matches (configuration `mongo.discovery.lexical-facet-match-limit`, default 1000, valid 1 to 5000) were counted; such counts are never totals, and with a radius they cover only the radius-restricted subset of those top matches. A job opened after the last search index update is absent until it is indexed. `truncated` keeps its meaning of bucket truncation (at most 20 buckets per dimension).

Startup readiness guarantees that the lexical search index exists and is ready; the request does not check it again. An index dropped at runtime returns empty results, which are not detected per request. When the search service is unreachable, a stage is unsupported, or the shared time budget (`mongo.discovery.max-time-millis`, covering the text match and the recount together) is exhausted, the request returns `SearchUnavailable { code: FACETS_UNAVAILABLE, retryable: true }` in `data`; there is no fallback to structured counts. A request with `query` is charged the cost of a search page and counts toward the expensive-root limit. Operation fixture: [lexical-query facets](../src/test/resources/graphql/job-discovery-facets.graphql).

## AI search outcomes

`semanticJobSearch`, `recommendedJobs`, `candidateMatches` and `jobDiscoveryFacets` are nullable and return unions, so a screen that mixes ordinary fields with AI search still renders when the embedding provider or vector search is down:

```graphql
union SemanticJobSearchResult = RankedJobResults | SearchUnavailable | ValidationError | DomainError
union RecommendedJobsResult = RankedJobResults | SearchUnavailable | ValidationError | DomainError
union CandidateMatchesResult = RankedCandidateResults | SearchUnavailable | ValidationError | DomainError
union JobDiscoveryFacetsResult = JobDiscoveryFacets | SearchUnavailable | ValidationError
type SearchUnavailable implements UserError { code: ErrorCode!  message: String!  retryable: Boolean! }
```

Select the ranked results with an inline fragment and the refusals through `UserError` or per type, for example `{ semanticJobSearch(query: "scala", first: 10) { ... on RankedJobResults { results { score job { id } } } ... on SearchUnavailable { code retryable } ... on ValidationError { code field } ... on DomainError { code } } }`.

| Outcome | Codes | Member |
|---|---|---|
| Search cannot be served now (retryable) | `PROVIDER_UNAVAILABLE`, `VECTOR_SEARCH_UNAVAILABLE` (including search not configured), `FACETS_UNAVAILABLE`, `MISSING_EMBEDDING`, `STALE_EMBEDDING` | `SearchUnavailable` with `retryable: true` |
| Invalid input | `INVALID_SEARCH_FILTER`, `INPUT_TOO_LARGE`, `VALIDATION_FAILED`, `INVALID_FILTER` | `ValidationError`; `field` is the input path (`query`, `filter.city`, `filter.skills`, `first`, `radiusKm`) or null |
| Business refusal (for example `NOT_FOUND`, `RECRUITER_REQUIRED`, `CANDIDATE_REQUIRED`) | non-exceptional domain codes | `DomainError` (not a member of `JobDiscoveryFacetsResult`; there it stays top-level) |
| Authentication, authorization, readiness, store failure | `UNAUTHORIZED`, `FORBIDDEN`, `SERVICE_NOT_READY`, `UNAVAILABLE`, `INTERNAL` | Top-level `errors` entry; the nullable root nulls only that field and siblings keep their data |

Recording the search session is best-effort: when it fails, the results and their `searchId` are still returned and one safe log event (`SEARCH_RECORDING_FAILED`: search kind, request id and error code or class, never result ids or query text) is written; there is no retry. A later `recordJobView` or `recordSearchResultClick` for that `searchId` can therefore return `DomainError` with `SEARCH_SESSION_UNAVAILABLE` or `SEARCH_SESSION_PENDING` (or `NOT_FOUND` when nothing was queued). Clients treat these on clicks and views as non-fatal: the results stay usable and only that interaction is not attributed to the search.

**Degraded results.** `semanticJobSearch` and `candidateMatches` fall back to keyword (lexical) ranking when the embedding provider or vector search is unavailable. The ranked results then carry a non-null `degradedReason` (`PROVIDER_UNAVAILABLE` or `VECTOR_SEARCH_UNAVAILABLE`; null when not degraded, and the only degradation signal), every hit has `searchMode: LEXICAL`, and `model` is null (it is nullable on `RankedJobResults` and `RankedCandidateResults`) because no embedding model was used. Fallback hits keep every live check (open job, filter, active and consenting candidate) except embedding freshness, so a missing or stale embedding is still `SearchUnavailable` (`MISSING_EMBEDDING`, `STALE_EMBEDDING`) with no fallback. The fallback runs on the same search deployment and behind the same discovery circuit breaker and admission limit as the vector search, so it helps when the embedding provider is down, but not when MongoDB Atlas search itself is unavailable. A vector query that exceeded its time budget or was refused by the admission limit or open breaker is not retried through the fallback; it returns `SearchUnavailable` (`VECTOR_SEARCH_UNAVAILABLE`). Lexical relevance is not comparable with semantic relevance, so clients should show a notice when `degradedReason` is set. If the lexical retrieval also fails, the field returns `SearchUnavailable` with `VECTOR_SEARCH_UNAVAILABLE`. `recommendedJobs` and `jobDiscoveryFacets` have no fallback and return `SearchUnavailable` instead.

`RATE_LIMITED` and the cost budget refusal remain HTTP 429 for the whole request. Query complexity is unchanged: a union selection weighs as its most expensive alternative, not their sum, so adding `... on UserError { code message }` does not raise the cost for the same `first`.

## Interview scheduling, cancellation and rescheduling

Fixtures: [scheduling operations](../src/test/resources/graphql/interview-scheduling.graphql) and [cancellation and reschedule operations](../src/test/resources/graphql/interview-cancellation.graphql), both validated against the live schema in the unit suite; the SDL snapshot above carries the types. The change is additive: nothing public was removed or renamed (`rescheduleInterview` was never exposed).

### Schema

```graphql
input InterviewActionInput { workflowId: InterviewWorkflowID!, expectedRevision: Long!, idempotencyKey: UUID! }
input ProposeInterviewRescheduleInput {
  workflowId: InterviewWorkflowID!, expectedRevision: Long!, startsAt: Instant!, endsAt: Instant!, idempotencyKey: UUID!
}
union InterviewActionResult = InterviewWorkflow | ValidationError | DomainError

type Mutation {
  cancelInterview(input: InterviewActionInput!): InterviewActionResult!
  requestInterviewReschedule(input: InterviewActionInput!): InterviewActionResult!
  dismissInterviewRescheduleRequest(input: InterviewActionInput!): InterviewActionResult!
  proposeInterviewReschedule(input: ProposeInterviewRescheduleInput!): InterviewActionResult!
  withdrawInterviewReschedule(input: InterviewActionInput!): InterviewActionResult!
  acceptInterviewReschedule(input: InterviewActionInput!): InterviewActionResult!
  declineInterviewReschedule(input: InterviewActionInput!): InterviewActionResult!
}
```

The read `interviewWorkflow(workflowId: InterviewWorkflowID!): InterviewWorkflow` is nullable. It returns `null`, with no error, when the workflow does not exist or is not visible to the caller, so existence is not revealed; other failures are GraphQL errors. `InterviewWorkflow.progress` is the non-null `InterviewProgress` enum, and `notifiedParticipants` is `[InterviewParticipant!]!`, where `InterviewParticipant` has exactly `CANDIDATE` and `RECRUITER`.

`InterviewWorkflow` exposes the current interval as `slot: TimeSlot!` (replacing flat `startsAt`/`endsAt`) and gains nullable `pending: TimeSlot` (the replacement held after the candidate accepted), `cancelledAt`, `proposal: RescheduleProposal` (`slot: TimeSlot!`, `expiresAt`; the open proposal) and `rescheduleRequestedAt: Instant` (set while the candidate's request is open). `TimeSlot` is `{ startsAt endsAt }`. `application: Application` resolves the workflow's application with the application's own visibility, null when the caller may not see it. A workflow is visible only to its candidate, its owning recruiter and Admin, and nothing identifies who proposed: the inputs and the type carry no actor, role, proposer or initiator. `cancelInterview` has no text field; cancelling records system-generated feedback chosen by the trusted initiator (candidate, recruiter or administrator).

`progress` is the workflow phase, the `InterviewProgress` enum with 15 values, one per domain phase, in SCREAMING_SNAKE_CASE: `RESERVATION_PENDING`, `STATUS_COMMIT_PENDING`, `COMPENSATION_PENDING`, `NOTIFICATIONS_PENDING`, `COMPLETED`, `REPAIR_REQUIRED` (scheduling); `PROPOSAL_PENDING` (a proposal awaits the candidate; the old slot is untouched); `CANCEL_PENDING`, `CANCEL_NOTIFICATIONS_PENDING`, `CANCELLED` (cancellation); `RESCHEDULE_HOLD_PENDING`, `RESCHEDULE_SWAP_PENDING`, `RESCHEDULE_CANCEL_OLD_PENDING`, `RESCHEDULE_NOTIFICATIONS_PENDING`, `RESCHEDULE_COMPENSATION_PENDING` (an accepted proposal being booked). Mutations return the workflow as stored right after the decision; provider calls and notifications follow asynchronously, so poll `interviewWorkflow` for the later phases.

### Authorization

The actor comes only from the authenticated request. A workflow the caller does not participate in is indistinguishable from a missing one (`NOT_FOUND`); a participant refused an action receives `FORBIDDEN`. Refusals are typed `DomainError` payloads for these seven mutations (so one refused alias does not discard the others); a missing or invalid token is still the `UNAUTHORIZED` GraphQL error.

| Action | Candidate on the application | Owning recruiter | Admin | Any other candidate or recruiter |
|---|---|---|---|---|
| `cancelInterview` (rejects the application) | allow | allow | allow | `NOT_FOUND` |
| `requestInterviewReschedule` | allow | `FORBIDDEN` | `FORBIDDEN` | `NOT_FOUND` |
| `dismissInterviewRescheduleRequest` | `FORBIDDEN` | allow | allow | `NOT_FOUND` |
| `proposeInterviewReschedule` | `FORBIDDEN` | allow | allow | `NOT_FOUND` |
| `withdrawInterviewReschedule` | `FORBIDDEN` | allow | allow | `NOT_FOUND` |
| `acceptInterviewReschedule` / `declineInterviewReschedule` | allow | `FORBIDDEN` | `FORBIDDEN` | `NOT_FOUND` |

Consent to a new time is the candidate's alone, so Admin cannot accept or decline. The candidate gains no other status power: `rejectApplication` and the other status mutations remain for the owning recruiter and Admin.

### Error codes (`UserError.code`)

`UserError.code` is the closed `ErrorCode` enum, generated from the failure catalog and shared by `DomainError` and `ValidationError`; top-level GraphQL errors keep their string `extensions.code`. The codes these seven actions can return are `NOT_FOUND`, `FORBIDDEN`, `STALE_REVISION` (the workflow moved since `expectedRevision`), `INVALID_STATUS_TRANSITION` (the application is no longer `Interview`, or the action does not fit the current state), `INTERVIEW_ALREADY_STARTED`, `INTERVIEW_ALREADY_CANCELLED`, `INTERVIEW_NOT_SETTLED` (an earlier cancel or reschedule is still being carried out), `PROPOSAL_ALREADY_OPEN`, `NO_OPEN_PROPOSAL`, `PROPOSAL_EXPIRED`, `NO_RESCHEDULE_REQUEST` (dismissing a request that was never made), `INVALID_INTERVIEW_INTERVAL` (a scheduled or proposed interview must start in the future and end after it starts; `scheduleInterview` returns this code too), `RESCHEDULE_INTERVAL_UNCHANGED`, `CONFLICT` (an idempotency key reused for a different operation or input; also a lost concurrent write) and `RATE_LIMITED`. Storage failures and unexpected states surface as the generic `UNAVAILABLE` GraphQL error. Messages are fixed text: no workflow, user or application identifiers, times or feedback text.

### Idempotency

Every action takes an `idempotencyKey`, scoped to the acting user. Repeating the same operation with the same input returns the stored workflow without a second effect. A key reused with a different operation or input is a `CONFLICT`. Exception: a `requestInterviewReschedule` whose flag is already set (a no-op) writes nothing, not even a receipt, so repeating it with any key is harmless but a key first used for such a no-op is not remembered for conflict detection.

### Notification guarantee

Cancel and reschedule notifications (cancelled, proposed, declined, withdrawn, expired, requested, rescheduled, could not be booked) are sent after the change is durable and are at-least-once on a non-local provider: a crash after the provider accepted a message but before the receipt is stored causes a resend, so a duplicate is possible and a silent loss is not (an exhausted notification becomes visible command-level repair for Admin). The local ledger provider keeps exactly one receipt per key.

### Rate limit and request bounds

Each authenticated actor may perform at most `auth.interview-action-rate-limit.attempts` interview actions (any of the seven mutations) per `window-seconds` (packaged values 30 per 60 seconds and 10000 users, process-local; the section is required, so a missing or invalid value fails startup; see [application settings](../src/main/resources/application.conf)). The check uses the verified token claims and runs before any storage work. Every aliased or batched action takes its own unit, so a request that exceeds the allowance has its surplus actions answered with `DomainError { code: "RATE_LIMITED" }` while the others keep their results; the message states no limit or count. This differs from the login and sign-up limit, which returns a top-level GraphQL error (`extensions.code = RATE_LIMITED` with `extensions.retryAfter` seconds, keyed by client address): an interview action is refused with a `DomainError` payload in `data`, keyed by the authenticated user, and carries `retryAfterSeconds`: the ceiling of the remaining window in seconds, at least 1, computed from the same allowance that refused the call. Once `max-buckets` users are tracked in a window, further unseen users are not refused and do not evict a counted user: they share `overflow-buckets` striped counters (packaged 256) with the same allowance and window, so the worst case for a flood of distinct users is a shared allowance among the newcomers that hash to the same counter. That allowance can itself be exhausted: an attacker holding about `max-buckets` keys plus `overflow-buckets` times the allowance in charges can make unseen users `RATE_LIMITED` for the window, while tracked users and users who already exhausted their allowance are unaffected. The once-per-window overflow warning in the log is the signal. Each action also weighs 100 in the query-complexity budget (1000 per request), so a single request can carry at most nine of them, and that weight is charged to the query cost budget described under the error list below.

## Execute operations

```bash
curl -sS http://127.0.0.1:8080/schema.graphql
curl -sS http://127.0.0.1:8080/health
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/ready
curl -sS http://127.0.0.1:8080/graphql \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data '{"query":"query OpenJobs($first: Int!) { jobs(first: $first) { searchId edges { cursor node { id title } } pageInfo { hasNextPage endCursor } } }","operationName":"OpenJobs","variables":{"first":10}}'
```

`GET /health` returns HTTP 200 with `UP` and does not access MongoDB. `GET /ready` returns HTTP 200 with `READY` when MongoDB connectivity and setup readiness (and enabled embedding-worker health) pass, and HTTP 503 with `NOT_READY` otherwise. The `OpenJobs` example needs a bearer token from `login` or `signUp` in `ACCESS_TOKEN`; a successful response has the shape `{"data":{"jobs":{"searchId":…,"edges":[…],"pageInfo":{…}}}}`.

By default, GraphQL execution has a five-second HTTP deadline and a four-second resolver-service deadline. Because Sangria leaf actions are `Future`-based, an HTTP timeout cannot cancel a resolver already running after the Cats Effect to Future bridge. The service bound limits cooperative `IO` work, but a timed-out mutation may still have completed; clients must determine the outcome through a subsequent authorized read instead of blindly retrying.

Named operations and variables:

```json
{
  "query": "query OpenJobs($first: Int!, $after: Cursor) { jobs(first: $first, after: $after) { edges { cursor node { id title } } pageInfo { hasNextPage endCursor } } }",
  "operationName": "OpenJobs",
  "variables": {"first": 10}
}
```

Send `Content-Type: application/json`; GraphQL responses negotiate between `application/graphql-response+json` and `application/json` and echo the selected media type. An absent `Accept` header prefers `application/graphql-response+json`; unsupported response media returns 406. GraphQL request envelopes are decoded by http4s/Circe, while GraphQL document parsing remains owned by Sangria.

`query` is required. Missing/null `variables` means an empty object, and missing/null `operationName` means no selected name. When the document contains several operations, provide an operation name. Supply required variables explicitly; the pinned Sangria version has a documented limitation with omitted required-variable defaults.

## Persisted-query allowlist

An optional production mode restricts `POST /graphql` to a fixed set of full documents. The default is `off`, which leaves execution unchanged.

| Setting | Default | Meaning |
|---|---|---|
| `graphql.persisted-queries.mode` (env `GRAPHQL_PERSISTED_QUERIES_MODE`) | `off` | `off` or `allowlist` |
| `graphql.persisted-queries.manifest` (env `GRAPHQL_PERSISTED_QUERIES_MANIFEST`) | none | Path to the manifest, a machine-local file read at startup |

- Each manifest entry is the lowercase hexadecimal SHA-256 of the exact UTF-8 bytes of the request's `query` string. No whitespace or other normalization is applied, so one changed character is a different document.
- Full documents only. A request carrying only `extensions.persistedQuery.sha256Hash` and no `query` is refused without a lookup. Hash-only (APQ) registration is not supported.
- The check runs before `GraphQLDocumentCache`. An unlisted document is refused with HTTP 400 and `PERSISTED_QUERY_NOT_FOUND`. The document is not parsed, not cached, not echoed in the response, and not charged to the query cost budget. This code is an HTTP-level error, not a member of the `ErrorCode` enum.
- Introspection exemption: a document whose root selections are only `__schema`, `__type` or `__typename`, with no fragments and distinct operation names, runs without a manifest entry and is governed only by `graphql.schema-exposure` (see [Browse and track the contract](#browse-and-track-the-contract)). A document that mixes introspection with another root field, such as `{ __schema { types { name } } jobs { id } }`, is not exempt and is refused.
- Allowed documents still pay the rate limits and the query cost budget.
- The manifest is read once at startup. In `allowlist` mode a missing, unreadable, empty or malformed manifest fails startup with a typed configuration error, reported as the `CONFIG_INVALID` event.
- The manifest is generated from the operation fixtures in `src/test/resources/graphql/`, and a test requires a fresh generation to equal the committed manifest. Regenerate with `sbt "Test / runMain com.example.graphQL.cats.api.http.PersistedQueryManifestCapture"` and review the diff. Production points `graphql.persisted-queries.manifest` at its own machine-local file under `.local/config/`, which is not committed.

Implementation: `PersistedQueryAllowlist` (`api/admission`), the typed `graphql.persisted-queries` configuration (`config`, [application settings](../src/main/resources/application.conf)), and the route check in `GraphQLHttpRoutes`. Tests: `PersistedQueryAllowlistSpec` and `PersistedQueryConfigSpec`. The committed manifest is [persisted-queries.manifest](../src/test/resources/graphql/persisted-queries.manifest). It has one lowercase SHA-256 per line, with blank lines and `#` comments ignored.

## Errors and limits

Errors use a sanitized `errors` array. The active 32-character hexadecimal OpenTelemetry trace ID is the request correlation ID; W3C `traceparent` propagation and response headers are owned by the HTTP server middleware. Invalid syntax/schema/variables/operation selection, query budgets or a document refused by the persisted-query allowlist (`PERSISTED_QUERY_NOT_FOUND`) produce 400; unsupported method/media produce 405/406/415; oversized body 413; an exhausted query cost budget 429; overload 503; deadline 504; unexpected failures 500. GraphQL field failures, including rate-limited login/signup fields (but not the whole-request cost budget refusal), use HTTP 200 with `errors[].extensions.code`; rate-limit errors additionally include `errors[].extensions.retryAfter` in seconds (the remaining window, rounded up, at least 1). The **query cost budget** limits how much GraphQL complexity one caller may spend per window: every query and mutation is charged its computed complexity (after the page-size, depth and complexity checks, before any resolver runs) to the authenticated actor, taken from the verified token subject without a storage read, or to the resolved client address (the trusted-proxy rules above; IPv6 per /64) when anonymous. `graphql.cost-budget.max-cost` per `window-seconds` is allowed (packaged 10000 per 60 seconds, process-local; authenticated actors are tracked in `max-actor-buckets` (10000) and anonymous clients in `max-client-buckets` (10000), separately, so anonymous key flooding cannot take capacity from signed-in users; values are validated at startup (`max-cost` must be at least the per-query cap of 1000), and when the whole `graphql.cost-budget` section is omitted the same defaults apply, as for the `resilience` section; the packaged `application.conf` is the single documented source of the numbers); a single query is capped at complexity 1000 separately. When the budget is spent the whole request is refused with HTTP 429, a `Retry-After` header, and `{"data":null,"errors":[{"message":"Query cost budget exhausted; retry later","extensions":{"code":"RATE_LIMITED","retryAfter":60}}]}` (`retryAfter` in seconds: the remaining window of the budget, rounded up to whole seconds, at least 1; the example value is illustrative). A refused request still counts toward the window. When a cache is full, unseen keys are charged to `overflow-buckets` shared striped counters (packaged 256, chosen by a per-process randomly seeded hash, same window and the same cost) instead of evicting a tracked key, so an exhausted key is never reset and a flood of distinct keys degrades into a shared budget for the newcomers. That budget can itself be exhausted (about `max-actor-buckets` or `max-client-buckets` keys plus `overflow-buckets` times `max-cost` in charges make unseen callers of that kind `RATE_LIMITED` for the window); tracked clients, authenticated actors (separate capacity) and exhausted victims are unaffected; a safe warning that names only the limiter is logged at most once per window while overflow is in use. **Cost in the response (`extensions.cost`).** A request charged to the caller's own bucket carries `"extensions":{"cost":{"requested":8,"limit":10000,"remaining":9992,"resetsInSeconds":60}}` at the top level of the response: `requested` is the complexity charged for this request, `limit` is `max-cost`, `remaining` is `max(0, limit - charged so far in the window)` after this charge, and `resetsInSeconds` is the rest of the fixed window rounded up, at least 1. The 429 refusal carries the same object with `remaining = 0` (and `resetsInSeconds` equal to `retryAfter`); `Retry-After` and `retryAfter` are unchanged. The values are per process, not cluster-wide: each instance keeps its own window, so behind several instances `remaining` describes only the instance that answered. A request charged to a shared overflow counter (see below), or made by an anonymous caller whose client address could not be resolved (all such callers share one bucket), has no `extensions.cost`, on success or on 429, because the numbers would describe other callers' consumption; clients must treat the object as optional. A request refused before the budget step (page-size check, disabled schema exposure, persisted-query refusal, invalid document) is not charged and has no cost object. The window is fixed, not a token bucket, so `remaining` can jump back to the limit when the window ends. The cost formula and caps for `semanticJobSearch`, `recommendedJobs`, `candidateMatches`, `jobDiscoveryFacets` and `nearbyJobs` are in their SDL descriptions: page-priced roots cost `100 + first * (1 + cost of the selected subfields)`, facets `100 + cost of the selected subfields` (`100 + 25 * (1 + ...)` with `query`), within the per-request caps of complexity 1000, depth 16 and the expensive-root limit. **Anonymous callers share a budget** when the peer address is missing, or when the service runs behind a proxy and `http.trusted-proxy-cidrs` does not list it (every request then appears to come from the proxy address, or from one unknown client); configure the real proxy networks for per-client budgets. A request refused by the page-size check (`first` outside 1..100, including through variables, fragments and aliases) is not charged: it is answered with HTTP 200, `data: null` and a `VALIDATION_FAILED` error, before any resolver or budget step. Expected mutation domain outcomes are selected from operation-specific unions in `data`. Stable codes such as `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `DUPLICATE_APPLICATION`, `INVALID_STATUS_TRANSITION`, `PROFILE_ROLE_MISMATCH`, and `PROFILE_UNSUPPORTED_FOR_ROLE` never expose raw driver messages or stack traces. Relationship loading (the `users`, `jobs` and email-visibility fetchers) batches at most 100 keys per repository call; larger sets are split into consecutive batches of at most 100, and each batch uses the same authorization predicate. Parsed documents are cached, but validation is not: every request runs full query validation, including `@oneOf` and variable checks, so a cached document cannot bypass them.

**Hidden is the same as missing.** A resource that exists but that the caller may not see answers exactly like one that does not exist: the same code (`NOT_FOUND`), the same message (`<entity> not found`) and no extra fields, decided in the service before any further work. This covers `job` and `recordJobView` (a Draft or Closed job that is not the caller's to manage), `applicationHistory`, the nested `Application.events` and the application views (another candidate's application, or one on a job the recruiter does not own), `jobApplications` and `Job.applications`, `updateJob`, `publishJob` and `closeJob` for a job the recruiter does not own, every application status mutation on an application the caller may not manage, `candidateMatches` on another recruiter's job, and `recordSearchResultClick` for another caller's `searchId`. `FORBIDDEN` is kept where a role simply lacks the right and there is no existence to hide: a Candidate calling a Recruiter-only mutation (`createJob`, `updateJob`, `publishJob`, `closeJob`, `jobApplications`, `acceptApplication`, ...), a Recruiter calling a Candidate-only operation, and a Candidate attempting a status change other than `declineApplication` on their own application. `submitApplication` to a Draft answers `NOT_FOUND`. **Documented exception:** `submitApplication` to a Closed job keeps answering `JOB_MUST_BE_OPEN`, so it still reveals that a closed job exists; this is a deliberate product decision, because closing is a public business state of a job a candidate could already see.

**Job lifecycle.** `createJob` creates a **Draft** owned by the calling recruiter (the mutation takes no status). A Draft is visible to its owner and the Admin only: `myJobs`, `job` and `updateJob` work for them, while candidates get `NOT_FOUND`, and it is absent from `jobs`, `nearbyJobs`, `jobDiscoveryFacets`, `semanticJobSearch`, `recommendedJobs` and `candidateMatches`, and it accepts no application. `publishJob` moves a Draft to Open (publishing an Open or Closed job is `INVALID_JOB_TRANSITION`); `closeJob` closes a Draft or Open job. `JOB_CREATED` is published once, when the job is published; `JOB_UPDATED` and `JOB_CLOSED` follow only for a job that was published, so a Draft that is edited or closed publishes nothing.

**Declining.** `declineApplication` is also available to the candidate who owns the application (a reason is required; only `CREATED` can be declined). The history entry has the candidate as actor. Candidates have no other application status action.

**Duplicate and conflict.** A second `submitApplication` by the same candidate to the same job answers `DUPLICATE_APPLICATION` (a typed `DomainError`-style refusal, reported immediately), never `CONFLICT`. `CONFLICT` is reserved for a lost concurrent write after the server has retried the transaction.

`CONFLICT` on `submitApplication` or an application status change means a concurrent write on the same job, application or acting user won, and nothing was changed. Retry the same request with the same idempotency key after a short randomized backoff (about 100 to 500 ms, a few attempts). If `CONFLICT` persists for the same application, its state really changed (for example it was already decided): re-read it instead of retrying. A Recruiter or Admin issuing many status changes in parallel can see occasional `CONFLICT`, so such clients should limit their parallelism.

The [HTTP configuration](../src/main/resources/application.conf) and [GraphQL routes](../src/main/scala/com/example/graphQL/cats/api/http/GraphQLHttpRoutes.scala) define request admission, request size, depth/complexity and deadline bounds. Introspection uses those same limits. Run `sbt test` for contract checks and `sbt 'IntegrationTest / test'` for real HTTP/database checks.
