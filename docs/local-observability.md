# Local observability

Opt-in, local-workstation-only stack for looking at the API's metrics, traces and logs. Signal definitions, privacy and cardinality rules live in [hiring-observability-resilience](specs/hiring-observability-resilience.md); this page is the runbook and the record of what is and is not verified.

## Components

| Signal | Producer | Transport | Store | Viewer |
|---|---|---|---|---|
| HTTP metrics | `TelemetryRuntime` (otel4s) | OTLP/HTTP to the collector | Prometheus (scrapes the collector) | Grafana "Hiring API - RED" |
| Backlog metrics | `BacklogSampler` / `BacklogMetrics` | same | Prometheus | Grafana "Hiring Backlogs" |
| Traces | otel4s `ServerMiddleware` | same, then OTLP/gRPC to Tempo | Tempo | Grafana Explore → Tempo |
| Logs | API container stdout | Alloy via the Docker API | Loki | Grafana Explore → Loki, `{service_name="api"}` |
| Alert rules | Prometheus evaluates the eight rules in `docker/observability/alerts.yaml` every 5 s | Prometheus `alerting` section | Prometheus alert state (`ALERTS`) | Prometheus → Alerts, `127.0.0.1:9090` |
| Alert routing | Alertmanager (`prom/alertmanager`, 0.34.2, pinned by digest) routes `page` and `ticket` alerts to two receivers | HTTP from Prometheus | in memory; `/alertmanager` is a tmpfs | `127.0.0.1:9093` |
| Alert sink | `alert-sink`: the pinned collector image with a `webhookevent` receiver and a `debug` exporter; it logs each webhook | HTTP webhook from Alertmanager to `alert-sink:8080/alerts` | container log only; nothing is stored | none (no published port) |

Files: `compose.observability.yaml`, `docker/observability/**`, `scripts/generate-local-traffic.sh`, `scripts/seed-local-jobs.sh`, and for alert verification `scripts/check-alert-rules.sh`, `scripts/run-alert-delivery-drill.sh`, `scripts/run-alert-backlog-drill.sh`, `scripts/alert-delivery-lib.sh`, `scripts/alert_sink_notifications.py`.

The existing HTTP server metrics and spans come from the http4s otel4s middleware. Observed HTTP series: `http_server_request_duration_seconds_{bucket,count,sum}` with `http_request_method`, `http_response_status_code`, `http_phase` and `classifier`. There is **no `http_route` label**: the http4s otel4s metrics middleware (0.19.0) never emits one; the route template is carried by its `classifier` attribute, which `TelemetryRuntime.routeLabel` fills from the fixed public path list (`/graphql`, `/health`, ...) or `_unmatched`, so no raw path can reach a label. Dashboards use `classifier`; no application change was needed. Every request records two samples: `http_phase="headers"` (no status code) and `http_phase="body"` (with status code). Queries must select `http_phase="body"`, otherwise request counts and the error-ratio denominator double and latencies mix two measurements.

Mongo client spans (`<command> <collection>`, kind CLIENT, the same attributes) are children of the current request span only when the JVM runs with `-Dcats.effect.trackFiberContext=true` (set for `sbt run` and tests). The container deliberately does not set it (decision D13 of the container runtime specification), so in the container Mongo operations record the duration histogram without span parenting and create no span; the same holds for background workers (outbox publisher, embedding workers, backlog sampler). When the flag is off, `Main` selects the standard OpenTelemetry thread-local context storage (`TelemetryRuntime.selectContextStorage`), because the fiber-backed storage that `otel4s-oteljava-context-storage` registers throws on every otel4s instrument call without the flag. GraphQL requests rejected before a document exists (malformed JSON, unsupported media type, HTTP authentication failures, payload too large) appear only in the HTTP server metrics, not in the GraphQL counter; parse failures, invalid documents and persisted-query misses are the `_invalid` count. Field-level GraphQL errors return HTTP 200, so use `hiring.graphql.root_field.executions` by `hiring.graphql.outcome`, not the HTTP status, for GraphQL failure ratios; a typed business payload (for example an interview action refusal) is not an error entry and counts as `success`.

## Run

Create the secret files described in the README ("Container runtime"), then:

```bash
docker compose -f compose.yaml -f compose.observability.yaml --profile api up -d --build
scripts/generate-local-traffic.sh 120
```

`generate-local-traffic.sh [seconds=60] [base-url=http://127.0.0.1:8080]` first checks `/health` (BLOCKED, exit 2, if there is no answer), then sends the request cycle for exactly the given duration (each request limited to 3 s), prints `ok/4xx/5xx/failed` counts every 10 s and ends with `RESULT: PASS|FAIL|BLOCKED ...`. One 4xx per cycle is the intentional invalid query; the run fails on any 5xx or failed request. `--help` lists the exit codes (see "Operator scripts" in `engineering-quality.md`).

### Measuring telemetry overhead (opt-in search mix)

Decision: the overhead of the observability overlay is measured with the same script and the same seeded data, overlay off and then on, so that the only difference is the telemetry. Why: the default mix only exercises `/health` and trivial queries, which never touch MongoDB, so it cannot show what OpenTelemetry costs a real request; the risk it controls is a production claim ("telemetry is cheap") made without a measurement. Every job query needs authentication, so this mode is the one documented exception to "the script sends no credentials" (see "Operator scripts" in `engineering-quality.md`): the tokens belong to synthetic candidates from the seed, the base URL must be loopback, and the client sends queries only. The server still records a search session for every `jobs` call, so the database grows a little with each run; reset or ignore the growth, but keep it comparable between the two configurations.

**What is and is not a signal.** Throughput is bounded by the per-actor query cost budget (packaged 10000 per 60 s) because the script paces itself to stay below it; it is therefore **not** an overhead signal. The signals are the latency percentiles (p50/p95/p99 of successful requests) and the CPU and memory of the API container. Aim for at least 1000 successful requests per run; with fewer, p99 is not reliable and the result line carries `low-sample=yes`. The start line prints the pace and the minimum seconds needed. With 8 candidates and `--concurrency 8` (one worker per token) every token serves one worker, and the run needs roughly `1000 * pause / workers` seconds, where `pause = 60 * average_cost / (0.8 * 10000)` (for example an average cost of 40 gives a pause of 0.3 s and about 38 s); use at least that, and a round 120 s to be safe. A `--concurrency` that is not a multiple of the token count loads the busiest token with `ceil(workers / tokens)` workers and the pause grows accordingly.

**Procedure** (identical for both configurations; a difference in procedure is a confound). The recorded baseline (2026-11-03) used a 300 s measured run, a 60 s warm-up after every start, and the order off, on, on, off so that drift over the session does not favour either configuration; follow the same. Two prerequisites found on the first real run:

- `signUp` is refused with `ADMIN_BOOTSTRAP_REQUIRED` until the singleton Admin exists. On a fresh local database, seed it once through the API's admin seed (`ADMIN_SEED_ENABLED`, `ADMIN_SEED_NAME`, and the password as `ADMIN_SEED_PASSWORD_FILE` pointing under `/run/secrets/`, which the entrypoint exports inside the process only), for example with a small local compose override that is not committed. After the first start the seed is a no-op.
- Start only `mongodb api` (plus the six overlay services for the "on" runs). `--profile api up` without service names also starts Kafka, which is not needed here and needs its own secrets and port 9092.

```bash
# 1. Start the stack WITHOUT the overlay (create the secret files from the README first), and seed once per database.
docker compose -f compose.yaml --profile api up -d --build mongodb api
scripts/seed-local-jobs.sh http://127.0.0.1:8080 --jobs 50 --candidates 8      # writes .local/data/perf-seed.env (0600)

# 2. Throwaway warm-up run after the start (JIT, connection pools, caches). Not recorded.
( . .local/data/perf-seed.env && scripts/generate-local-traffic.sh 60 --mix search --concurrency 8 )

# 3. Measured run. In a second terminal, sample the API container every 5 s for the same time (Ctrl+C when the run ends):
cid="$(docker compose -f compose.yaml --profile api ps -q api)"
while sleep 5; do docker stats --no-stream --format '{{.CPUPerc}} {{.MemUsage}}' "$cid"; done | tee .local/logs/overhead-off-stats.txt
#    and in the first terminal (a subshell keeps the tokens out of your shell; rerun the seed if they expired):
( . .local/data/perf-seed.env && scripts/generate-local-traffic.sh 300 --mix search --concurrency 8 --latency-file .local/logs/overhead-off.txt )

# 4. Stop and start again WITH the overlay, same restart discipline (the MongoDB data and the seed survive in .local/data/mongodb).
docker compose -f compose.yaml -f compose.observability.yaml --profile api stop api otel-collector tempo loki alloy prometheus grafana
docker compose -f compose.yaml -f compose.observability.yaml --profile api up -d --wait mongodb api otel-collector tempo loki alloy prometheus grafana
#    repeat steps 2 and 3, with -f compose.observability.yaml in the `ps -q api` command and overhead-on* file names;
#    then the second "on" run and the final "off" run with the same restart.

# 5. Summarise the container samples of each run: mean and max CPU %, max memory.
awk '{ c = $1 + 0; s += c; if (c > m) m = c; n++ } END { printf "cpu mean %.1f%% max %.1f%% samples %d\n", s / n, m, n }' .local/logs/overhead-off-stats.txt
awk '{ print $2 }' .local/logs/overhead-off-stats.txt | sort -h | tail -1
```

The traffic script never calls docker; the sampling loop is separate on purpose. If several pairs of runs are done, alternate the order (off, on, on, off) to average out drift; compare medians of the percentiles and of the CPU means, not single numbers. The service is called `api` in `compose.yaml` (no `container_name`), so `ps -q api` finds the right container whatever the project name is.

**Details.** `seed-local-jobs.sh [base-url] [--jobs M=50, at most 500] [--candidates N=1, at most 8]` creates the synthetic recruiter `perf-recruiter`, `--jobs` published jobs (deterministic titles, the skill `perfseed`, five fixed cities) and the candidates `perf-candidate-N` through the public GraphQL API (at most 8 candidates, because login and signup allow 20 attempts per minute per network; a rate limit ends the run BLOCKED, `reason=auth-rate-limited`). It is idempotent: it creates nothing if the recruiter already owns that many open jobs, and job requests use fixed idempotency keys. Passwords are random per run, written to the file right after each signup, never printed. The tokens are written only when all of them passed a format check (token characters and length, strict ISO-8601 expiry) and the base URL is loopback (`127.0.0.1`, `localhost` or `[::1]`, exact host; there is no option for a remote host); requests follow no redirect and use no proxy. Rerun it to refresh expired tokens. If the file is lost while the accounts exist it stops BLOCKED. Accounts carry no email: email is optional and not a login identity.

`generate-local-traffic.sh [seconds] [base-url] --mix search [--concurrency N] [--latency-file PATH]` sends two MongoDB-backed operations, `jobs(first: 20, filter: {skills: ["perfseed"]})` (UC01) and `job(id:)` (UC03), alternated by N workers (1-16, default 4). The token comes only from `TRAFFIC_BEARER_TOKEN` or `TRAFFIC_BEARER_TOKENS` (comma-separated, round-robin), never from an argument; it reaches curl through a 0600 header file in a 0700 directory `.local/data/traffic.XXXXXX` that is removed on exit, so it is not in the process list. Source the seed file in a subshell, as above, so the tokens do not stay in your shell. One warm-up search and one detail request (not counted) read the job ids and `extensions.cost`; the clock of the run starts after them, workers start staggered by `pause * i / workers`, and a request still in flight at the end finishes (up to 3 s past the given seconds). Every request opens a new connection (no keep-alive) and the connect time is part of the latency, identically in every run. BLOCKED (exit 2): no token, a token in an unexpected format, no API, a refused token, a persisted-query allowlist that is not `off`, no seeded jobs, a failed warm-up, no `extensions.cost` in the answers. Any HTTP 429 fails the run (`reason=cost-budget-exhausted`) because the numbers would measure rejections; an unwritable or link-redirected `--latency-file` fails it too (`reason=latency-file-refused`). The result line adds `429` and `gqlerr` (HTTP 200 with a GraphQL `errors` entry) counts, `requests`, `throughput`, `p50`/`p95`/`p99` in ms (nearest rank over the successful measured requests), `samples` and `concurrency`. The latency file has one `kind class seconds` line per measured request and must resolve below `.local/logs/`. After a SIGKILL, remove a leftover `.local/data/traffic.*` directory by hand. Self-test without network: `scripts/tests/local-traffic-options.sh`. A single pair of runs on a laptop is local evidence, not a production measurement.

Grafana: `http://127.0.0.1:3000`, user `admin`, password `$GRAFANA_ADMIN_PASSWORD` (default `admin`). Prometheus: `http://127.0.0.1:9090`. Tear down with `docker compose -f compose.yaml -f compose.observability.yaml --profile api down`; Tempo and Loki data is on tmpfs and disappears with the containers.

## Alert rules, routing and drills

Scope: the eight rules in `docker/observability/alerts.yaml`, their unit tests, a local Alertmanager with two local receivers, and fault drills that follow an alert to the sink. Verified on 2026-11-06 and 2026-11-07 on one workstation; see [Recorded results](#recorded-results-2026-11-06-and-2026-11-07). Thresholds and windows are provisional local values, not SLOs. Production routing, on-call contacts and any paging provider are not defined here. The design and acceptance IDs (OAV-01 to OAV-06) are in the [operational alert verification](specs/operational-alert-verification.md) specification.

### Rules

| Alert | Severity | Fires when (`for`) | No-data behavior |
|---|---|---|---|
| `HiringApiHighErrorRate` | page | More than 5% of body-phase, non-probe requests are 5xx (2 m), and the non-probe rate is at least 0.1 req/s over 1 m | No data below the floor: a total 5xx outage at lower traffic does not fire (accepted limitation) |
| `HiringBacklogOldestPendingTooOld` | ticket | `hiring_backlog_oldest_pending_age_seconds` above 300 for each `hiring_capability` (2 m) | No oldest-age series for an empty backlog, so it stays silent |
| `HiringBacklogUnobserved` | ticket | Sample age above 60 s, or the sample-age series is absent (2 m) | Absence is the firing condition: missing data is unobserved, not zero |
| `HiringApiSlowRequests` | ticket | p95 above 0.3 s (2 m) with the non-probe rate at least 0.1 req/s | No data below the floor |
| `HiringKafkaConsumerLagHigh` | ticket | Lag above 1000 records for 10 m (minimum over 10 m) | Starting threshold |
| `HiringKafkaPublisherSendFailureRatioHigh` | ticket | Failed sends above 10% of sends over 5 m (5 m), only when sends occur | No sends means no ratio, so it stays silent |
| `HiringKafkaProducerFenced` | ticket | At least 3 `ProducerFencedException` or `InvalidProducerEpochException` send failures in 15 m (15 m) | A single fence is expected and stays silent |
| `HiringKafkaRebalanceRateHigh` | ticket | More than 5 partition moves per minute for 10 m | Starting threshold |

The Kafka rules are tested with `promtool`. `HiringKafkaProducerFenced` was observed firing on a running Kafka-enabled stack in one operator drill on 2026-11-08 (see the [Kafka flow hardening](specs/kafka-flow-hardening.md) specification, KFH-04.9); that drill's harness is git-ignored and not in the repository. The lag, send-failure-ratio and rebalance rules have not been observed firing under Kafka-enabled traffic. The lag and rebalance rules have not been observed firing, so their alerts, whose series carry labels outside the alert allowlist (see below), have not been checked against it.

### Routing and receivers

- `severity="page"` goes to `local-page`; `severity="ticket"` goes to `local-ticket`. The default receiver is `local-ticket`, so an alert without a `severity` label also lands there. No shipped rule lacks one.
- Both receivers post to `http://alert-sink:8080/alerts` with `send_resolved: true`. Nothing leaves the stack.
- Alerts are grouped by `alertname` and `hiring_capability`. `group_wait` is 5 s, `group_interval` 10 s and `repeat_interval` 30 m. These are local drill values chosen so drills finish quickly; they are not delivery-latency claims.
- **Label allowlist (decision D7).** An alert may carry only these ten label names: `alertname`, `severity`, `hiring_capability`, `job`, `instance`, `exported_job`, `service_name`, `telemetry_sdk_language`, `telemetry_sdk_name` and `telemetry_sdk_version`. The last seven come from our Prometheus scrape and the OpenTelemetry resource, not from hiring data; a real alert carries them, so a three-name set would fail correct behavior. Closed values: `severity` is `page` or `ticket`; `hiring_capability` is `operational_event_outbox`, `embedding_work` or `drill`; `service_name` is `hiring-api`. Annotations are `summary` only. Any other label name fails OAV-02.5. Why it matters: a new label could carry hiring content or an identifier into the sink and the log, and an allowlist fails closed on a new name instead of trusting every label. Labels are not stripped by relabeling in this slice. The check runs in two places: the delivery drill on its synthetic alerts, and the backlog drill on each real alert after it fires (the age alert and `HiringBacklogUnobserved`), where it records how many real alerts it inspected. The Kafka rules are not yet fully covered: the lag rule keeps its series labels, so its alerts also carry `hiring_consumer_group`, `messaging_destination_name` and `messaging_kafka_partition`; the rebalance rule carries `hiring_consumer_group`. None of these names is on the allowlist. The send-failure-ratio rule keeps no series labels. The lag and rebalance rules have not been observed firing, so the check has not seen them; a firing of either would fail it. `HiringKafkaProducerFenced`'s expression is `sum(...)` with no `by` clause, so its alert should carry only `alertname` and `severity`; that is not checked against the allowlist, and no label check on that alert is recorded.
- `alert-sink` logs each webhook as one record that still contains the receiver name, the status and the alert labels, so a drill can judge delivery from `docker compose logs alert-sink`. It publishes no port and stores nothing.

### Decisions

| Decision | Reason | Why it matters |
|---|---|---|
| `promtool` runs from the pinned Prometheus image (service `alert-rules`, profile `alert-tests`, no network, read-only mounts) | No new image; the test binary matches the Prometheus version that loads the rules | The test run cannot reach the network or write the repository |
| The rule tests and the drills are not in `scripts/check-local.sh` | They need Docker, and a skipped Docker step must not read as a pass | `check-local.sh` does not prove the alert rules; run the commands below |
| No rule was changed by this slice | Hand evaluation and the runs found no rule defect | Thresholds stay as they were in `alerts.yaml` |
| Alertmanager is local only: `127.0.0.1:9093`, `read_only`, `cap_drop: [ALL]`, 64 MiB, tmpfs `/alertmanager`, pinned by digest | A route must not be reachable beyond the workstation, and the digest, not the tag, decides what runs | Silences and the notification log are lost when the container is recreated |
| The sink is the pinned collector image logging webhooks (no new image, no credential, no external endpoint) | Alertmanager's own counters alone would not show what was delivered | It is a local proof, not an escalation design |

### Commands

Start the stack. Prometheus reads the `alerting` section when it starts; if it was already running before the alert files changed, restart it with `docker compose -f compose.yaml -f compose.observability.yaml --profile api restart prometheus`. The delivery drill stops with that instruction if it finds Prometheus without the Alertmanager.

```bash
docker compose -f compose.yaml -f compose.observability.yaml --profile api up -d --build
```

The scripts are run with `bash`, so the executable bit is not needed. Run them from the repository root, outside any sandbox that blocks Docker.

```bash
# Rule tests: promtool check rules and test rules (no stack needed; needs Docker)
bash scripts/check-alert-rules.sh

# OAV-02: routing, resolved messages, a dead sink, local-only exposure (about 35 s on the recorded run)
bash scripts/run-alert-delivery-drill.sh

# OAV-03: a stalled outbox backlog through the real age rule (about 9 min on the recorded run)
bash scripts/run-alert-backlog-drill.sh --scenario stalled-backlog

# OAV-04: MongoDB stopped on a healthy backlog (about 3.5 min on the recorded run)
bash scripts/run-alert-backlog-drill.sh --scenario mongo-outage
```

| Command | Preconditions (checked by the script) | What it changes | Ends with |
|---|---|---|---|
| `check-alert-rules.sh` | Docker, the compose files and both rule files | Nothing persisted | `RESULT: PASS`, `FAIL` or `BLOCKED` |
| `run-alert-delivery-drill.sh` | Alertmanager and Prometheus answer on loopback; Prometheus lists `alertmanager:9093`; `alert-sink` is running | Stops and starts `alert-sink`; posts three synthetic alerts named `OperationalAlertDrill*` (closed label set, no hiring data) and resolves them | Sink running; synthetic alerts resolved |
| `run-alert-backlog-drill.sh --scenario stalled-backlog` | API answers on `127.0.0.1:8080` (`--profile api`); `mongodb` running; no backlog alert firing; no oldest-age series; sample age present; **zero `Retryable` outbox rows** | Creates exactly one job with `scripts/seed-local-jobs.sh --one-fresh-job --candidates 1` (one createJob and one publishJob with random idempotency keys; it ignores `--jobs` and the recruiter's existing jobs, so it cannot replay or count earlier seeds). That leaves one pending `event_outbox` row (nothing drains outbox rows with `KAFKA_ENABLED=false`). After the firing it removes that job's pending rows, as described in [What the backlog drill deletes](#what-the-backlog-drill-deletes) | Backlog empty unless the release refused or a delete failed. The seeded job and accounts stay (their events are deleted); each run leaves one more published job; the seed refreshes `.local/data/perf-seed.env` |
| `run-alert-backlog-drill.sh --scenario mongo-outage` | The same preconditions, including zero pending outbox rows | Stops `mongodb`, waits for `HiringBacklogUnobserved`, starts `mongodb` again | MongoDB running |
| `run-alert-backlog-drill.sh --scenario mongo-outage-during-stall` | As `stalled-backlog` | Stalls first, then stops MongoDB while the age alert is firing | Not run (see below) |
| `run-alert-backlog-drill.sh --scenario all` | As above | Runs `stalled-backlog`, then `mongo-outage` | Not run as one combined run |

Exit codes for every script: 0 PASS, 1 FAIL, 2 BLOCKED (precondition, usage or a refused release), 130 interrupted. The last line is `RESULT: ...`. Each drill writes its timeline and verdicts to `.local/logs/alert-drills/<UTC time>-delivery/evidence.md` or `.local/logs/alert-drills/<UTC time>-backlog/evidence.md`; the backlog drill also keeps `seed-local-jobs.log` there. `.local/` is git-ignored: the evidence is never committed, and the summary in this page is the only copy that is shared.

### What the backlog drill deletes

The drill creates exactly one job itself and removes only that job's pending rows, and only when a check passes:

1. The database clock is read before seeding. The seed creates one job by construction (`--one-fresh-job`). The drill then counts the jobs of the seed recruiter `perf-recruiter`, matched by its id, created since that instant. Any count other than one ends the drill BLOCKED and deletes nothing.
2. The drill collects the `_id` values of the job's pending outbox rows (`aggregateType` Job, `aggregateId` the job, state `Retryable`, `occurredAt` at or after the instant) and of its embedding work row (`_id` `Job:<job>`, state `Ready` or `Retry`, `createdAt` at or after the instant).
3. `scripts/alert_release_scope.py` decides, as a pure function: exactly one job, 1 to 4 outbox rows and 0 to 2 embedding rows. Anything else is refused.
4. The delete removes those `_id` values only, with the state and time conditions kept, so a row written after the check is not deleted.

**What is guaranteed.** The drill creates exactly one job, so one job's rows are pending by construction. The post-check catches a second `perf-recruiter` job created in the same window and ends BLOCKED with nothing deleted. Deletion is limited to that job's rows, selected by identity and time and removed by `_id`, so rows written after the check are not deleted. A refused release deletes nothing. A delete call that fails, or returns no usable count, ends FAIL and prints a read-only inspection command for the same scope.

**What is assumed.** No other writer creates or touches the seeded job during the run. A second writer's rows would stay pending and are not deleted. The identity fields (`aggregateType`, `aggregateId` and the `Job:<id>` key) were read from the source; the filter ran once on 2026-11-06 and the recruiter-filtered version on 2026-11-07. A mismatch makes the drill refuse, never delete more.

**Not exercised by a run:** the failed-delete path, the verdicts-before-BLOCKED path and the refusal path end to end. The refusal is covered only by the unit test `scripts/tests/test_alert_release_scope.py` (8 tests) and by reading the script.

Side effects that stay: each run leaves one more published job in the local database; the seeded job and its synthetic accounts remain (their events are deleted); the release may delete the embedding work row of that job, so the job is left with no queued embedding work; the seed replaces the tokens and passwords in `.local/data/perf-seed.env` (mode 0600), so earlier copies of those values stop being current.

**The `--one-fresh-job` option.** `scripts/seed-local-jobs.sh --one-fresh-job --candidates 1` creates and publishes exactly one new job with random idempotency keys, ignoring `--jobs` and the existing jobs; it never counts the recruiter's open jobs. Why: the seed's idempotency receipts expire after 7 days, so the earlier open-plus-one design could, a week after the first run, replay many jobs or create none. This option cannot. Covered by `scripts/tests/test_seed_fresh_job.py` (3 tests, no network). The 2026-11-07 stalled-backlog run used it against the live API and recorded the one job created (see the stalled-backlog row).

### When a backlog drill is BLOCKED on the outbox

The backlog drills refuse to start while `event_outbox` has `Retryable` rows, because the age alert's timeline would be ambiguous. The BLOCKED line prints the pending count and the oldest `occurredAt`, read-only. No script clears a standing backlog, and the release deletes only the seeded job's rows. Clearing old rows is therefore a manual step, and it is your decision:

- Old rows from earlier local use: back them up under `.local/backups/` first, then remove them by hand. The containerised API cannot drain them (`KAFKA_ENABLED=false`); draining them through a publisher with Kafka on is not verified in this slice.
- Rows of a drill whose release was refused: nothing is deleted. The refusal prints a read-only `printjson` command that shows that scope. The script itself never deletes on a refusal. The refusal prints a read-only `printjson` inspection command (the rows of that scope) and nothing else; any delete is written by you after you have read those rows. A delete that fails ends the drill FAIL (exit 1) and prints the same read-only inspection command; the rows may still be pending, and any removal is yours.

On 2026-11-06 a standing backlog of 10,842 `Retryable` rows (oldest `occurredAt` 2026-11-03) blocked the first attempts. The user backed the rows up under `.local/backups/` and cleared them before the recorded backlog run.

### What the containerised API does to the outbox

With `KAFKA_ENABLED=false` (the Compose default for `api`), nothing claims `event_outbox` rows. So `HiringBacklogOldestPendingTooOld` fires for any outbox row older than 5 minutes plus its 2-minute `for`. On 2026-11-06 the real rule fired about two minutes after Prometheus restarted, for rows left from earlier local use, and `local-ticket` received it before any drill ran. A demo deployment that keeps Kafka off would alert continuously. Whether that is acceptable is an owner decision. This slice changed no rule.
