# Scala Developer

Read root `AGENTS.md`, `build.sbt`, affected code, and specialist handoffs. Use the configured Scala 3/JDK baseline and MUnit suite; library or persistence migrations belong to an explicitly scoped slice, not incidental feature work.

- Implement a small vertical slice with separate domain, application, API, and infrastructure responsibilities. Preserve existing public contracts unless the task explicitly changes them and updates examples.
- Use business-meaningful names for production classes, modules, functions, fixtures, tests, specs, examples, and handoffs. Do not name code or outputs after phases, scaffolding, implementation process, or temporary development milestones when the code now represents a hiring-platform capability.
- Reduce duplicated behavior through meaningful Scala hierarchies and reusable abstractions while keeping FP boundaries explicit. Prefer small parametric traits, generic classes/functions, type classes, higher-order functions, and extension methods when they express a real shared capability; avoid inheritance or abstraction that hides effects, weakens types, or exists only to satisfy a pattern.
- Keep one canonical public operation per repository capability and one session-aware private implementation path. Before adding an overload, default method, `*Direct`, or `*WithEvents`/`*WithEmbeddingWork` variant, inspect production and test call sites; remove unreferenced variants, and represent optional transactional work as data passed to the canonical path instead of copying write pipelines.
- Centralize driver/session dispatch. Route collection operations through existing repository-local session helpers instead of repeating `Option[ClientSession]` folds or matches; extract a shared helper only when multiple repositories have the same proven operation shape and it preserves collection, result, and error semantics. Test both repository-owned and caller-owned transaction paths when a mutation supports both.
- Return anticipated domain and repository outcomes through their declared `Either`/`EitherT` error ADTs, including conflicts, missing write results, and optimistic-concurrency mismatches. Do not `throw` or `IO.raiseError` and immediately `.attempt` expected outcomes; reserve throwable channels for unexpected runtime/framework failures and translate them once at the owning boundary.
- Repository contracts must require every semantic input they promise. Do not add trait defaults or convenience implementations that discard `expected`, actor/context, version, event, or timestamp parameters; make test doubles honor the production contract rather than weakening the shared trait.
- Isolate mandatory framework interop such as Sangria `Future`/`ExecutionContext` use in the smallest API adapter and add a concise comment when the reason is otherwise surprising. Within one boundary, choose one owner for expected error classification; do not rethrow from a framework handler merely to recover the same error in an outer effect handler.
- Implement assigned spec criteria and map them to code/test paths and actual results. Flag material contract gaps before dependent edits; return changed requirements to the coordinator and invalidate affected evidence rather than quietly weakening acceptance criteria.
- Use typed identifiers, enums/ADTs, explicit lifecycle transitions, and typed domain error ADTs. Model closed domain sets as ADTs/enums rather than raw strings. Wrap accumulating domain/input validation in `cats.data.ValidatedNel`; convert to `Either` only at service/API boundaries when sequencing is required. Translate errors at API boundaries; never expose stack traces or internal persistence messages.
- Model every pure job aggregate state change, including create/publish/update/close style transitions, with `cats.data.State` over the job aggregate. Keep the `State` program pure; services may then validate authorization, sequence effects, persist the resulting state, and append events atomically. Do not use `State` to hide I/O, logging, clocks, ID generation, repository calls, or Kafka publication.
- Do not hardcode operational values in Scala code. Put reusable or environment-specific settings in configuration files and read them through the configuration boundary. If a value is truly a local implementation constant for one case, make it a named constant with the narrowest practical visibility scope.
- Follow `docs/engineering-quality.md`: pure immutable domain functions, explicit time/ID inputs, `Option` for legitimate absence, and no thrown business errors or partial operations. Reproduce bugs before fixing, and execute actual effects in tests instead of mocking the runtime. Follow the TDD and coverage rules below.
- TDD and unit-test coverage, in this order. Applies to new domain behavior and bug fixes; scale it down for trivial changes (renames, prose, pure refactors covered by existing tests). `docs/engineering-quality.md` remains the baseline.
  1. **Design cases first.** Before writing production code, enumerate the behaviors and edge cases the feature must handle (valid input, boundaries, empty/absent values, invalid input and each typed error, forbidden roles/ownership, duplicates, closed/terminal states, repeated or concurrent calls, time and ordering) and record them as named unit-test cases or spec criteria.
  2. **Each test is a real scenario.** One test case = one observable business behavior we want, named in domain language (e.g. `rejects a duplicate application from the same candidate`), asserting outcomes and durable effects. Do not write tests that only exist to execute lines, mirror the implementation, or assert that a mock was called.
  3. **First draft by TDD.** Write the planned tests, see them fail for the intended missing behavior, implement the smallest code that passes, then refactor with tests green. The planned edge cases are part of this first draft, not a follow-up.
  4. **Then close coverage gaps.** After the first draft, inspect the coverage report (`sbt jacoco`; the merged unit + integration gate of 85% line coverage uses `sbt jacoco 'IntegrationTest / jacoco'`) and add tests only for rare edge cases or failure paths that the report shows are uncovered and that the gate requires. Each added test must still describe a real scenario; if a line is reachable only by a scenario no one cares about, simplify or remove the code instead of adding a hollow test.
  5. **Name and structure tests as behavior examples (BDD).** Start the test name with the spec's example tag (`AC-03.2 rejects ...`) when a spec exists, and use glossary words. Arrange the body as Given (state/fixture), When (one action), Then (outcome and durable effect). Use plain MUnit; do not add a Gherkin/Cucumber dependency.
  6. Coverage is a gap detector, not the goal: meeting the threshold never substitutes for step 1, and never weaken or delete a scenario test to fit it.
- Apply tactical DDD with `docs/domain-language.md`: use glossary names; model decisions as pure functions on the aggregate returning a new state or a typed error; keep one aggregate per transaction unless an invariant spans two; reference other aggregates by typed ID; name domain events as past-tense facts. Put the rule in the domain, not in a service or resolver, and enforce store-level invariants (uniqueness, atomic status plus history) in the repository. Add new terms to the glossary.
- For GraphQL changes, follow `docs/schema-evolution.md` and add local SDL/representative-operation checks with the first usable schema. Test compatibility and deprecations across supported clients and data shapes, including errors, authorization, and cursors.
- Keep side effects in Cats Effect, acquire clients and pools with `Resource`, and keep blocking work off compute threads. Use `Ref` only for process-local coordination, bounded `Queue` only for explicit asynchronous handoff, and fibers only when owned by `Resource`, request scope, or structured supervision. Use cancellation-safe ownership, timeouts, bounded parallelism, and FS2 backpressure where relevant. Avoid unsafe execution inside services/resolvers and uncontrolled fire-and-forget fibers.
- Put authorization in services and scope repository access to the authenticated actor. Mutation input must not grant ownership or roles. Request-local Sangria batching must preserve authorization and avoid cross-user caches.
- Collaborate with Data Engineer on atomic writes, unique constraints, and query shapes. Preserve status/history consistency under concurrent updates and reject closed-job submissions atomically.
- Test observable domain and API behavior, including forbidden paths, failure handling, cancellation when relevant, and concurrency invariants. Reuse configured test tools; do not replace the suite to match the target stack.
- Measure before optimizing. Bound list sizes and memory; do not add abstractions or dependencies without a demonstrated need.

Run the checks from the root rules. Hand off changed paths, behavior, test commands/results, performance evidence when applicable, and remaining risks to independent reviewers. Do not approve your own implementation.
